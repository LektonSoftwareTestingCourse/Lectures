## Часть А. E2E-набор (2 балла)

Написать пять сквозных тестов в модуле `e2e-tests`. Каждый сценарий проходит через Gateway, как настоящий клиент, и проверяет **три звена**:

1. **Ответ** — что увидел клиент: `status`, `responseCode`, `rrn`, `authCode`.
2. **Данные** — что стало с деньгами и записями: `availableBalance`, `limit_usage`, `transactions`.
3. **Асинхронный след** — что доехало до логгера и уведомлений.

**Обязательные сценарии:**

| № | Сценарий | Что проверяем |
|---|---|---|
| 1 | Покупка APPROVED | `00`, списание ровно на сумму, запись в логгере |
| 2 | Отказ `51` (недостаточно средств) | код `51`, баланс не изменился, резерв не создан |
| 3 | Отказ `61` (превышен лимит) | код `61`, баланс и счётчики лимитов не изменились |
| 4 | Возврат (reversal, `mti=0400`) | баланс восстановлен, повтор по тому же `rrn` не возвращает деньги дважды |
| 5 | Технический сценарий (на выбор) | отказ публикации → `96` и откат резерва, либо сообщение в DLQ, либо недоступность зависимости |

**Требования:**

- Данные создаются внутри сценария (`POST /api/cards`); карты из `init.sql` не используем.
- Ожидания — только через Awaitility. `Thread.sleep` в наборе быть не должно.
- Сценарии не зависят от порядка запуска и выдерживают повторный прогон.

## Часть Б. CI и демонстрация прогона (1 балл)

Набор подключается к конвейеру вашего репозитория:

- Джоб `e2e-tests` в GitHub Actions поднимает стек (`docker compose up -d`), дожидается готовности сервисов без `sleep` и прогоняет полный набор.
- Прогон на обычной сборке зелёный; ссылка на запуск прилагается в отчёте.
- На приёмке прогон демонстрируется: живой запуск или свежий запуск с логами и видимыми стадиями.

Опыт подключения у вас уже есть: в модуле 4 поднимался джоб `java-services`, в модуле 6 интеграционные тесты прогонялись в Actions с контейнерами. Здесь добавляется одно: стек должен быть поднят внутри джоба.

## Часть В. Прогон против сломанной сборки и баг-репорты (3 балла)

Курс публикует вариант СМП с пятью намеренно внесёнными дефектами: образы с тегом `practice-7-bugs` и файл `docker-compose.practice-7-bugs.yml` в эталонном репозитории. Дефекты относятся к трём звеньям проверки: ответу, данным и асинхронному следу.

**Порядок работы:**

1. Остановить обычную сборку с удалением данных: `docker compose down -v`.
2. Поднять сломанную сборку: `docker compose -f docker-compose.yaml -f docker-compose.practice-7-bugs.yml up -d`.
3. Прогнать свой E2E-набор против неё. Набор, зелёный на обычной сборке, здесь частично падает: падения и есть находки.
4. Каждое падение разобрать: какое звено показало дефект и какое поведение ожидалось по ТЗ.
5. Оформить не менее трёх баг-репортов. В сборке внесено пять дефектов; пять обязательных сценариев ловят не все из них.
6. Вернуться на обычную сборку (`docker compose down -v`, затем обычный `up -d`) и убедиться, что набор снова зелёный.

**Каждый отчёт** — по шаблону курса из 8 полей (модуль 2, лекция 4, слайд 42):

1. ID (`BR-001`)
2. Заголовок: объект + условие + ожидание
3. Шаги воспроизведения: endpoint, данные, порядок
4. Ожидаемый результат
5. Фактический результат
6. Severity
7. Priority
8. Связанное требование и связь со сценарием `SC-NNN`

**Доказательства обязательны:** тело ответа, снимок состояния БД, запись (или её отсутствие) в логгере/очереди.

**Что не считается дефектом:**

- Параметры `?fail=` и `?delay=` у Bin Lookup — спроектированное поведение для отработки таймаутов; отчёты на него не принимаются.
- Падение сценария по причине самого сценария (неверное ожидание, общие данные, `sleep`) — это дефект теста, а не системы.
- Если набор не поймал ни одного дефекта, это результат о наборе, а не о системе: проверьте звенья 2 и 3.

## Формат отчёта

```markdown
# E2E-отчёт: СМП

## 1. Summary
| Всего сценариев | Пройдено (обычная сборка) | Упало (сборка с дефектами) | Оформлено баг-репортов |

## 2. Сценарии
### SC-001: Покупка APPROVED
- Шаги, результат PASS/FAIL, три звена проверки

## 3. Прогон против сборки с дефектами
| Проверка | Сценарий | Звено | Ожидали | Получили |

## 4. Баг-репорты
### BR-001: <заголовок>
- STR, ожидаемый результат, фактический результат
- Доказательства по звеньям
- Severity / Priority, связь с SC-NNN
```

## Критерии

| Критерий | Баллы | Что должно быть |
|---|:---:|---|
| Покрытие e2e | 2 | 5 сценариев, три звена в каждом, изоляция данных, без `sleep` |
| Демонстрация CI | 1 | Джоб `e2e-tests` в Actions, зелёный прогон на обычной сборке, показан на приёмке |
| Баг-репорты | 3 | ≥3 отчёта по шаблону; каждый воспроизводится на сборке `practice-7-bugs`, соответствует реально внесённому дефекту, с доказательствами и связью `SC-NNN` |

Типичные потери баллов: сценарий проверяет только ответ; общие данные; `Thread.sleep`; баг-репорт без доказательств; баг-репорт на спроектированное поведение; набор не падает на сломанной сборке.

## Как сдавать

1. Работа в своём репозитории `Practic{Имя}{Фамилия}`, ветка `practice-7`.
2. Тесты — в модуле `e2e-tests`, отчёт — `docs/practice-7/e2e-report.md`.
3. Прогнать набор в CI и приложить ссылку на запуск.
4. Создать Issue в эталонном репозитории: заголовок «Практика 7 — Фамилия», label `practice-7`, ссылки на репозиторий, ветку, Actions run и артефакт.
5. Полный текст отчёта в Issue не вставляется: LLM-проверка находит отчёт в ветке по пути `docs/practice-7/e2e-report.md`.
