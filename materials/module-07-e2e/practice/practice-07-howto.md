## Шаг 0. Подготовка окружения

1. Подтянуть изменения эталонного репозитория в свой `Practic{Имя}{Фамилия}` (см. `docs/submission-guide.md`, раздел «Синхронизация»).
2. Создать ветку `practice-7` от актуального `main`.
3. Поднять стек: `docker compose up -d`. Дождаться готовности: health-check всех сервисов зелёный.
4. Прогнать вручную через Gateway один сценарий покупки и проверить три звена:
   - ответ: `status=APPROVED`, `responseCode="00"`, есть `rrn` и `authCode`;
   - состояние: `GET /api/cards/{pan}` — `availableBalance` уменьшился ровно на сумму;
   - след: запись о транзакции находится через `GET /api/transactions/search?stan=...` в течение 5 секунд.

**Результат шага:** все три звена доступны. Если какое-то звено проверить не удаётся, начинайте с него: без третьего звена набор не поймает большинство внесённых дефектов.

## Шаг 1. Первый сценарий

1. В модуле `e2e-tests` создайте тест покупки APPROVED по каркасу ниже.
2. Данные создаются внутри сценария: `POST /api/cards`, свои `stan` и `terminalId`. Карты из `init.sql` не используются.
3. Проверка — три звена; ожидание записи — через Awaitility, `Thread.sleep` запрещён.
4. Прогон зелёный локально; повторный прогон тоже зелёный.

**Каркас первого теста:**

```java
class PurchaseE2eTest {

    private static final String GATEWAY = "http://localhost:8080";
    private String pan;

    @BeforeEach
    void setUp() {
        pan = createCard(10_000, 50_000, 500_000);   // своя карта — изоляция данных
    }

    @Test
    void purchase_isApproved_andMoneyIsReserved() {
        Response response = given().baseUri(GATEWAY)
                .contentType("application/json")
                .body(authRequest(pan, 1_500, "000001"))
                .post("/api/transactions");

        // Звено 1: ответ
        assertEquals("APPROVED", response.jsonPath().getString("status"));
        assertEquals("00", response.jsonPath().getString("responseCode"));
        String rrn = response.jsonPath().getString("rrn");

        // Звено 2: состояние
        BigDecimal balance = getBalance(pan);
        assertEquals(0, new BigDecimal("8500").compareTo(balance));

        // Звено 3: асинхронный след
        await().atMost(5, SECONDS).untilAsserted(() -> assertTrue(transactionExists(rrn)));
    }
}
```

**Результат шага:** один зелёный сценарий с тремя звеньями.

## Шаг 2. Полный набор

Дописать набор до пяти сценариев по таблице из задания:

1. Покупка APPROVED.
2. Отказ `51` (недостаточно средств): баланс не изменился, резерв не создан.
3. Отказ `61` (превышен лимит): баланс и счётчики лимитов не изменились.
4. Возврат (`POST /api/cards/{pan}/rollback` с телом `{rrn, pan, amount}`): баланс восстановлен; повтор по тому же `rrn` не возвращает деньги дважды. (В документации reversal обозначается как `mti=0400`; фактический вызов — этот endpoint, Gateway принимает только `mti=0100`.)
5. Технический на выбор: отказ публикации → `96` и откат резерва; сообщение в DLQ; недоступность зависимости (для неё есть штатные параметры `?fail=` и `?delay=` у Bin Lookup).

Проверка набора: сценарии проходят в произвольном порядке и при повторном запуске.

**Результат шага:** пять зелёных сценариев локально.

## Шаг 3. Подключение CI

1. В `.github/workflows/` создайте (или дополните) workflow с джобом `e2e-tests`:
   - runner `ubuntu-latest`, JDK 21;
   - шаг поднятия стека: `docker compose up -d`;
   - готовность сервисов — через health-check с ретраями, не через `sleep`;
   - прогон набора: `mvn -pl e2e-tests test` (или команда вашего модуля).
2. Дождаться зелёного прогона на обычной сборке. Ссылку на запуск приложите в отчёт.

Опыт уже есть: джоб `java-services` из модуля 4, контейнеры в CI из модуля 6. Новое здесь одно: стек поднимается внутри джоба.

**Результат шага:** зелёный прогон `e2e-tests` в Actions.

## Шаг 4. Прогон против сломанной сборки

1. Остановить обычную сборку с удалением данных: `docker compose down -v`.
2. Поднять сломанную: `docker compose -f docker-compose.yaml -f docker-compose.practice-7-bugs.yml up -d`.
3. Прогнать набор. Падения это находки: фиксируйте сценарий, звено, ожидание по ТЗ и фактическое поведение.
4. Вернуться на обычную сборку (`down -v`, затем `up -d`) и убедиться, что набор снова зелёный.

Если набор на сломанной сборке зелёный, проверяйте звенья 2 и 3: набор не видит состояние и след.

**Результат шага:** список падений с разбором по звеньям.

## Шаг 5. Баг-репорты

Не менее трёх отчётов. В сборке внесено пять дефектов; пять обязательных сценариев ловят не все.

Каждый отчёт — по шаблону из 8 полей: [`bug-report-template.md`](bug-report-template.md) (там же скелет для заполнения и пример). Поля: ID, заголовок (объект + условие + ожидание), шаги, ожидаемый результат, фактический результат, severity, priority, связь с требованием и сценарием `SC-NNN`.

- Доказательства по звеньям обязательны: тело ответа, снимок состояния, запись (или её отсутствие) в логе/очереди.
- Перед заведением проверьте, что такой дефект ещё не описан в вашем отчёте: поиск по объекту и условию.
- Отчёты на спроектированное поведение (`?fail=`, `?delay=` у Bin Lookup) не принимаются.
- Качество проверяйте чек-листом из блока про баг-репорты ([`lecture-14-bug-reports.md`](../slides/lecture-14-bug-reports.md)).

**Результат шага:** три отчёта, каждый воспроизводится на сломанной сборке.

## Если что-то пошло не так

| Симптом | Причина | Действие |
|---|---|---|
| Тесты зелёные поодиночке, падают вместе | общие данные | своя карта на сценарий, уникальные `stan` и `terminalId` |
| Локально зелёный, в CI красный раз в несколько прогонов | `sleep` или гонка | Awaitility с таймаутом по сервису |
| Тест зелёный при остановленном consumer | нет третьего звена | добавить проверку следа через Awaitility |
| Набор зелёный на сломанной сборке | проверяется только ответ | добавить звенья 2 и 3 |
| `docker compose up` на сломанной сборке не находит образ | локально образа нет, а pull не сработал | проверить интернет и повторить `docker compose -f docker-compose.yaml -f docker-compose.practice-7-bugs.yml pull`; при 403 — сообщить преподавателю |
