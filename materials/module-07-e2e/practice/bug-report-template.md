# Шаблон отчёта о дефекте (баг-репорт)

> **Модуль**: 7 — E2E и тестирование бизнес-сценариев
> **Применение**: практика 7, часть В (баг-репорты); единый шаблон курса
> **Теория**: [`lecture-14-bug-reports.md`](../slides/lecture-14-bug-reports.md) — назначение полей, оценки, чек-лист

Восемь обязательных полей. Отчёт без любого из них возвращается на доработку.

## Поля шаблона

| № | Поле | Назначение | Требование |
|---|---|---|---|
| 1 | **ID** | Ссылка на отчёт | Формат `BR-NNN`, уникален в работе |
| 2 | **Заголовок** | Дефект ищут и группируют по заголовку | Объект + условие + ожидание; описывает поведение, а не решение |
| 3 | **Шаги воспроизведения** | Повторить дефект | Начальное состояние, точка входа, данные, порядок действий; повторяемость числами («3 раза из 3») |
| 4 | **Ожидаемый результат** | Норма, с которой сравниваем | С опорой на требование, спецификацию, контракт или ТЗ; источник указан явно |
| 5 | **Фактический результат** | Наблюдаемое поведение | Код, тело ответа, значения полей; без версий о причине |
| 6 | **Severity** | Степень влияния на систему | Обоснована бизнес-последствием |
| 7 | **Priority** | Порядок исправления | Согласуется с релизом; не дублирует severity |
| 8 | **Связи** | Прослеживаемость | Связанное требование и сценарий `SC-NNN` (или сессия `SES-NN`) |

**Доказательства обязательны** и прикладываются до назначения исполнителя: тело ответа, снимок состояния БД, запись (или её отсутствие) в логе/очереди, идентификаторы для поиска (`stan`, `rrn`, PAN, время операции).

## Скелет для заполнения

```markdown
### BR-001: <объект> при <условии> <ожидание, которое нарушено>

- **Шаги.** 1. <начальное состояние>. 2. <действие с данными>. 3. <действие>. 4. <наблюдение>.
- **Ожидалось:** <норма по требованию/контракту>.
- **Получено:** <наблюдаемое поведение с кодом, телом ответа, значениями>.
- **Доказательства:** <ответ, снимок состояния, записи в логе, идентификаторы>.
- **Severity:** <…> | **Priority:** <…>
- **Связи:** требование <…>, сценарий SC-NNN.
- **Воспроизводимость:** <N раз из N>.
```

## Пример (разобран в блоке про баг-репорты)

### BR-002. Повтор авторизации с тем же stan создаёт второй резерв

- **Шаги.** 1. Поднять стенд, дождаться готовности сервисов. 2. Создать карту ACTIVE: баланс 10 000, лимиты 50 000 и 500 000, зафиксировать PAN. 3. Отправить POST /api/transactions: mti 0100, сумма 150 000, stan 000042, terminalId TERM001, merchantId MERCH00000000042. 4. Зафиксировать ответ и rrn. 5. Повторить запрос без изменений. 6. Запросить состояние карты и список резервов.
- **Ожидалось:** повторный запрос возвращает исходный rrn, резерв остаётся один (требование идемпотентности авторизации).
- **Получено:** второй ответ APPROVED с новым rrn; два холда на карту; баланс уменьшился на 300 000.
- **Доказательства:** оба тела ответа Gateway (один stan, разные rrn), снимок баланса и списка резервов, две записи в логе с одним stan.
- **Severity:** критическая (деньги клиента заблокированы дважды, при клиринге это двойное списание). **Priority:** высокий (идемпотентность входной границы относится к критичным для выпуска свойствам).
- **Связи:** требование идемпотентности авторизации, сценарий SC-003.
- **Воспроизводимость:** 3 раза из 3.

## Самопроверка перед отправкой

- [ ] Дефект воспроизведён дважды, а не однократно
- [ ] Заголовок содержит объект, условие и отклонение
- [ ] В шагах есть начальное состояние, точка входа, данные и ожидание на шаге
- [ ] Ожидаемый результат опирается на требование или контракт
- [ ] Приложены доказательства: ответ, состояние данных, записи в логах
- [ ] Указаны severity и priority, важность обоснована влиянием
- [ ] Указана связь с требованием и со сценарием `SC-NNN`
- [ ] Проверено, что такой дефект ещё не заведён: поиск по объекту и условию
- [ ] Отчёт проверен на актуальной сборке
