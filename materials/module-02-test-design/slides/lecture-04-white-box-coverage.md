### Слайд 3. От чёрного ящика к белому

**Слайд:**
- Техники чёрного ящика опираются на требования и описание поведения. Техники белого ящика опираются на внутреннее устройство: код и его структуру.
- Чёрный ящик: взгляд снаружи
- Вход — требования и спецификация.
- Вопрос: «что система должна делать?»
- Инструмент: КЭ, ГЗ, pairwise, таблицы решений.
- Не даёт ответа, все ли ветви кода задействованы.
- Белый ящик: взгляд изнутри
- Вход — исходный код и его структура.
- Вопрос: «какие части кода ещё не выполнялись?»
- Инструмент: покрытие операторов, ветвей, условий.
- Дополняет чёрный ящик, а не заменяет его.
- Почему это не замена: сто процентов покрытия не гарантируют корректности — тесты могут исполнять код, но ничего не проверять.

**Speaker notes:**

> Оснований для перехода от чёрного ящика к белому два.
>
> Первое. Техники чёрного ящика отвечают на вопрос, что подлежит проверке, но не дают ответа на вопрос о том, какие части реализации остались невыполненными. Полный набор классов эквивалентности и граничных значений может не задействовать отдельные ветви кода. Покрытие кода выявляет такие участки количественно.
>
> Второе. Состав решений определяется реализацией, а не требованиями. Одно и то же требование может быть реализовано одной ветвью или несколькими; обработчики исключений в требованиях, как правило, не описаны вовсе.
>
> Отсюда следуют два положения. Техники белого ящика дополняют техники чёрного ящика, но не заменяют их. Покрытие является метрикой выполнения, а не метрикой проверки: тест может выполнить оператор и не проверить его результат. Это ограничение рассматривается в конце блока.

### Слайд 4. Что такое покрытие кода

**Слайд:**
- Покрытие кода (code coverage) — доля структурных элементов программы, выполненных при прогоне набора тестов, выраженная в процентах.
- Что считаем
- Структурный элемент: оператор, ветвь, условие, путь.
- На чём считаем
- На результате прогона конкретного набора тестов, а не на тесте по отдельности.
- Как измеряем
- Инструментом: он инструментирует код и фиксирует исполненные элементы.
- Формула: покрытие = выполненные элементы ÷ всего элементов × 100%.
- Уровень покрытия задаётся выбором элемента: что считаем — то и покрываем. Поэтому «уровень покрытия» — это не одно число, а семейство метрик.

**Speaker notes:**

> Определение. Покрытие кода (code coverage) — степень, в которой заданные элементы покрытия оказались выполнены при прогоне набора тестов, выраженная в процентах. Формулировка опирается на определение термина coverage в ISTQB Glossary.
>
> К определению необходимы три уточнения.
>
> Первое. Элемент покрытия задаётся явно, поскольку от его выбора зависит значение метрики. В структурном тестировании применяются четыре основных типа элементов.
>
> Оператор (statement) — минимальная исполняемая инструкция. Определение и порядок измерения: ISTQB CTFL v4.0, раздел 4.3.
>
> Ветвь (branch) — результат вычисления решения, определяющий одно из направлений передачи управления. В терминологии ISTQB используется синоним «решение» (decision); там же.
>
> Условие (condition) — атомарное логическое выражение, принимающее значение «истина» или «ложь». Атомарным называется условие, не содержащее логических операторов. Определение приведено в ISTQB Glossary. Условие и ветвь являются разными элементами: одно решение может состоять из нескольких условий.
>
> Путь (path) — последовательность узлов графа потока управления от точки входа до точки выхода. Определение графа потока управления и понятие пути приведены у Куликова, раздел 2.2.
>
> Второе. Покрытие вычисляется на наборе тестов, а не на отдельном тесте. Один тест выполняет одно подмножество элементов, другой — другое; метрика описывает их суммарный прогон.
>
> Третье. Значение метрики получают инструментальным измерением. Инструмент выполняет инструментирование байт-кода или исходного кода, вставляя счётчики, фиксирующие факт выполнения элемента, и агрегирует результат.
>
> Следствие из определения: уровень покрытия определяется выбором элемента и представляет собой семейство метрик, а не единственную величину.
>
> Далее фрагмент кода приводится целиком, после чего все четыре типа элементов перечисляются на примерах из этого фрагмента, а затем на нём же рассматриваются все шесть уровней покрытия.

### Слайд 5. Фрагмент кода: метод getIssuerId()

**Слайд:**
- Сервис: Authorization · файл: services/authorization/src/main/java/com/processing/authorization/client/BinLookupClient.java · метод: getIssuerId(String pan)
```java
public Optional<String> getIssuerId(String pan) {
    if (pan == null || pan.length() < 6) {
        LOG.warn("Bin lookup skipped: PAN too short");
        return Optional.empty();
    }
    String bin = pan.substring(0, 6);
    try {
        BinLookupResponse response = restClient.get().uri(url + "/api/bin/{bin}", bin)
                .retrieve().body(BinLookupResponse.class);
        String issuerId = response != null ? response.issuerId() : null;
        LOG.debug("Bin lookup OK: bin={} -> issuerId={}", bin, issuerId);
        return Optional.ofNullable(issuerId);
    } catch (Exception e) {
        LOG.warn("Bin lookup failed for bin={}: {}", bin, e.getMessage());
        return Optional.empty();
    }
}
```
- Условия: A — pan == null · B — длина pan меньше 6 · C — response != null
- Решения: guard A || B · тернарный оператор по C · try/catch  →  8 операторов · 5 ветвей · 4 линейных пути

**Speaker notes:**

> Все дальнейшие уровни рассматриваются на одном фрагменте кода.
>
> Приведён метод getIssuerId класса BinLookupClient из сервиса Authorization учебного проекта. Метод получает идентификатор банка-эмитента из внешнего сервиса bin-lookup: из номера карты выделяются первые шесть цифр, образующие BIN.
>
> Выбор метода обусловлен тремя обстоятельствами. Он содержит составное условие с логическим сложением и коротким замыканием, тернарный оператор и обработчик исключения. Эти конструкции требуют различных наборов тестов для разных уровней покрытия. Метод имеет небольшую длину и полностью размещается на слайде. Код приведён без изменений.
>
> Перечислим структурные элементы метода.
>
> Атомарных условий три: A — pan равен null; B — длина pan меньше шести; C — ответ сервиса не равен null. Условия A и B независимы и соединены логическим сложением.
>
> Решений три вида: составное решение A || B в первой ветви; тернарный оператор по условию C; конструкция try-catch.
>
> Операторов восемь; они перечислены на следующем слайде. Ветвей пять: истинная и ложная ветви решения A || B, нормальное завершение и ветвь исключения конструкции try-catch, ложная ветвь тернарного оператора. Линейных путей четыре; они перечислены при рассмотрении последнего уровня.
>
> Уровни покрытия различаются тем, какое из этих множеств должно быть покрыто полностью: три, пять или четыре элемента. Примеры элементов каждого типа приведены на двух следующих слайдах.

### Слайд 6. Элементы покрытия: оператор и ветвь

**Слайд:**
- Оператор — минимальная исполняемая инструкция. ISTQB CTFL v4.0, 4.3
| #  Оператор в коде |
| 1   LOG.warn("PAN too short") |
| 2   return Optional.empty()  (в guard) |
| 3   String bin = pan.substring(0, 6) |
| 4   response = …retrieve().body(…) |
| 5   issuerId = … ? … : null |
| 6   LOG.debug("Bin lookup OK…") |
| 7   return Optional.ofNullable(issuerId) |
| 8  тело  catch : два оператора |
- Итого 8 операторов. Условие if и вызов restClient.get() операторами не являются.
- Ветвь — результат вычисления решения. Синоним: решение. ISTQB CTFL v4.0, 4.3
| #  Ветвь |
| 1   A || B  → истина → выход |
| 2   A || B  → ложь → далее |
| 3   try  → нормальное завершение |
| 4  тернарный  C  → ложь |
| 5   catch  → исключение |
- Итого 5 ветвей. Истинная ветвь тернарного оператора относится к ветви 3 и отдельно не считается. Каждому решению отвечают две ветви: A || B содержит два условия, но является одним решением.

**Speaker notes:**

> Два первых типа элементов покрытия с примерами из рассматриваемого кода.
>
> Оператор — минимальная исполняемая инструкция. В таблице слева приведены все восемь операторов метода, в порядке выполнения. К ним отнесены вызовы логирования, операторы возврата, присваивание результата substring и присваивание результата тернарного оператора. Тело обработчика исключения содержит два оператора; в таблице они объединены в строке 8, поскольку при рассмотрении уровней покрытия учитываются совместно.
>
> Существенно, что не всякая конструкция является оператором. Условие в операторе if оператором не является; оно образует решение, которому соответствуют ветви. Вызов метода restClient.get() также не выделяется в отдельный оператор: он входит в состав оператора присваивания и учитывается вместе с ним.
>
> Ветвь — результат вычисления решения, определяющий направление передачи управления. В таблице справа приведены пять ветвей метода. Две относятся к решению A || B, две — к конструкции try-catch, одна — к ложной ветви тернарного оператора.
>
> Отметим соответствие между решениями и ветвями. Каждому решению соответствуют две ветви. Составное решение A || B содержит два условия, но представляет собой одно решение и даёт две ветви. Истинная ветвь тернарного оператора совпадает по направлению передачи управления с нормальным завершением конструкции try и отдельной ветвью не считается.
>
> На следующем слайде рассматриваются условия и пути.

### Слайд 7. Элементы покрытия: условие и путь

**Слайд:**
- Условие — атомарное логическое выражение, принимающее значение истина или ложь. ISTQB Glossary
| Обозн.  Условие в коде  Где |
| A   pan == null   операнд решения 1 |
| B   pan.length()    операнд решения 1 |
| C   response != null   тернарный оператор |
- Итого 3 атомарных условия. Выражение A || B целиком условием не является: это решение.
- Путь — последовательность узлов графа потока управления от входа до выхода. Куликов, 2.2
| #  Путь |
| 1  вход →  A||B  истина → выход |
| 2  вход →  A||B  ложь →  C  ложь → выход |
| 3  вход →  A||B  ложь →  C  истина → выход |
| 4  вход →  A||B  ложь → исключение → выход |
- Итого 4 пути. Число путей определяется числом решений, а не условий.
- Иерархия элементов: 8 операторов → 5 ветвей → 3 условия и 3 решения → 4 пути. Уровни покрытия различаются тем, какое из этих множеств требуется покрыть полностью.

**Speaker notes:**

> Два оставшихся типа элементов покрытия.
>
> Условие — атомарное логическое выражение, принимающее значение истина или ложь. Атомарным называется условие, не содержащее логических операторов. В таблице слева приведены три атомарных условия метода: A — pan равен null, B — длина pan меньше шести, C — response не равен null. Условия A и B входят в одно решение, условие C образует решение в тернарном операторе.
>
> Отметим разграничение понятий. Выражение A || B условием не является: это решение, составленное из двух условий. Именно поэтому в методе три условия, но решений, образованных условиями, два. Третье решение — конструкция try-catch — условием не описывается.
>
> Путь — последовательность узлов графа потока управления от точки входа до точки выхода. В таблице справа приведены четыре пути метода. Первый проходит через истинную ветвь решения A || B. Второй и третий проходят через ложную ветвь этого решения и различаются ветвью тернарного оператора. Четвёртый проходит через ветвь исключения.
>
> Существенно, что число путей определяется числом решений, а не числом условий. Составное решение A || B даёт две ветви и участвует в формировании всех путей как один узел графа.
>
> Итоговая иерархия элементов метода: восемь операторов, пять ветвей, три условия, четыре пути. Уровни покрытия, рассматриваемые далее, различаются тем, какое из этих множеств требуется покрыть полностью.

### Слайд 8. Набор тестов для уровней покрытия

**Слайд:**
- Все уровни рассматриваются на одном фрагменте. Ниже перечислены пять тест-кейсов, из которых собираются наборы.
| Кейс  Вход  Что происходит в методе  Зачем нужен |
| TC-01  валидный PAN, сервис отвечает, issuerId не пуст  операторы 3–7  основной успешный сценарий |
| TC-02  PAN из 3 цифр  истинная ветвь  A || B : операторы 1–2  ветвь 1; условие B истинно |
| TC-03   pan = null   истинная ветвь  A || B : операторы 1–2  условие A истинно |
| TC-04  валидный PAN,  issuerId = null   ложная ветвь тернарного оператора  ветвь 4; условие C ложно |
| TC-05  валидный PAN, сервис недоступен  ветвь исключения: оператор 8  ветвь 5; путь 4 |
- TC-03 нужен только для покрытия условий, TC-04 — только для покрытия ветвей. К покрытию операторов они ничего не добавляют: TC-03 выполняет те же операторы, что TC-02, а TC-04 — те же, что TC-01.
- Число тестов по уровням: операторы — 3 (TC-01, 02, 05); ветви — 4 (+ TC-04); условия — 4 (TC-01, 02, 03, 04); решения-условия — 5 (все).

**Speaker notes:**

> Прежде чем переходить к уровням, зафиксируем набор тест-кейсов, на который будем ссылаться.
>
> Всего используется пять тест-кейсов, TC-01 — TC-05. Они различаются входными данными и тем, какие элементы кода при этом выполняются.
>
> TC-01: корректный PAN, сервис отвечает, значение issuerId не пусто. Выполняются операторы с третьего по седьмой.
>
> TC-02: PAN из трёх цифр. Управление уходит в истинную ветвь решения A || B, выполняются операторы 1 и 2.
>
> TC-03: значение pan равно null. Управление также уходит в истинную ветвь решения A || B, выполняются те же операторы 1 и 2.
>
> TC-04: корректный PAN, но сервис отвечает пустым значением issuerId. Выполняется ложная ветвь тернарного оператора.
>
> TC-05: корректный PAN, сервис недоступен, возбуждается исключение. Выполняется обработчик, то есть оператор 8.
>
> Теперь ключевое для понимания дальнейшего материала. TC-03 и TC-04 не уникальны по выполняемым операторам: TC-03 выполняет те же операторы, что TC-02, а TC-04 — те же, что TC-01. Поэтому к покрытию операторов они ничего не добавляют, но необходимы на других уровнях: TC-03 даёт истинное значение условия A, TC-04 проходит ложную ветвь тернарного оператора.
>
> Отсюда и различия в размерах наборов по уровням. Покрытие операторов требует трёх тестов: TC-01, TC-02, TC-05. Покрытие ветвей — четырёх: добавляется TC-04 для ложной ветви тернарного оператора. Покрытие условий — также четырёх, но другого состава: TC-01, TC-02, TC-03, TC-04. Покрытие решений-условий требует всех пяти, поскольку ему нужны одновременно и все ветви, и все значения условий.
>
> На каждом следующем слайде в первой строке явно указан используемый набор тестов.

### Слайд 9. Уровень 1: покрытие операторов

**Слайд:**
- Набор уровня: 3 теста — TC-01, TC-02, TC-05. TC-03 и TC-04 не используются: они выполняют те же операторы.
- Покрытие операторов (statement coverage) — доля исполняемых операторов метода, выполненных при прогоне набора тестов.
| #  Оператор  TC-01  TC-02  TC-05 |
| 1   LOG.warn("PAN too short")   —  ✔  — |
| 2   return Optional.empty()  — guard  —  ✔  — |
| 3   bin = pan.substring(0, 6)   ✔  —  ✔ |
| 4   response = restClient…body()   ✔  —  ✔ |
| 5   issuerId = response != null ? … : null   ✔  —  — |

| 7   return Optional.ofNullable(issuerId)   ✔  —  — |
| 8  тело  catch :  LOG.warn  +  return empty   —  —  ✔ |
- Трёх тестов достаточно для 100%. Но ветвь тернарного оператора при issuerId = null (TC-04) не пройдена — покрытие операторов этого не замечает.

**Speaker notes:**

> Определение. Покрытие операторов (statement coverage) — доля исполняемых операторов, выполненных при прогоне набора тестов. Источник определения: ISTQB CTFL v4.0, раздел 4.3.1.
>
> Набор этого уровня состоит из трёх тестов: TC-01, TC-02, TC-05. TC-03 и TC-04 в набор не входят.

> TC-01: корректный PAN, сервис отвечает, issuerId не пуст. TC-02: PAN из трёх цифр, выполняется первая ветвь, метод возвращает пустой Optional. TC-05: корректный PAN, сервис недоступен, возбуждается исключение, выполняется обработчик.
>
> Обратимся к таблице. TC-01 выполняет операторы с третьего по седьмой. TC-02 выполняет первый и второй. TC-05 выполняет восьмой. Все восемь операторов выполнены, покрытие операторов равно 100%.
>
> Далее рассмотрим тест TC-04: корректный PAN, сервис отвечает, значение issuerId в ответе равно null. Этот тест не изменяет покрытие операторов, поскольку выполняет те же операторы, что и TC-01. Тернарный оператор вычисляется в истинную ветвь, а ложная ветвь не выполняется ни в одном тесте набора.
>
> Таким образом, покрытие операторов, равное 100%, не означает, что проверено поведение метода при пустом значении issuerId. Оператор внутри ветви может быть выполнен при том, что сама ветвь не пройдена. Этот случай рассматривается на следующем уровне.

### Слайд 10. Уровень 2: покрытие ветвей

**Слайд:**
- Набор уровня: 4 теста — TC-01, TC-02, TC-04, TC-05. К набору предыдущего уровня добавлен TC-04 — единственная непройденная ветвь, ложная ветвь тернарного оператора.
- Покрытие ветвей (branch coverage, decision coverage) — доля ветвей метода, выполненных при прогоне набора тестов. Ветвь — каждый возможный результат решения.
| Ветвь  Решение  Тест |
| 1   A || B  → истина (guard сработал)  TC-02, TC-03 |
| 2   A || B  → ложь (валидный PAN)  TC-01, TC-04, TC-05 |
| 3   try  → нормальное завершение  TC-01, TC-02, TC-04 |
| 4  тернарный  C  → ложь  TC-04 |
| 5   catch  → исключение  TC-05 |
- Включение: покрытие ветвей включает покрытие операторов, но не наоборот.
- Набор — 4 теста: TC-01, TC-02, TC-04, TC-05. Добавляется ровно один — TC-04, закрывающий ветвь 4.

**Speaker notes:**

> Определение. Покрытие ветвей (branch coverage), в терминологии ISTQB также покрытие решений (decision coverage), — доля ветвей, выполненных при прогоне набора тестов. Ветвь — каждый возможный результат решения. Источник: ISTQB CTFL v4.0, раздел 4.3.2.
>
> Набор этого уровня: TC-01, TC-02, TC-04, TC-05 — четыре теста. От набора предыдущего уровня он отличается добавлением TC-04.
>
> В таблице перечислены пять ветвей метода. Первые две — ветви решения A || B: истинная, при которой выполняется возврат пустого значения, и ложная, при которой управление передаётся далее. Две следующие — ветви конструкции try-catch: нормальное завершение и ветвь исключения. Пятая — ложная ветвь тернарного оператора; её истинная ветвь уже покрыта тестом TC-01 и нового требования не создаёт.
>
> Размер набора возрастает с трёх тестов до четырёх. Добавляется тест TC-04, в котором сервис отвечает пустым значением issuerId. Ложная ветвь тернарного оператора становится пройденной.
>
> Отметим свойство отношения между уровнями. Покрытие ветвей включает покрытие операторов: любой оператор принадлежит некоторой ветви, поэтому выполнение всех ветвей влечёт выполнение всех операторов. Обратное утверждение неверно, что показано на предыдущем слайде. В терминах теории покрытий это отношение называется подчинением (subsumption).
>
> Практический вывод: при выборе между измерением покрытия операторов и покрытия ветвей предпочтительно второе, поскольку оно информативнее при увеличении набора на один тест.

### Слайд 11. Уровень 3: покрытие условий

**Слайд:**
- Набор уровня: 4 теста — TC-01, TC-02, TC-03, TC-04. Состав другой, чем на уровне ветвей: вместо TC-05 взят TC-03, дающий истинное значение условия A.
- Покрытие условий (condition coverage) — доля атомарных условий, вычисленных в обоих значениях: и истина, и ложь.
| Тест  Вход  A:  pan == null   B: длина меньше 6  C:  response != null |
| TC-01  валидный PAN  ложь  ложь  истина |
| TC-02  PAN «123»  ложь   истина   не вычисляется |
| TC-03   pan = null    истина   не вычисляется  не вычисляется |
| TC-04  валидный PAN  ложь  ложь   ложь |
- Короткое замыкание: в TC-03 пан равен null, поэтому правый операнд A || B не вычисляется вовсе — условие A засчитывается как истинное.
- Непройденная ветвь: все три условия в обоих значениях, но ветвь «исключение» из try осталась непройденной. 100% условий не гарантируют 100% ветвей.

**Speaker notes:**

> Определение. Покрытие условий (condition coverage) — доля атомарных условий, вычисленных в обоих значениях: истина и ложь. Источник: ISTQB CTFL v4.0, раздел 4.3.3; определение атомарного условия — ISTQB Glossary.
>
> Набор этого уровня: TC-01, TC-02, TC-03, TC-04 — четыре теста, но иного состава, чем на уровне ветвей. Вместо TC-05 в набор включён TC-03, поскольку именно он даёт истинное значение условия A.
>
> В методе три условия: A — pan равен null; B — длина pan меньше шести; C — ответ сервиса не равен null.
>
> По таблице: TC-01 даёт ложь по A, ложь по B и истину по C. TC-02 даёт истину по B. TC-03 даёт истину по A. TC-04 даёт ложь по C. Все три условия вычислены в обоих значениях.
>
> Рассмотрим две особенности, существенные при работе с реальным кодом.
>
> Первая связана с коротким замыканием. Оператор || не вычисляет правый операнд, если левый истинен. В TC-03 значение pan равно null, поэтому решение A || B вычисляется по левому операнду, а условие B не вычисляется вовсе. Это учитывается при чтении отчётов покрытия условий, поскольку невычисленное условие не считается покрытым.
>
> Вторая связана с достижимостью комбинаций. Сочетание, при котором истинны и условие B, и условие C, в данной реализации недостижимо, поскольку к запросу к внешнему сервису допускается только корректный PAN. Покрытие условий такой случай не выявляет: оно рассматривает условия по отдельности, а не их сочетания.
>
> Из таблицы следует ещё одно положение. Четыре теста обеспечивают полное покрытие условий, однако ветвь исключения остаётся непройденной. Следовательно, полное покрытие условий не влечёт полного покрытия ветвей, и уровни не находятся в отношении подчинения. Именно по этой причине в ISTQB введён уровень, объединяющий оба требования.

### Слайд 12. Уровень 4: покрытие решений-условий

**Слайд:**

- **Требование 1: решения** — Пять ветвей метода: guard true и false, try — завершение, catch — исключение, тернарный — false.
- **Требование 2: условия** — Три атомарных условия A, B, C — каждое вычислено и в истине, и в лжи.
- **Что даёт вместе** — Устраняет пробел предыдущего уровня: ветвь «исключение», непокрытая при 100% условий, теперь обязательна.
- **Набор уровня: 5 тестов** — TC-01 … TC-05 — все кейсы. К набору уровня условий (TC-01, 02, 03, 04) добавлен TC-05 для ветви исключения.


**Speaker notes:**

> Определение. Покрытие решений-условий (decision-condition coverage) — уровень, требующий одновременного выполнения двух условий: полного покрытия решений и полного покрытия условий. Источник: ISTQB CTFL v4.0, раздел 4.3.4.
>
> Первое требование: все пять ветвей метода должны быть пройдены. Второе требование: все три атомарных условия должны быть вычислены в обоих значениях. Уровень достигается только при одновременном выполнении обоих требований.
>
> На предыдущем уровне было достигнуто полное покрытие условий при непройденной ветви исключения. Теперь эта ветвь обязательна, поэтому набор дополняется тестом TC-05, в котором сервис недоступен и выполняется обработчик. Итоговый набор содержит пять тестов.
>
> Зависимость размера набора от уровня приведена ниже.
>
> Операторы — 3 теста; ветви — 4; условия — 4; решения-условия — 5.
>
> Далее рассматривается наиболее строгий уровень, применяемый на практике, — MC/DC.

### Слайд 13. Уровень 5: MC/DC

**Слайд:**
- Набор уровня: 3 теста на одно решение A || B — TC-01 (базовый), TC-03 (доказывает влияние A), TC-02 (доказывает влияние B). TC-04 и TC-05 к этому решению отношения не имеют.
- MC/DC — каждое атомарное условие должно независимо влиять на результат решения. Покажем на реальном решении A || B нашего метода.
| Влияние  Тест  A  B  A || B  Вывод |
| —  TC-01 (базовый)  ложь  ложь  ложь  базовый случай |
| A   TC-03   истина   не вычисляется   истина   A влияет |
| B   TC-02  ложь   истина    истина   B влияет |
- Три теста вместо четырёх: модифицированное покрытие не перебирает все комбинации, а доказывает влияние каждого условия.
- Короткое замыкание допустимо: в TC-03 правый операнд не вычисляется — для MC/DC этого достаточно.

**Speaker notes:**

> Определение. MC/DC (modified condition/decision coverage) — уровень, при котором каждое атомарное условие в решении продемонстрировало независимое влияние на результат решения. Источник: ISTQB Glossary, статья modified condition/decision coverage.
>
> Под независимым влиянием понимается следующее: при фиксированных значениях остальных условий изменение данного условия изменяет результат решения.
>
> Рассмотрим решение A || B из метода getIssuerId.
>
> Базовый случай — TC-01: оба операнда ложны, решение ложно.
>
> Первый тест, демонстрирующий влияние A, — TC-03: значение pan равно null, левый операнд принимает значение «истина», решение становится истинным. Правый операнд при этом не вычисляется вследствие короткого замыкания. Это не препятствует применению MC/DC: условие, не участвующее в вычислении, не влияет на результат.
>
> Второй тест, демонстрирующий влияние B, — TC-02: pan не равен null, но короче шести; левый операнд ложен, правый истинен, решение истинно. Результат отличается от базового, следовательно, B влияет на решение.
>
> Итог: для двух условий достаточно трёх тестов. Полный перебор требует четырёх комбинаций; сокращение достигается за счёт того, что проверяется только независимое влияние каждого условия. В этом состоит значение термина «модифицированное».
>
> Область применения: системы, для которых цена дефекта высока. К таким системам относятся, в частности, бортовое программное обеспечение, медицинское оборудование и системы железнодорожной автоматики. В прикладной разработке уровень применяется редко ввиду стоимости набора тестов.

### Слайд 14. Уровень 6: покрытие путей

**Слайд:**
- Набор уровня: 4 теста — TC-01, TC-02, TC-04, TC-05, по одному на каждый путь. TC-03 не используется: он ведёт по тому же пути, что и TC-02.
- Покрытие путей (path coverage) — доля путей через граф потока управления метода, выполненных при прогоне набора тестов.
| #  Путь  Тест  Вердикт |
| 1  guard true → выход empty  TC-02, TC-03  линейно независимый |
| 2  guard false → C false → empty  TC-04  базовый |
| 3  guard false → C true → значение  TC-01  линейно независимый |
| 4  guard false → исключение → catch → empty  TC-05  линейно независимый |
- В методе нет циклов, поэтому полное покрытие путей достижимо — четыре пути. Это редкость: в коде с циклами число путей бесконечно.

**Speaker notes:**

> Определение. Покрытие путей (path coverage) — доля путей через граф потока управления, выполненных при прогоне набора тестов. Путь — последовательность узлов графа потока управления от точки входа до точки выхода. Источник: ISTQB CTFL v4.0, раздел 4.3.6; понятие графа потока управления — Куликов, раздел 2.2.
>
> В методе четыре пути. Первый: решение A || B истинно, возвращается пустое значение. Второй: решение ложно, условие C ложно, возвращается пустое значение. Третий: решение ложно, условие C истинно, возвращается значение issuerId. Четвёртый: решение ложно, запрос завершается исключением, выполняется обработчик, возвращается пустое значение.
>
> В первой строке таблицы одному пути соответствуют два теста, TC-02 и TC-03. С точки зрения графа потока управления оба теста приводят к одной и той же выходной вершине; различие между ними относится к уровню условий, а не путей. Путь включён в набор как линейно независимый при построении базового множества путей.
>
> Теперь о достижимости. В методе нет циклов, поэтому полное покрытие путей достижимо и составляет четыре пути. В общем случае это не так. При наличии циклов число путей не ограничено, поскольку повторение цикла образует новый путь. Кроме того, каждое дополнительное бинарное решение удваивает число путей, то есть рост числа путей экспоненциальный.
>
> По этой причине полное покрытие путей на практике не применяется. В качестве рабочей нормы используется покрытие ветвей. В качестве альтернативы применяется покрытие базовых путей: выбираются линейно независимые пути через граф, а не все пути.
>
> Итог по уровням приведён на следующем слайде.

### Слайд 15. Сравнение уровней покрытия

**Слайд:**

**Колонки:** Уровень | Тест-кейсы набора | Тестов | Включение | 03 нужен только для покрытия условий; TC-04 — только для ветвей и путей.

**Speaker notes:**

> Таблица сводит шесть уровней и приводит размер набора тестов, полученный на одном и том же фрагменте кода.
>
> Покрытие операторов потребовало трёх тестов на восемь операторов. Покрытие ветвей — четырёх: набор дополнен одним тестом для ложной ветви тернарного оператора. Покрытие условий — также четырёх, но иного состава: набор обеспечивает значения условий, однако ветвь исключения остаётся непройденной. Покрытие решений-условий — пяти, поскольку обязательными становятся и все ветви, и все значения условий. MC/DC для решения A || B — трёх тестов вместо четырёх комбинаций. Полное покрытие путей — четырёх тестов; оно достижимо вследствие отсутствия циклов.
>
> Из таблицы следует, что выбор уровня определяет размер набора тестов. Выбор уровня представляет собой компромисс между стоимостью набора и полнотой покрытия.
>
> Колонка подчинения показывает отношение между уровнями по строгости. Покрытие ветвей подчиняет покрытие операторов. Покрытие условий относится к иному измерению и покрытие ветвей не подчиняет, вследствие чего оба требования объединены в уровне решений-условий. MC/DC подчиняет предыдущий уровень. Покрытие путей подчиняет остальные уровни, однако в общем случае недостижимо.
>
> Практический вывод: для прикладной разработки в качестве нормы принимается покрытие ветвей, поскольку оно подчиняет покрытие операторов и требует одного дополнительного теста.

### Слайд 16. Что осталось за границей покрытия

**Слайд:**
- Все уровни дают 100% на фрагменте — и при этом ни один тест не проверяет значение результата.
```java
@Test
void smoke() {
    // assertions нет — тест ничего не проверяет
    binLookupClient.getIssuerId(null);
    binLookupClient.getIssuerId("123");
    binLookupClient.getIssuerId("4276010000001111");
}
```
- Покрытие выполнено. Три вызова исполняют все восемь операторов и четыре линейных пути. Инструмент покажет 100%.
- Проверок нет. Ни одно значение не сверено с ожидаемым. При неверном issuerId прогон останется успешным.

**Speaker notes:**

> Перед рассмотрением ограничений приведём пример, иллюстрирующий различие между выполнением кода и проверкой результата.
>
> В листинге приведён тест, содержащий три вызова метода getIssuerId: с аргументом null, с коротким PAN и с корректным PAN. Утверждений (assertions) тест не содержит.
>
> При прогоне этого теста будут выполнены все восемь операторов и все четыре линейных пути. Инструмент измерения покажет 100% покрытия операторов и 100% покрытия ветвей, и эти значения соответствуют действительности. При этом ни один результат не проверяется.
>
> Если метод начнёт возвращать неверный идентификатор, либо вычислять тернарный оператор в иную ветвь, либо возбуждать исключение там, где требуется возврат пустого значения, прогон останется успешным. Успешность прогона определяется истинностью утверждений, а утверждения в тесте отсутствуют.
>
> Отсюда следует основное ограничение метода: покрытие является метрикой выполнения, а не метрикой проверки. Значение 100% означает, что код был выполнен, и не содержит сведений о том, что полученный результат проверен.

### Слайд 17. Инструменты измерения покрытия

**Слайд:**
- Как это работает
- 1. Инструмент инструментирует код: вставляет счётчики.
- 2. Прогоняется набор тестов.
- 3. Счётчики фиксируют исполненные элементы.
- 4. Отчёт агрегирует покрытие по уровням.
- Инструменты по языкам
- Java: JaCoCo, Cobertura.
- Go: встроенный go test -cover.
- Python: coverage.py.
- JavaScript / TypeScript: nyc (на основе Istanbul).
- $ mvn test jacoco:report
- $ open target/site/jacoco/index.html
- Instruction coverage: 100%
- Branch coverage: 100%   ← на нашем фрагменте

**Speaker notes:**

> Порядок измерения покрытия состоит из четырёх шагов. Первый: инструмент выполняет инструментирование кода, вставляя в байт-код или исходный код счётчики, фиксирующие факт выполнения. Второй: набор тестов прогоняется на инструментированной сборке. Третий: счётчики фиксируют выполненные элементы. Четвёртый: инструмент формирует отчёт с показателями по уровням.
>
> Инструменты различаются в зависимости от языка программирования при общем принципе работы. Для Java применяется JaCoCo, для Go измерение встроено в go test, для Python — coverage.py, для JavaScript и TypeScript — nyc, построенный на библиотеке инструментирования Istanbul.
>
> В листинге приведён фрагмент отчёта. Значения 100% по инструкциям и по ветвям относятся к рассматриваемому методу, а не к сервису в целом. Существенно, что показатель покрытия интерпретируется в разрезе: значение по одному методу не характеризует остальные.
>
> Отметим также, что полный набор для метода составил пять тестов: три обеспечивают полное покрытие операторов, четыре — полное покрытие ветвей. При анализе отчёта следует учитывать, какая именно метрика приведена и на каком объёме кода она получена.

### Слайд 18. Ограничения: покрытие не равно корректности

**Слайд:**
- Главное ограничение: покрытие измеряет, что код выполнялся, а не что результат проверялся.
- Тест без проверки: три вызова getIssuerId() без утверждений дают 100% покрытия при отсутствии проверок результата.
- Отсутствующее требование: если бы метод не обрабатывал pan = null, в коде не было бы этой ветви. Покрытие покажет 100% — нечего покрывать.
- Комбинаторика: 100% ветвей не означают всех комбинаций условий — ложная ветвь тернарного оператора потребовала отдельного TC-04.
- Данные: покрытие не говорит, были ли использованы граничные значения — PAN ровно из 5 и ровно из 6 цифр.
- Приписывать покрытию смысл, которого в нём нет, — распространённая ошибка. Это метрика полноты исполнения, а не метрика качества проверок.

**Speaker notes:**

> Рассмотрим ограничения метода. Их объединяет положение: покрытие характеризует выполнение кода, а не проверку результата.
>
> Ограничение первое: тест без утверждений. Три вызова метода без утверждений дают 100% покрытия при отсутствии проверок, как показано на предыдущем слайде. Инструмент не выявляет этот случай, поскольку фиксирует выполнение, а не проверку результата.
>
> Ограничение второе: отсутствующая ветвь. Если реализация не содержит обработки значения null, соответствующая ветвь в коде отсутствует, и покрытие может быть полным. Требование при этом остаётся невыполненным. Средствами белого ящика отсутствующая в коде логика не выявляется.
>
> Ограничение третье: сочетания условий. Полное покрытие ветвей не влечёт проверки всех сочетаний значений условий; примером служит необходимость отдельного теста TC-04 для ложной ветви тернарного оператора.
>
> Ограничение четвёртое: данные. Покрытие не содержит сведений о том, какие значения подавались на вход. Полное покрытие ветвей достижимо без граничных значений, в частности для PAN длиной пять и шесть цифр.
>
> Общий вывод: интерпретация покрытия как показателя качества проверок не обоснована. Метрика характеризует полноту выполнения кода.

### Слайд 19. Как использовать покрытие правильно

**Слайд:**
- Полезно как
- Индикатор пропущенных участков кода.
- Критерий для критичных модулей: покрытие ветвей как норма.
- Инструмент поиска мёртвого кода.
- Метрика регрессии: покрытие не должно падать.
- Бесполезно как
- Самоцель: гнаться за ста процентами на любом коде.
- Доказательство качества: покрытие не равно корректности.
- Замена тест-дизайну: без чёрного ящика набор будет неполным.
- Общая метрика по проекту без разбивки по модулям.
- Разумный ориентир: покрытие ветвей для критичных модулей, покрытие операторов как базовая проверка отсутствия мёртвого кода.

**Speaker notes:**

> Практические рекомендации по применению покрытия.
>
> Первое. Покрытие применяется как индикатор непроверенных участков. Практическая ценность отчёта состоит не в итоговом значении, а в перечне невыполненных элементов. По каждому элементу устанавливается причина: неиспользуемый код либо отсутствующий тест.
>
> Второе. Для модулей с высокой ценой дефекта покрытие ветвей устанавливается в качестве нормы. Покрытие операторов для этой цели не применяется как менее строгое.
>
> Третье. Покрытие применяется для выявления неиспользуемого кода. Код, не выполняемый ни одним тестом, может не использоваться.
>
> Четвёртое. Покрытие применяется как метрика регрессии. Снижение показателя после изменения указывает на добавление кода без тестов либо на удаление тестов.
>
> Показатель не применяется в следующих случаях: в качестве самостоятельной цели; в качестве доказательства качества, поскольку покрытие не эквивалентно корректности; в качестве замены тест-дизайна, поскольку без техник чёрного ящика набор остаётся неполным; в качестве агрегированного показателя по проекту без разбивки по модулям.
>
> Рекомендуемый ориентир: покрытие ветвей для модулей с высокой ценой дефекта, покрытие операторов как базовая проверка отсутствия неиспользуемого кода.

### Слайд 20. Резюме

**Слайд:**
- Белый ящик опирается на структуру кода; дополняет чёрный ящик, но не заменяет его.
- Покрытие кода — доля структурных элементов, исполненных при прогоне набора; измеряется инструментом.
- Уровни: операторы → ветви → условия → решения-условия → MC/DC → пути. Строгость растёт, применимость падает.
- На одном фрагменте getIssuerId(): 8 операторов — 3 теста, 5 ветвей — 4, 4 пути — 4, MC/DC для A || B — 3.
- Рабочая норма — покрытие ветвей: включает операторы и не требует недостижимых комбинаций.
- Главное: покрытие измеряет исполнение, а не корректность. Сто процентов покрытия не означают отсутствия дефектов.

**Speaker notes:**

> Итог блока. Пять положений.
>
> Первое. Техники белого ящика опираются на структуру кода и дополняют техники чёрного ящика.
>
> Второе. Покрытие кода определяется как доля выполненных элементов покрытия при прогоне набора тестов и измеряется инструментально.
>
> Третье. Уровни упорядочены от покрытия операторов до покрытия путей; с увеличением строгости требования применимость уровня снижается.
>
> Четвёртое. На одном фрагменте кода получены следующие размеры наборов тестов: для восьми операторов — три теста, для пяти ветвей — четыре, для четырёх путей — четыре, для MC/DC решения A || B — три теста вместо четырёх комбинаций. Эти значения позволяют сопоставлять стоимость уровня с размером набора.
>
> Пятое. Покрытие является метрикой выполнения, а не корректности; полное покрытие не исключает дефектов, что показано на примере теста без утверждений.
>
> В модуле 4 покрытие измеряется при написании unit-тестов. В качестве рабочей нормы принимается покрытие ветвей с учётом рассмотренных ограничений.
