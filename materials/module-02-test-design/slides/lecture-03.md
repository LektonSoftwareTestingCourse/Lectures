### Слайд 3. Утверждение: нельзя протестировать всё

**Слайд:**
- Принцип ISTQB №2: исчерпывающее тестирование невозможно.
- Пример из реальных тестов
- POST /api/v1/clients/create-individual
- Один запрос содержит множество полей
- Поля делятся на обязательные и необязательные
- У каждого поля свой формат и ограничения
- POST /api/v1/clients/create-individual
- {
- "contacts": {
- "email": "user@example.com",
- "phone": "+79161234567",
- "notification_phone": null
- },
- "individual": {
- "demographic": {
- "birth_date": "1981-11-13",
- "gender": "Male",
- "marital_status": "Single"
- }
- },
- "tax": { "tax_number": "123456789012" }
- }
- Структура запроса создания клиента
- Полный перебор полей и их значений невозможен — необходим системный отбор проверок.

**Speaker notes:**

> Рассмотрим запрос, которым в системе создаётся клиент: POST /api/v1/clients/create-individual.
>
> Этот запрос используется практически во всех сценариях работы с системой. Даже при тестировании только транзакций по карте необходимо создать карту, а для этого требуется клиент и его счета. Поэтому именно на этом примере рассматриваются все техники тест-дизайна в лекции.
>
> Даже в одной группе полей contacts содержится три поля: email, phone и notification_phone. Далее следуют группа individual с датой рождения, полом и семейным положением, а также группа tax. Вложенные объекты добавляют поля следующего уровня.
>
> Часть полей обязательна, часть необязательна. Для каждого поля заданы собственный формат и ограничения.
>
> Задача состоит в том, чтобы по одному такому запросу определить, что подлежит проверке. Полный перебор полей и их значений невозможен. Требуется системный отбор: определить, что проверяется в первую очередь и по какой причине. Для этого применяются техники тест-дизайна.

### Слайд 4. Что такое тест-дизайн

**Слайд:**
- Тест-дизайн — процесс выбора и структурирования тестовых условий и тест-кейсов на основе анализа целей тестирования (ISTQB CTFL, раздел «Test design»).
- Тестовое условие — что проверить (аспект, свойство, ситуация).
- Тестовый кейс — как проверить: конкретные входные данные, шаги и ожидаемый результат.
- Вход: требования и модель системы.
- Выход: набор условий и кейсов.
- Критерий: максимум обнаруженных дефектов при разумных затратах времени и ресурсов.
- Парадокс пестицидов (B. Beizer, «Software Testing Techniques»): многократный прогон одного и того же набора тестов по неизменённому коду снижает его способность находить новые дефекты — набор нужно периодически пересматривать и обновлять.

**Speaker notes:**

> Определение. Тест-дизайн — это процесс выбора и структурирования тестовых условий и тест-кейсов на основе анализа целей тестирования. Формулировка соответствует определению ISTQB CTFL: «the process of selecting, organizing, and structuring test conditions and test cases based on analysis of test objectives» (ISTQB Certified Tester Foundation Level, Syllabus, раздел Test design). Существенно, что тест-дизайн представляет собой систематический выбор из потенциально бесконечного пространства входных данных, что было показано на примере запроса создания клиента.
>
> Ключевое терминологическое различие — тестовое условие и тест-кейс. Тестовое условие отвечает на вопрос «что нужно проверить»: это аспект, свойство или ситуация, которую следует покрыть при помощи теста. Тестовый кейс отвечает на вопрос «как именно проверить»: это конкретные входные данные, предусловия, шаги и ожидаемый результат. Одно и то же тестовое условие порождает несколько кейсов, и путать эти уровни нельзя — иначе вы теряете и прослеживаемость, и метрики покрытия.
>
> Пример на домене курса. Тестовое условие формулируется как свойство, подлежащее покрытию: «авторизация по карте, статус которой отличен от ACTIVE, отклоняется». Конкретных значений условие не содержит и в таком виде неисполнимо. Это условие порождает три тест-кейса, поскольку невалидных статусов три: TC-AUTH-02 (карта INACTIVE → DECLINED, причина CARD_INACTIVE), TC-AUTH-03 (карта BLOCKED → DECLINED, причина CARD_BLOCKED), TC-AUTH-04 (карта EXPIRED → DECLINED, responseCode 54). В эталонном артефакте практики 2 это различие материализовано в структуре таблицы: колонка «Источник» содержит условие (например, «КЭ: status = INACTIVE»), а строка целиком является тест-кейсом.
>
> Второй пример показывает, что число кейсов не равно числу условий. Условие «срок действия карты не истёк на момент авторизации» даёт два кейса по сторонам границы: TC-AUTH-05 (expiryDate — предыдущий месяц, минимально невалидное значение → DECLINED, код 54) и TC-AUTH-06 (expiryDate — текущий MMYY, минимально валидное значение → APPROVED, код 00). Оба кейса покрывают одно условие, поэтому покрытие, посчитанное по кейсам, оказывается завышенным относительно покрытия по условиям.
>
> Практические следствия путаницы уровней. Прослеживаемость строится как «требование → условие → кейс»: если в среднее звено записать текст кейса, цепочка рвётся и обосновать полноту набора нечем. Метрика покрытия считается в условиях: одно условие, размноженное на десять кейсов, покрытие не увеличивает. Обратное также верно: условие без кейсов не исполнено, а кейс без условия не имеет обоснования и первым попадает под сокращение при ревизии набора.
>
> Определение, на которое опирается разграничение: тестовое условие — testable aspect компонента или системы, определённый как основание для тестирования (ISTQB Glossary, статья «Test condition»).
>
> У тест-дизайна определены вход и выход. Вход — требования и модель системы (спецификация, модель состояний, интерфейсы). Выход — структурированный набор тестовых условий и тест-кейсов. Критерием качества является не количество тестов, а эффективность: максимум обнаруженных дефектов при ограниченных затратах времени и ресурсов. Поэтому набор представляет собой информативное подмножество проверок.
>
> Парадокс пестицидов является следствием того же принципа, рассмотренного во времени. Термин введён Борисом Бейзером в книге «Software Testing Techniques». Формулировка парадокса: многократный прогон одного и того же набора тестов по неизменённому коду снижает его способность обнаруживать новые дефекты. Следствие: набор подлежит периодическому пересмотру и дополнению. Для получения новых типов проверок применяются различные техники тест-дизайна.

### Слайд 5. Классификация техник тест-дизайна

**Слайд:**
- Техники разделяются по тому, на что они опираются: спецификация, структура кода или опыт тестировщика.
- ⬛ Specification-based (чёрный ящик)
- Источник — спецификация и\или требования
- КЭ, ГЗ, таблицы решений, state transition, попарное тестирование.
- Пример: форма регистрации с полем — email без «@», с пробелом, длиной 200 символов.
- ⬜ Structure-based (белый ящик)
- Источник — структура кода: ветви, условия, пути. Измеряем покрытие кода
- Пример: функция с тремя ветками if — проверяем, что каждая выполнена хотя бы раз.
- 🧠 Experience-based (эвристические)
- Источник — знание и опыт тестировщика
- Error guessing, exploratory, checklist-based
- Пример: «что будет если?»
- Сегодня в фокусе — спецификационные (чёрный ящик) техники: классы эквивалентности (КЭ), граничные значения (ГЗ) и попарное тестирование.

**Speaker notes:**

> Все техники тест-дизайна разделяются по одному признаку — на что они опираются как на источник информации: спецификацию, структуру кода или опыт тестировщика. В ISTQB CTFL (Syllabus, раздел Test design techniques) это три официальные категории.
>
> 1. Specification-based techniques — техники на основе спецификации, они же техники чёрного ящика. Опора — требования и описание поведения; в код мы не смотрим. Сюда входят классы эквивалентности, граничные значения, таблицы решений, тестирование переходов состояний (state transition) и попарное тестирование. Пример: форма регистрации — проверяем email без «@», с пробелом, длиной 200 символов, то есть по требованиям к допустимому формату.
>
> 2. Structure-based techniques — техники на основе структуры, они же техники белого ящика. Опора — внутреннее устройство кода: ветви, условия, пути; измеряем соответствующее покрытие. Пример: функция с тремя ветками if — нужно, чтобы каждая выполнилась хотя бы раз. Подробно разберём в модулях 3–4.
>
> 3. Experience-based techniques — техники, основанные на опыте; в русских переводах также «эвристические». Опора — знания, интуиция и опыт тестировщика, а не формальная модель. Сюда входят угадывание ошибок (error guessing), исследовательское тестирование (exploratory testing) и тестирование по чек-листам (checklist-based). Пример: «что если отправить форму дважды подряд?» или искать дефекты там, где они уже были раньше.
>
> Про термин. В ходу встречается название «опытно-эвристическое тестирование» — это калька, а не официальный термин. Источник — стандарт ISTQB Certified Tester Foundation Level (CTFL), Syllabus; третья категория в нём называется experience-based techniques. Поэтому на слайде и в лекции используем англоязычные оригиналы с русским пояснением: specification-based / structure-based / experience-based — так студентам проще потом искать материалы в ISTQB Glossary.
>
> Сегодня нас интересует первая группа — спецификационные техники чёрного ящика: КЭ, ГЗ и попарное тестирование.

### Слайд 7. Классы эквивалентности: определение

**Слайд:**
- Класс эквивалентности (equivalence partition) — множество входных значений, которые система обрабатывает одинаково: внутри класса поведение не различается, между классами — различается.
- Достаточно одного представителя класса
- По определению все значения внутри одного КЭ обрабатываются одинаково.
- Негативное тестирование
- Позитивные и негативные классы выделяем раздельно: система должна уметь корректно реагировать на данные из негативных классов
- Пример: поле email в POST /api/v1/clients/create-individual
- ✅ Позитивный класс: формат корректен → user@example.com
- ❌ Негативные классы: без @ · с пробелом · длиной > 254

**Speaker notes:**

> Определение. Класс эквивалентности (equivalence partition) — это множество входных значений, которые система обрабатывает одинаково. В ISTQB CTFL это техника «equivalence partitioning» (раздел Test design techniques). Ключевое слово — «одинаково»: класс эквивалентности определяется поведением системы, а не внешней похожестью значений. Это гипотеза о поведении программы, и её нужно уметь защищать перед разработчиком.
>
> - тесты направлены на поиск одной и той же ошибки
> - если один из тестов обнаруживает ошибку, другие её тоже, скорее всего, обнаружат
> - если один из тестов не обнаруживает ошибку, другие её тоже, скорее всего, не обнаружат
> - тесты используют одни и те же наборы входных данных.
> - для выполнения тестов совершаются одни и те же операции
> - тесты генерируют одинаковые выходные данные или приводят приложение в одно и то же состояние
> - все тесты приводят к срабатыванию одного и того же блока обработки ошибок, либо ни один из тестов не приводит к срабатыванию блока обработки ошибок
>
> Из определения напрямую следует: если значения внутри класса обрабатываются одним и тем же кодом, то любой представитель даёт тот же результат. Значит, вместо сотен адресов достаточно одного. Если его представитель поймал дефект — его поймали бы и остальные; если не поймал — не поймают и остальные, при условии что класс выделен верно. В этом и состоит сокращение набора.
>
> Классы эквивалентности можно поделить еще и на две большие группы: позитивные и негативные. Мы выделяем позитивные и негативные классы раздельно. Систему нужно проверять не только на то, что она принимает корректные данные, но и на то, что она корректно отклоняет некорректные.
>
> Все примеры рассматриваются на том же объекте: заведение клиента, POST /api/v1/clients/create-individual. Поле email. Валидный класс — адрес, проходящий проверку формата; представитель — user@example.com. Невалидные классы: адрес без символа «@»; адрес с пробелом; адрес длиной более 254 символов. Это разные классы, поскольку система может отклонять их разными ветвями кода и разными сообщениями об ошибке. Поэтому на каждый невалидный класс формируется отдельная проверка.
>
> Ход мысли тестировщика: смотрим на требование к формату поля и задаём вопрос «какие входные данные система обработает одинаково?» — и группируем. Границы этих групп уточним следующей техникой — граничными значениями.

### Слайд 8. Классы эквивалентности: методика

**Слайд:**
- Шаги
- 1. Выделить классы эквивалентности по каждому полю.
- 2. Создать тест-кейс на каждый класс — минимум один представитель.
- Отдельно
- Негативные классы выделяем отдельно.
- Пример: обязательные поля заведения клиента
- ✅ email: формат корректен → user@example.com
- ❌ без @ · с пробелом
- ✅ phone: +7XXXXXXXXXX → +79161234567
- ❌ 10 цифр · буквы
- ✅ birth_date: прошлое, возраст ≥ 18 → 1981-11-13
- ❌ будущая дата · возраст
- ✅ gender: значение из списка → Male
- ❌ пусто · значение не из списка
- ✅ tax_number: верная длина и только цифры
- ❌ буквы · неверная длина
- Классические негативные классы: значение ниже/выше диапазона, не из списка, неверный формат, пустое значение.
- Правило: несколько невалидных значений нельзя объединять в один тест.

**Speaker notes:**

> Методика — два шага. Шаг 1: выделить классы эквивалентности по каждому полю. Шаг 2: на каждый класс создать минимум один тест-кейс с одним представителем.
>
> Критически важное различие — валидные и невалидные классы. Валидные — данные, которые система должна принять. Невалидные — те, которые она должна корректно отклонить. Оба направления проверяются; второе — это негативное тестирование.
>
> Классические невалидные классы: значение ниже диапазона, выше диапазона, не из допустимого списка, неверный формат, пустое значение.
>
> Пример — обязательные поля заведения клиента. email: валидный класс — корректный формат (user@example.com); невалидные — без «@» и с пробелом. phone: валидный — формат +7XXXXXXXXXX, одиннадцать цифр (+79161234567); невалидные — десять цифр, буквы. birth_date: валидный — дата в прошлом, возраст не меньше 18 (1981-11-13); невалидные — будущая дата, возраст меньше 18. gender: валидный — значение из списка (Male); невалидные — пусто, значение не из списка. tax_number: валидный — корректная длина и только цифры; невалидные — буквы, неверная длина. Оговорка: конкретные правила могут отличаться — если требование задаёт иную длину или формат, берём правило из требования; если требование молчит, это повод задать вопрос аналитику, а не додумывать.
>
> И главное правило: невалидные значения нельзя смешивать в одном тесте. Если отправить запрос с пустым email И неверным tax_number — система вернёт ошибку, но вы не поймёте, какая проверка сработала. Каждый невалидный класс — отдельный тест.

### Слайд 9. Классы эквивалентности: пример — создание клиента

**Слайд:**
- Требование: POST /api/v1/clients/create-individual — валидация полей запроса
- contacts.email
- ✅ Валидный: user@example.com
- ❌ Без @ · с пробелом · длина > 254
- individual.demographic.birth_date
- ✅ Валидный: 1981-11-13
- ❌ Будущая дата · неверный формат · возраст
- individual.demographic.gender
- ✅ Валидный: Male
- ❌ Пусто · значение не из списка
- contacts.phone
- ✅ Валидный: +79161234567
- ❌ 10 цифр · буквы · пусто
- Итог: N классов → N тест-кейсов — по одному представителю на класс.
- Один невалидный класс = один тест: иначе не локализуем причину.

**Speaker notes:**

> Пример из практики — заведение клиента через POST /api/v1/clients/create-individual. Мы уже видели этот запрос на слайде про «нельзя протестировать всё»: полей много, у каждого свой формат. Теперь применим к нему классы эквивалентности.
>
> Начинаем с полей, у которых правило проверяется на входе.
>
> email. Валидный класс — адрес, проходящий валидацию формата; представитель user@example.com. Невалидные классы: без «@»; с пробелом; длина больше 254 символов. Три разных невалидных класса — три отдельных теста.
>
> birth_date. Валидный класс — дата в прошлом, возраст не меньше 18; представитель 1981-11-13. Невалидные классы: будущая дата; неверный формат строки; возраст меньше 18 лет.
>
> gender. Валидный класс — значение из допустимого списка (Male). Невалидные классы: пустое значение; значение не из списка.
>
> phone. Валидный класс — одиннадцать цифр в формате +7XXXXXXXXXX, например +79161234567. Невалидные — десять цифр; буквы.
>
> Ход мысли: для каждого поля мы задаём один и тот же вопрос — «какие значения система обработает одинаково, а где начинается другое поведение?». Ответ даёт нам классы, класс даёт тест-кейс. Итого: сколько классов — столько тест-кейсов, по одному представителю на класс.
>
> И правило, которое здесь видно особенно наглядно: один невалидный класс = один тест. Если отправить сразу пустой email и неверный gender, ответ будет один — ошибка, но мы не узнаем, какая именно проверка сработала и работает ли вторая вообще.
>
> Оговорка про требования: длина 254, правило «не младше 18», формат телефона — это примеры ограничений. Если в вашем требовании указано другое значение — берём его. Если требование молчит, это не повод придумывать — это повод задать вопрос аналитику. И здесь же мостик к следующей технике: именно на границах диапазонов, например, при возрасте ровно 18, живут самые частые дефекты.

### Слайд 10. Классы эквивалентности: типы классов

**Слайд:**

- **Непрерывный диапазон** — Возраст по birth_date, например 18–120: 1 валидный + 2 невалидных (ниже и выше)
- **Дискретный набор** — gender / marital_status: 1 валидный + невалидные (не из списка, пусто)
- **Одно значение** — tax_number фиксированного формата: валидный класс — само это значение
- **Набор значений** — Если список мал — по представителю на каждое значение (например, gender)
- **Выходные значения** — Классы и по ответам API: успех 200, ошибка валидации 400, отказ 403


**Speaker notes:**

> Типы входных данных и то, какие классы по ним выделяются. Разбираем на примере — заведении клиента.
>
> Непрерывный диапазон — числовое или временное поле с границами. В нашем запросе так ведёт себя возраст, вычисляемый по birth_date: например, требование может задавать допустимый возраст 18–120. Тогда один валидный класс и два невалидных — ниже и выше диапазона. Именно у таких полей особенно нужны границы — это следующий слайд.
>
> Дискретный набор — поле со списком допустимых значений. gender (Male / Female / …) и marital_status: один валидный класс и невалидные — значение не из набора, пусто.
>
> Одно значение — поле, где валидный класс совпадает с единственным допустимым значением. В нашем примере так ведёт себя tax_number с фиксированным форматом цифр: валидный класс — строка нужной длины из цифр, всё остальное невалидно.
>
> Набор значений — если допустимый список мал, берём по представителю на каждое значение, а не одно значение на весь список. Например, проверяем каждое значение gender, если список короткий и значения обрабатываются по-разному.
>
> Выходные значения — важное расширение: классы можно выделять не только по входу, но и по ответу системы. Для запроса создания клиента это коды ответа: успех 200, ошибка валидации 400, отказ в доступе 403. Группируем ответы в классы и проверяем, что каждый достижим хотя бы одним входом.
>
> Ход мысли: тип поля подсказывает форму классов, а требование — их границы. Сначала определяем тип, потом ищем сам список допустимых значений.

### Слайд 11. Классы эквивалентности: частые ошибки

**Слайд:**
- Пересечения классов приходятся на границы классов; именно там чаще всего выявляются дефекты.

**Speaker notes:**

> Четыре типичные ошибки при выделении классов. Каждую показываем на сквозном примере — заведении клиента.
>
> Первая — «добить класс тестами». Если система обрабатывает класс одинаково, десятый тест внутри класса не даст ничего нового: для email достаточно одного валидного адреса, остальные поведут себя так же. Именно на этой аксиоме держится вся экономия техники.
>
> Вторая — смешивание невалидных полей. Нельзя отправлять пустой email И неверный tax_number в одном запросе: ошибка придёт одна, и вы не локализуете причину. Один невалидный класс — один тест.
>
> Третья — пересекающиеся классы. Пример: требование задаёт один класс «возраст до 18» и другой «возраст от 18». Значение 18 попадает сразу в два класса — это дефект требований, а не ваша ошибка. Ваша задача — заметить пересечение и поднять вопрос аналитику до начала тестирования.
>
> Четвёртая — влияние дизайна интерфейса. Если gender в форме не свободный ввод, а выпадающий список допустимых значений, целые классы невалидных данных (значение не из списка, с опечаткой) просто исчезают. Интерфейс с ограничениями сокращает пространство входов — и это нужно учитывать при выделении классов.
>
> Мостик к границам: пересечения классов всегда возникают на стыках диапазонов, то есть на границах. Там же прячутся и ошибки сравнений в коде — поэтому следующая техника, граничные значения, дополняет классы эквивалентности.

### Слайд 12. Позитивные и негативные проверки

**Слайд:**
- Правило: сначала — позитивный тест, затем — негативный.
- Порядок обоснован тем, что негативная проверка информативна только при подтверждённом основном сценарии: если корректный запрос не выполняется, ответ 400 не подтверждает наличие валидации.
- Сквозной пример: создание клиента
- Позитивный: POST /api/v1/clients/create-individual со всеми корректными полями → 200, клиент создан.
- Негативный: email без «@» или возраст 17 → 400, клиент не создан.

**Speaker notes:**

> Правило задаёт порядок выполнения проверок: сначала позитивная, затем негативная. Негативная проверка информативна только при подтверждённом основном сценарии. Если создание клиента с корректными данными не выполняется, ответ 400 на email без «@» не подтверждает работу валидации: система может отклонять любой запрос. Поэтому сначала проверяется основной сценарий, затем — реакция на некорректные данные.
>
> Это правило влияет на две вещи. Первое — порядок тест-кейсов: позитивный сценарий идёт первым, он же становится ориентиром для набора. Второе — трактовка результатов: если позитивный тест падает, негативные падения на этом фоне неинформативны, и их причина, скорее всего, общая — блокирующий дефект, а не ошибка валидации. В сквозном примере это выглядит так: сначала валидный запрос create-individual с корректными полями и ожидание 200, затем запрос с email без «@» или с возрастом 17 и ожидание 400.

### Слайд 13. Граничные значения: определение

**Слайд:**
- Граничные значения (boundary value analysis, BVA) — техника тест-дизайна, при которой тестовые данные выбираются на границах классов эквивалентности и рядом с ними, а не внутри классов.
- Большинство дефектов концентрируется на границах классов эквивалентности.
- ON — граница
- Минимальное или максимальное допустимое значение класса.
- OFF — за границей
- Значение непосредственно за границей (off-by-one) — соседний класс.
- Причина: ошибки сравнений (>= вместо >,  вместо ) и «off-by-one» при работе с диапазонами и счётчиками.
- BVA — «ошибко-ориентированное» дополнение к классам эквивалентности, а не замена.
- В примере заведения клиента граничными значениями являются возраст ровно 18 по birth_date и email длиной 254 символа.

**Speaker notes:**

> Как мы уже говорили, классы отвечают на вопрос «какие значения система обрабатывает одинаково». Но при переходе от одного КЭ к другому могут и часто возникают ошибки в обработке входных данных или в значениях возращаемого результата. В ISTQB (и в целом в мировой практике) такие тесты называют boundary value analysis (BVA) и формулируют определение так: BVA — техника тест-дизайна, при которой тестовые данные выбираются на границах классов эквивалентности и рядом с ними, а не внутри классов. При этом подчёркивают: BVA не заменяет классы эквивалентности, а дополняет их. Сначала строятся классы, затем «прощупываются» их границы.
>
> Термины точек: ON-точка — значение ровно на границе класса (минимальное или максимальное допустимое); OFF-точка — значение непосредственно за границей, в соседнем классе. Пара ON/OFF и проверяет, что оператор сравнения в коде задан верно (>= vs >, <= vs <).
>
> Почему дефекты концентрируются именно на границах? Первая причина — ошибки сравнений. Разработчик пишет условие диапазона операторами >= и <=. Замена >= на > (классический off-by-one) переводит значение, равное лимиту, из допустимого в отклонённое. Именно так возникают дефекты вида «ровно 18 лет система не пропускает».
>
> Вторая причина — неточные требования. Формулировка «до 18» и «от 18» оставляет вопрос: куда отнести 18? Одно и то же значение попадает в два класса или не попадает ни в один. Это дефект требования, и тестировщик и хорошо, когда он замечен до начала написания кода.
>
> В нашем примере — заведении клиента через POST /api/v1/clients/create-individual — таких граничных значений сразу несколько. Возраст, вычисляемый по birth_date: например, требование может задавать «не младше 18». Расчёт возраста — это арифметика с датами, и ошибка в ней проявляется ровно в день восемнадцатилетия. Второй пример — email с ограничением длины: например, максимум 254 символа. Валидация длины — это сравнение с константой, а значит, её дефект тоже может находиться на значении 254, а не в середине диапазона.
>
> На практике эти техники применяют в паре, и дальше мы разберём, как именно строится набор граничных значений.

### Слайд 14. Граничные значения: методика

**Слайд:**
- Единица измерения задаёт шаг
- int: 16 → {15, 16, 17}
- деньги: 5.00 → {4.99, 5.00, 5.01}
- строка: max 255 → {254, 255, 256} символов
- Отсутствие дублирования
- Если точка выше/ниже границы уже попадает в соседний класс — не дублировать.
- birth_date · возраст ≥ 18
- {17, 18, 19} — ON: 18; OFF: 17; контрольная точка валидной зоны: 19
- phone · +7XXXXXXXXXX
- {10, 11, 12} цифр — ON: 11, OFF: 10 и 12
- Для строгих границ иногда хватает двух точек (внутри/снаружи), но тройка надёжнее.

**Speaker notes:**

> Методика BVA по ISTQB состоит из трёх шагов. Сначала выделяем классы эквивалентности, затем находим границы каждого класса. И для каждой границы берём точки: саму границу и значения по обе стороны от неё.
>
> Здесь введем понятие понятие ON/OFF points. ON-точка — это значение ровно на границе, то есть крайнее допустимое. OFF-точка — значение сразу за границей, уже вне класса. Когда точек три (значение ниже, на границе и выше), говорят о 3-х значном BVA; когда две (внутри и снаружи) — о 2-х значном BVA. В ISTQB упоминается оба варианта, при это следует учитывать тройка надёжнее, потому что она не опирается на предположение о том, где именно проходит строгая граница.
>
> Что значит «чуть ниже/выше» — задаёт единица измерения. Для целого числа шаг 1: 15, 16, 17. Для денег дискретность — копейка: 4.99, 5.00, 5.01. Для строки ограничение задано в символах: 254, 255, 256.
>
> Разбираем на сквозном примере. Возраст клиента по birth_date: например, требование может задавать «не младше 18». Строим тройку {17, 18, 19}. ON-точка — 18: клиент на границе, валидно, заявка должна пройти. OFF-точки — 17 (ещё нет 18, должно быть отклонено) и 19 (совершенно точно проходит). Две OFF-точки здесь не лишние: одна проверяет невалидную зону, вторая — что валидная зона действительно открыта, а не «сломана» сразу за границей. При это в данном случае 17 - это значение из невалидного класса экививалетности, а 19 - из валидного, но они оба должны быть включены в тестовый набор. Это иллюстрация еще одного правила методики ГЗ - отказа от дублирования выбираемых значений. Если граница общая для двух соседних классов, то точки по разные стороны автоматически попадают в разные классы, и повторять один и тот же тест не нужно. Дубль не добавляет информации, только время прогона.
>
> Второй пример — phone в формате +7XXXXXXXXXX, то есть одиннадцать цифр. По длине образуется тройка {10, 11, 12}. ON — 11 цифр, OFF — 10 (короче) и 12 (длиннее). Ограничение накладывается не на значение телефона, а на длину его строкового представления.
>
> И оговорка про строгость границы: если требование однозначно говорит «строго больше», двух точек достаточно. Но формулировки чаще всего неоднозначны, поэтому в сомнительных местах тройка предпочтительнее.

### Слайд 15. Граничные значения: пример

**Слайд:**
- Тройки точек для сквозного примера клиента:
- birth_date · возраст ≥ 18:
- {17, 18, 19}
- email · max 254 символа:
- {253, 254, 255}
- phone · +7XXXXXXXXXX:
- {10, 11, 12} цифр
- display_name · max 255:
- {254, 255, 256}
- Тот же принцип в нейтральных примерах: rate limit 100 req/s → {99, 100, 101}; VARCHAR(255) → {254, 255, 256} символов.

**Speaker notes:**

> Показываем тройки на нашем примере — запросе создания клиента POST /api/v1/clients/create-individual.
>
> birth_date, возраст не младше 18: тройка {17, 18, 19}. 17 — OFF (заявка должна быть отклонена), 18 — ON (ровно на границе, должна пройти), 19 — контрольная точка со стороны валидной зоны (проверяем, что за границей система не сломалась). Здесь есть и дополнительная граница, которую можно и нужно рассматривать отдельно: дата рождения не может быть в будущем. Это верхняя граница для самой даты, и её логично также проверить тройкой вокруг текущей даты.
>
> email, максимум 254 символа: {253, 254, 255}. Формат тоже задаётся требованием: например, требование может задавать 254. 254 — ON, 255 — OFF. Отдельно проверяем наличие символа «@» — это уже не длина, а структурное требование к формату.
>
> phone, формат +7XXXXXXXXXX из одиннадцати цифр: {10, 11, 12}. 11 — ON, 10 и 12 — OFF. Здесь мы граничим длину строки, а не её содержимое.
>
> display_name, необязательное поле с максимумом 255 символов: {254, 255, 256}. 255 — ON, 256 — OFF. И поскольку поле необязательное, к этой тройке добавляется ещё структурная граница «пусто / заполнено», о которой — на следующем слайде.
>
> Так же строятся тройки и для остальных полей. tax_number фиксированного формата (например, двенадцать цифр) даст по длине {11, 12, 13}. social_security_number — аналогично, границы вокруг его фиксированной длины. contacts.notification_phone — необязательное поле, для него сначала проверяем структурную границу «пусто / заполнено».
>
> Нейтральные примеры оставляем как ориентир: rate limit 100 запросов в секунду → {99, 100, 101}, и длина строки в базе VARCHAR(255) → {254, 255, 256}. Принцип тот же, меняются только предметная область и единица измерения.

### Слайд 16. Граничные значения: структура и значение

**Слайд:**
- BVA применяется и к значению, и к структуре данных.
- Границы по значению — возраст клиента ≥ 18: {17, 18, 19}.
- Границы по длине (это структура) — phone +7XXXXXXXXXX: {10, 11, 12} цифр.
- Структурные границы запроса: пустой individual (нет обязательных полей), пустой contacts[], null в необязательном поле, число элементов массива.
- Для невалидных классов границы используем тогда, когда ожидаем разное поведение при обработке ошибки.

**Speaker notes:**

> BVA работает с двумя разными вещами: со значением полей и со структурой данных в конкретном поле. Это различие легко упустить, а оно определяет, что именно вы положите в тестовые сценарии.
>
> Границы по значению. Возраст клиента, вычисляемый по birth_date, — «не младше 18». Тройка {17, 18, 19} проверяет именно значение: 18 — ON, 17 и 19 — OFF.
>
> Границы по структуре. Телефон в формате +7XXXXXXXXXX — это требование к длине строки, то есть к структуре: {10, 11, 12} цифр. Мы проверяем количество цифр, а не сами цифры.
>
> Дальше — границы структуры самого запроса, а не отдельного поля. Пустой объект individual, когда обязательные поля вообще не переданы, — это граница между «данные есть» и «данных нет». Пустой массив contacts[] — граница между «нет контактов» и «есть хотя бы один». null в необязательном поле — отдельная ветка кода: разработчики часто путают «поле отсутствует» и «поле присутствует со значением null». И наконец, число элементов массива — если, например, требование может задавать лимит на количество контактов, границы берём по количеству элементов.
>
> Пустое значение относится к границам, поскольку система, как правило, обрабатывает состояние «пусто / отсутствует» отдельной ветвью кода. Ветвь соответствует отдельному поведению, поэтому её край подлежит проверке. При этом делается предположение о том, как система обработает пустое значение: наличие такой обработки в коде не проверяется, но техника предполагает включение соответствующей проверки в набор. Далее возможны два варианта:
> - обработка отсутствует → вероятно получение неинформативной ошибки → основание для заведения дефекта → ветвь обработки появляется;
> - обработка заложена - протестируем ветку кода, которая ее осуществляет;
>
> Замечание о невалидных классах. Границы внутри невалидной зоны информативны, если предполагается различная обработка ошибок. Если система отвечает на любое невалидное значение одним и тем же сообщением, дробление невалидной зоны на границы не даёт результата: ответ будет одинаковым. Покрытие при этом не увеличивается, а затраты на тестирование возрастают. Техники тест-дизайна направлены на отбор необходимого и достаточного множества проверок.

### Слайд 17. Классы эквивалентности + Граничные значения — базовая пара

**Слайд:**
- Классы эквивалентности
- Задают группы значений с одинаковой обработкой.
- Граничные значения
- Уточняют, что происходит ровно на границе классов эквивалентности.
- Применяются всегда, для любого объекта тестирования.
- Итоговый набор: представитель класса + границы каждого класса.
- Пример (клиент): email — представитель user@example.com + границы {253, 254, 255}; возраст — представитель 30 + границы {17, 18, 19}.
- Обязательно комбинировать с другими техниками тест-дизайна

**Speaker notes:**

> Классы эквивалентности и граничные значения образуют базовую пару техник. Классы задают наборы значений, которые система обрабатывает одинаково; границы уточняют поведение на стыке этих наборов.
>
> Обе техники применяются для любого объекта тестирования и лежат в основе проектирования тестов. Тестовые данные и выходные значения любого теста относятся либо к классу эквивалентности, либо к границе.
>
> Практическое правило: на каждый класс — один представитель, к каждому классу — его границы. На примере клиента: для email представитель валидного класса user@example.com, границы по длине {253, 254, 255}; для возраста по birth_date представитель внутри диапазона (30 лет), границы {17, 18, 19}. В итоговом наборе отсутствуют тесты с дополнительными валидными email: представитель покрывает весь класс, а границы обеспечивают точность на переходах.
>
> Почему именно такая пара? Классы без границ экономичны, но пропускают off-by-one дефекты на краях. Границы без классов просто дают набор точек — непонятно, почему мы взяли именно эти значения и не пропустили ли целую территорию. Вместе они дают и полноту, и точность.
>
> Для того, чтобы тесты были полными и исчерпывающими, необходимо совмещать данные техники с другими техниками тест-дизайна.

### Слайд 18. Попарное тестирование: определение

**Слайд:**
- Попарное тестирование (pairwise testing, all-pairs) — техника тест-дизайна, при которой набор тестов строится так, чтобы каждая пара значений любых двух параметров встретилась хотя бы в одном тест-кейсе.
- Цель — покрыть все попарные комбинации (покрытие всех пар, 2-wise coverage) при кратном сокращении числа тестов. Основание — эмпирическое наблюдение: большинство дефектов вызывается взаимодействием не более двух факторов.
- Итог для модели из семи параметров: полный перебор — 1296 комбинаций, попарный набор — около 16 строк, сокращение примерно в 81 раз.
- Ограничение: покрытие всех пар не гарантирует полноту — взаимодействие трёх и более параметров остаётся непроверенным.
- Подробный расчёт — на слайде «Попарное тестирование: расчёт на примере».

**Speaker notes:**

> Попарное тестирование — третья базовая техника чёрного ящика. Определение: набор тестов строится так, чтобы каждая пара значений любых двух параметров встретилась хотя бы в одном тест-кейсе. Англоязычные синонимы — pairwise testing и all-pairs testing; в отрасли встречается также название «тестирование всех пар».
>
> Цель техники формулируется строго: обеспечить покрытие всех пар (попарное покрытие, 2-wise coverage) при кратном сокращении числа тестов. Основание — эмпирическое наблюдение: в большинстве проанализированных наборов дефектов дефект воспроизводится взаимодействием не более двух факторов. Это наблюдательная закономерность, а не доказанный закон; она не гарантирует, что редкая тройка не останется непроверенной.
>
> Зачем это вообще нужно. Число полных комбинаций растёт как произведение количеств значений параметров, то есть экспоненциально по числу параметров. Три числа на слайде — анонс расчёта: для модели клиента из семи параметров полный перебор даёт 1296 комбинаций, попарных пар значений — 170, а итоговый набор сжимается примерно в 81 раз.
>
> Ограничение. Покрытие всех пар не гарантирует полноту: взаимодействия трёх и более параметров могут остаться непроверенными. Технику применяют риск-ориентированно и по необходимости дополняют вручную критичными комбинациями.
>
> Как именно получаются эти числа — разберём расчёт на примере модели клиента далее в разделе.

### Слайд 19. Попарное тестирование: эмпирические основания

**Слайд:**
- Это эмпирические данные, а не доказанный закон. Покрытие всех пар (2-wise) не гарантирует полноты: критичные взаимодействия трёх и более факторов остаются непроверенными, а важность комбинаций неравномерна.
- Источники: P. Brownlie (AT&T Bell Laboratories, 1992); D. R. Kuhn, D. R. Wallace, NISTIR 6732, 2001; D. R. Kuhn, M. J. Reilly, NASA/IEEE, 2002.

- **AT&T Bell Labs, 1992** — P. Brownlie. Попарный набор (≈1000 кейсов) обнаружил больше дефектов, чем исходный план регрессии из ≈1500 тестов, при существенно меньших затратах. Точная величина выигрыша зависит от проекта.
- **NIST, Kuhn & Wallace, 2001** — Анализ отзывов медицинских устройств за 15 лет: подавляющее большинство отказов (обычно цитируется ≈97–98%) воспроизводится взаимодействием не более двух факторов.
- **Kuhn & Reilly, 2002** — Анализ баг-трекера Mozilla: набор с полным попарным покрытием (2-wise) выявил бы порядка 70–76% зарегистрированных дефектов.


**Speaker notes:**

> Откуда взялась вера в «пары»? Это наблюдательные эмпирические работы, а не математические теоремы. Три классических исследования задают порядок величин.
>
> 1. AT&T Bell Labs, 1992. P. Brownlie применил практическое комбинаторное (попарное) тестирование и сравнил сгенерированный набор примерно из тысячи кейсов с исходным планом регрессии примерно из 1500 тестов. Попарный набор обнаружил больше дефектов при существенно меньших затратах. Точную цифру — «на 28% больше дефектов при вдвое меньших ресурсах» — надёжно подтвердить по открытым данным не удалось; её стоит либо убрать, либо приводить со ссылкой на первоисточник и пометкой «по данным автора». Характер результата (рост обнаруженных дефектов при сокращении ресурсов) устойчиво цитируется в литературе по комбинаторному тестированию.
>
> 2. NIST, 2001. D. R. Kuhn, D. R. Wallace, «Failure Modes in Medical Device Software: An Analysis of 15 Years of Recall Data» (NISTIR 6732; журнальная версия — Journal of Research of the NIST, 2001). По анализу отзывов медицинских устройств за 15 лет подавляющее большинство отказов воспроизводится взаимодействием не более двух факторов; в литературе обычно цитируется порядка 97–98%. Точное значение зависит от того, как трактовать «единственный фактор» и «пару», поэтому рекомендуемая формулировка — «подавляющее большинство (порядка 97–98%)».
>
> 3. NASA/IEEE, 2002. D. R. Kuhn, M. J. Reilly, «An Investigation of the Applicability of Design of Experiments to Software Testing». Анализ баг-трекера Mozilla: набор с полным попарным покрытием (2-wise coverage) выявил бы порядка 70–76% зарегистрированных дефектов. Разброс связан с методикой классификации дефектов; корректно говорить «порядка 70–76%», а не приводить одно число как точное.
>
> Почему это работает — эмпирически. В проанализированных наборах дефектов вероятность отказа, зависящего от взаимодействия именно двух параметров, заметно выше, чем от трёх и более. Отсюда и экономия: полный перебор растёт экспоненциально, а набор со строгим попарным покрытием — то есть такой, где каждая пара значений любых двух параметров встречается хотя бы в одной строке, — растёт существенно медленнее.
>
> Когда НЕ работает. Во-первых, взаимодействия трёх и более факторов (тройки, четвёрки) остаются непроверенными, и если дефект определяется именно тройкой — например, age_group <18 + marital_status Married + заданный external_id — 2-wise его не поймает. Во-вторых, важность комбинаций неравномерна: не все пары равнозначны, и «плоскую» гарантию покрытия надо дополнять знанием о критичных сочетаниях. Поэтому pairwise — инструмент сокращения и упорядочивания набора, а не доказательство полноты. Не обещайте «70–85% дефектов» как SLA.
>
> Проверка источников: NIST (Kuhn & Wallace, 2001) и Mozilla (Kuhn & Reilly, 2002) — широко цитируемые и хорошо согласованные в литературе работы, их названия и годы приведены корректно; цифры 97–98% и 70–76% даю как «порядка», требуют финальной сверки по первоисточнику. AT&T (Brownlie, 1992) подтверждена как классическая ссылка, но точные проценты (28% / 50%) — под вопросом и в карточке смягчены.

### Слайд 20. Попарное тестирование: методика

**Слайд:**
- Шаги построения попарного набора
- Выделить параметры и их значения из требований к объекту тестирования.
- Задать ограничения модели — несовместимые сочетания значений.
- Сгенерировать набор строк, покрывающий каждую пару значений любых двух параметров.
- Спроецировать каждую строку набора в тест-кейс: одна строка — один тест-кейс.
- Сквозной пример — модель клиента create-individual, 7 параметров
- Полный перебор — 1296 комбинаций, попарный набор — ≈ 16 строк (расчёт — на следующем слайде). Каждая строка набора соответствует одному тест-кейсу.

**Speaker notes:**

> Построение попарного набора (pairwise testing) выполняется по единой схеме, независимо от выбранного алгоритма; пять шагов на схеме отражают эту последовательность.
>
> Шаг 1. Из требований выделяются параметры объекта тестирования и их значения. Для сквозного примера это модель клиента create-individual — семь параметров: gender (3 значения), marital_status (4), age_group (3), tax_number (3), external_id (2), display_name (2), phone (3).
>
> Шаг 2. Задаются ограничения модели (constraints) — несовместимые сочетания значений, которые не должны попасть в набор. Пример: age_group under18 вместе с marital_status Married — сочетание невозможно и исключается.
>
> Шаг 3. Генерируется набор строк с покрытием всех пар: каждая пара значений любых двух параметров должна встретиться хотя бы в одной строке. Именно на этом шаге применяются ортогональные массивы либо жадные алгоритмы — о них далее в разделе.
>
> Шаг 4. Каждая строка набора проецируется в тест-кейс: строка фиксирует конкретные значения всех параметров и становится заготовкой тест-кейса.
>
> Числовой ориентир — на следующем слайде (полный перебор 3 × 4 × 3 × 3 × 2 × 2 × 3 = 1296, нижняя граница ceil(170 / 21) = 9, практический результат ≈ 16). Состав параметров и их значений берётся из требований; числа иллюстративны.

### Слайд 21. Попарное тестирование: расчёт на примере

**Слайд:**
- Модель клиента create-individual — 7 параметров
- gender — 3 · marital_status — 4 · age_group — 3
- tax_number — 3 · external_id — 2 · display_name — 2 · phone — 3
- 1296
- полный перебор3×4×3×3×2×2×3
- 170
- пар значенийна C(7,2) = 21 пару параметров
- ≈ 81×
- сокращение:1296 → ≈ 16 строк
- Расчёт шаг за шагом
- Полный перебор: 3 × 4 × 3 × 3 × 2 × 2 × 3 = 1296 комбинаций.
- Число пар параметров: C(7,2) = 21.
- Число пар значений по всем этим парам — 170.
- Нижняя граница: одна строка покрывает 21 пару, значит ceil(170 / 21) = 9 строк.
- Практический набор инструмента из-за конфликтов между парами — ≈ 16 строк.
- Выигрыш: 1296 / 16 ≈ 81× при покрытии всех пар (2-wise).

**Speaker notes:**

> Разберём расчёт последовательно на модели клиента create-individual — семь параметров.
>
> Шаг 1. Полный перебор. Число полных комбинаций — произведение количеств значений параметров: gender (3), marital_status (4), age_group (3), tax_number (3), external_id (2), display_name (2) и phone (3). Перемножаем: 3 × 4 × 3 × 3 × 2 × 2 × 3 = 1296 комбинаций. Новый параметр не складывается с уже имеющимися комбинациями, а умножает их; поэтому в реальных API с десятком-полтора параметров произведение уходит в миллионы — именно поэтому полный перебор неподъёмен.
>
> Шаг 2. Число пар значений. Для этой модели оно равно 170. Именно 170 различных сочетаний «значение параметра A + значение параметра B» обязана покрыть каждая корректная 2-wise-таблица. Как получается это число, разбирается на двух следующих слайдах: там даны общие формулы числа пар параметров и числа пар значений, а затем явный перебор по всем парам.
>
> Шаг 3. Нижняя граница строк. Одна строка набора содержит C(7,2) = 21 пару. Чтобы накрыть 170 пар, нужно минимум ceil(170 / 21) = 9 строк. Это теоретический минимум, а не достижимый на практике размер.
>
> Шаг 4. Практический размер набора. Алгоритм (PICT, AllPairs) не может разложить все пары идеально: пары конкурируют между собой за строки, возникают конфликты. Поэтому инструмент выдаёт больше нижней границы — для этой модели порядка 16 строк.
>
> Шаг 5. Выигрыш. Сравниваем полный перебор с практическим набором: 1296 полных комбинаций против ≈ 16 строк — сокращение примерно в 81 раз. При этом каждая пара значений гарантированно проверена (покрытие всех пар, 2-wise coverage).
>
> Ограничение, о котором помним: покрытие всех пар не гарантирует полноту — взаимодействия трёх и более параметров остаются непроверенными, поэтому критичные тройки добавляем вручную. Числа в модели иллюстративны: конкретный состав параметров и их значений берётся из требований.

### Слайд 22. Попарное тестирование: число пар значений

**Слайд:**
- Модель клиента create-individual: 7 параметров, количества значений 3 + 4 + 3 + 3 + 2 + 2 + 3
- 1. Число пар параметров
- C(n, 2) = n × (n − 1) / 2
- Порядок в паре не важен: (gender, phone) и (phone, gender) это одно и то же сочетание, покрыть его достаточно один раз.
- Общий вид: C(n, k) = n! / (k! × (n − k)!)
- n = 7 → 7 × 6 / 2 = 21
- 2. Число пар значений
- Σ k(i) × k(j)  по всем парам i < j
- k(i) это количество значений параметра i. Произведения складываются по всем парам параметров.
- Свёрнутая форма: ( (Σ k(i))² − Σ k(i)² ) / 2
- Σ k(i) = 20, Σ k(i)² = 60 → (400 − 60) / 2 = 170
- Различайте: 21 это число пар параметров, оно зависит только от количества параметров. 170 это число пар значений, оно зависит ещё и от количества значений у каждого параметра.

**Speaker notes:**

> Прежде чем считать 170, зафиксируем две общие формулы: по ним число выводится для любой модели, а не запоминается.
>
> Формула первая. Число пар параметров. Если параметров n, число неупорядоченных пар считается как число сочетаний из n по 2: C(n, 2) = n × (n − 1) / 2. Делим на два потому, что порядок параметров в паре не важен: пара gender и phone и пара phone и gender это одно и то же сочетание, и в наборе его достаточно покрыть один раз. Общий вид формулы числа сочетаний из n по k: C(n, k) = n! / (k! × (n − k)!); наша пара это частный случай при k = 2, когда факториалы сокращаются до n × (n − 1) / 2. Для семи параметров: 7 × 6 / 2 = 21.
>
> Формула вторая. Число пар значений. Обозначим k-и количество значений параметра i. Тогда нужная величина это сумма произведений k-и × k-джей по всем парам параметров, то есть по всем i < j. Каждое произведение отвечает на вопрос, сколько разных сочетаний значений образует данная пара параметров, а сумма складывает эти количества по всем парам. Например, пара gender и phone с тремя значениями у каждого даёт 3 × 3 = 9 сочетаний.
>
> Эту же величину удобнее считать через суммы: ((Σ k-и)² − Σ k-и²) / 2. Здесь Σ k-и это сумма количеств значений всех параметров, а Σ k-и² сумма их квадратов. Смысл конструкции такой: квадрат суммы перебирает все сочетания параметров, включая пары параметра с самим собой; эти лишние слагаемые как раз и составляют сумму квадратов. Деление на два убирает пары, попавшие в сумму дважды в обратном порядке.
>
> На нашей модели: Σ k-и = 3 + 4 + 3 + 3 + 2 + 2 + 3 = 20, Σ k-и² = 9 + 16 + 9 + 9 + 4 + 4 + 9 = 60, значит (400 − 60) / 2 = 170. Явный перебор по 21 паре параметров на следующем слайде даёт тот же результат.
>
> И проговорю разграничение, чтобы числа не смешивались. Двадцать один это число пар параметров, и оно зависит только от того, сколько у нас параметров. Сто семьдесят это число пар значений, и оно зависит ещё и от того, сколько значений у каждого параметра. Первое число одинаково для любых моделей с семью параметрами, второе меняется вместе с размерами списков значений.

### Слайд 23. Число пар значений: перебор

**Слайд:**
| Параметр |
| Знач. |
| Произведения по парам с остальными |
| Сумма |
| gender  3  3×4=12 · 3×3=9 · 3×3=9 · 3×2=6 · 3×2=6 · 3×3=9  51 |
| marital_status  4  4×3=12 · 4×3=12 · 4×2=8 · 4×2=8 · 4×3=12  52 |
| age_group  3  3×3=9 · 3×2=6 · 3×2=6 · 3×3=9  30 |
| tax_number  3  3×2=6 · 3×2=6 · 3×3=9  21 |
| external_id  2  2×2=4 · 2×3=6  10 |
| display_name  2  2×3=6  6 |
| phone  3  новых пар нет, см. строки выше  0 |
- Итог по строкам
- 51 + 52 + 30 + 21 + 10 + 6 = 170
- Проверка формулой
- (20² − 60) / 2 = 170
- Нижняя граница строк
- ceil(170 / 21) = 9
- Одна строка набора содержит C(7, 2) = 21 пару, поэтому корректная 2-wise-таблица обязана покрыть все 170 пар значений.

**Speaker notes:**

> Теперь получим те же 170 явным перебором, чтобы было видно, откуда берётся каждое слагаемое. Логика такая: идём по параметрам по порядку списка и для каждого перемножаем его количество значений с количествами всех параметров, которые идут ниже. Пары с параметрами выше уже посчитаны в предыдущих строках, поэтому здесь их не повторяем.
>
> gender, три значения, образует пары с шестью остальными: 3 × 4 = 12, 3 × 3 = 9, 3 × 3 = 9, 3 × 2 = 6, 3 × 2 = 6, 3 × 3 = 9. Сумма 51.
>
> marital_status, четыре значения, образует пары с пятью ниже: 4 × 3 = 12, 4 × 3 = 12, 4 × 2 = 8, 4 × 2 = 8, 4 × 3 = 12. Сумма 52.
>
> age_group, три значения, пары с четырьмя ниже: 3 × 3 = 9, 3 × 2 = 6, 3 × 2 = 6, 3 × 3 = 9. Сумма 30.
>
> tax_number, три значения, пары с тремя ниже: 3 × 2 = 6, 3 × 2 = 6, 3 × 3 = 9. Сумма 21.
>
> external_id, два значения, пары с двумя ниже: 2 × 2 = 4, 2 × 3 = 6. Сумма 10.
>
> display_name, два значения, одна пара ниже: 2 × 3 = 6. Сумма 6.
>
> phone стоит последним, новых пар не образует: все пары с его участием уже посчитаны в строках выше, поэтому здесь ноль. Сумма нулевая не потому, что параметр лишний, а потому, что мы не считаем одну и ту же пару дважды.
>
> Складываем итоги по строкам: 51 + 52 + 30 + 21 + 10 + 6 = 170. Контрольная проверка свёрнутой формулой даёт то же: сумма значений 20, сумма квадратов 60, тогда (400 − 60) / 2 = 170.
>
> Смысл числа. Внутри одной строки набора мы фиксируем по одному значению каждого из семи параметров, и такая строка содержит C(7, 2) = 21 пару параметров, то есть 21 пару значений. Значит, корректная 2-wise-таблица обязана покрыть все 170 сочетаний. Отсюда и нижняя граница по строкам: одна строка закрывает 21 пару, значит минимум ceil(170 / 21) = 9 строк. Это тот шаг расчёта, который на слайде с общей схемой расчёта был назван без вывода.
>
> На практике этот перебор делать руками не нужно: и число пар значений, и нижнюю границу считает инструмент. Но понимать, из чего складывается 170, полезно, потому что именно это число определяет, сколько строк обязан выдать генератор, и по нему проверяется, что набор полный.

### Слайд 24. Попарное тестирование: ортогональные массивы и жадные алгоритмы

**Слайд:**
- Ортогональные массивы
- Математическая конструкция, в которой каждая пара значений встречается одинаковое число раз. Обозначение L9(3⁵) — 9 строк для пяти параметров по три значения; известны и более крупные массивы, например L64(8²·4³). Размеры массива заданы заранее и «квантованы», поэтому модель 3/4/3/3/2/2/3 аккуратно в готовый массив не раскладывается.
- Жадные алгоритмы (AllPairs)
- Набор строится прямым покрытием пар: строки добавляются, пока не закрыты все пары значений. Строк обычно примерно на четверть меньше, чем в ортогональном массиве, и алгоритм применим к произвольной модели. Если значение в строке на покрытие не влияет, оно помечается знаком «~» — «значение несущественно».
- Оба подхода приводят к сопоставимому по размеру набору; конкретные числа для модели клиента приведены в расчёте на предыдущем слайде.

**Speaker notes:**

> Оба подхода решают одну задачу — построить набор со строгим покрытием всех пар, — но разными средствами.
>
> Ортогональные массивы — классическая конструкция из планирования эксперимента. Это таблица, в которой каждая пара значений встречается одинаковое число раз, что даёт дополнительную сбалансированность. Обозначение L9(3⁵) читается так: 9 строк, пять параметров по три значения; существуют и более крупные массивы, например L64(8²·4³). Практическое неудобство в том, что размеры массива «квантованы» — они заданы заранее, — поэтому модель с неодинаковым числом значений параметров (3/4/3/3/2/2/3) аккуратно в готовый массив не раскладывается.
>
> Жадные алгоритмы (AllPairs) идут от задачи покрытия: строки добавляются последовательно, пока каждая пара значений не встретится хотя бы раз. Число строк обычно примерно на четверть меньше, чем в ортогональном массиве, а алгоритм применим к произвольным моделям. Если значение в строке на покрытие не влияет, его помечают знаком «~», то есть «значение несущественно», и оно может быть проставлено произвольно.
>
> Числовой ориентир для модели клиента: нижняя граница — ceil(170 / 21) = 9 строк; практический набор жадного алгоритма — порядка 16 строк при полном переборе 1296 комбинаций. Оба подхода могут учитывать ограничения модели, если инструмент поддерживает их задание; конкретные инструменты — на следующем слайде.

### Слайд 26. Попарное тестирование: ограничения и область применения

**Слайд:**
- Ограничения
- Покрытие всех пар (2-wise) не покрывает взаимодействия трёх и более параметров; обобщение — покрытие всех n-наборов (n-wise), но с ростом n растёт и число строк.
- Несовместимые сочетания значений задаются ограничениями модели: например, under18 + Married исключается из набора.
- Критичные сочетания, известные команде, добавляются вручную — генератор их не выводит.
- Техника не заменяет анализ требований, а дополняет его риск-ориентированно.
- Область применения
- Параметров много, зависимости между ними неизвестны или слабо формализованы.
- Полный перебор недопустим по срокам, требуется приемлемое соотношение затрат и эффекта.
- Для модели клиента create-individual: 1296 полных комбинаций → ≈ 16 строк, покрывающих все пары.

**Speaker notes:**

> Попарное тестирование — мощный, но не универсальный инструмент.
>
> Ограничение первое: покрытие всех пар (2-wise) не покрывает взаимодействия трёх и более параметров. Если дефект определяется тройкой значений, попарный набор его не поймает. Обобщение техники — покрытие всех n-наборов (n-wise), но с ростом n число строк растёт быстро и выигрыш сокращается.
>
> Ограничение второе — несовместимые сочетания значений. В модели клиента сочетание age_group under18 и marital_status Married невозможно. Такие сочетания описывают как ограничения модели: IF [age_group] = "<18" THEN [marital_status] <> "Married". Инструмент исключает их из генерации и не тратит строки на невозможные кейсы. Состав ограничений определяется требованиями, а не инструментом.
>
> Ограничение третье: критичные сочетания, известные команде, добавляются вручную. Генератор знает только список параметров и ограничения, но не знает продукта. Если связка «несовершеннолетний + заданный tax_number + отсутствие внешнего идентификатора» критична, её проверяют явно, даже если попарный набор её не содержит.
>
> И главное: техника не заменяет анализ требований, а дополняет его риск-ориентированно. Область применения: параметров много, их взаимодействия неизвестны или слабо формализованы, полный перебор недопустим по срокам. Для модели клиента 1296 полных комбинаций сводятся к ≈ 16 строкам, каждая из которых становится тест-кейсом. Если же логика системы понятна, таблицы решений и классы эквивалентности часто дают более осмысленный набор.

### Слайд 31. Тестовая документация: иерархия

**Слайд:**
- Стратегия — основания и область

- Протоколы прогонов и отчёты о дефектах; служат основанием для корректировки плана и стратегии.
- Сквозной пример — создание клиента, POST /api/v1/clients/create-individual

**Speaker notes:**

> Назначение документации. Результаты анализа и проектирования тестов не удерживаются в памяти отдельного специалиста и требуют фиксации: они адресованы команде, руководству, разработчикам, новым сотрудникам, а в корпоративной среде — также внутреннему и внешнему аудиту. >
> Иерархия строится сверху вниз, от общего к частному, и соответствует уровням тестовой документации ISO/IEC/IEEE 29119: организационному, управленческому и динамическому. Тестовая политика (test policy) определяет общие принципы и цели тестирования на уровне организации. Тестовая стратегия (test strategy) задаёт подход и область тестирования на уровне программы или проекта, отвечая на вопрос «почему выбрано именно это». Отчёты и отчёты о дефектах фиксируют полученные результаты и замыкают цикл, корректируя план и стратегию.

>

Третье — воспроизводимость: тест-кейс может быть выполнен повторно, что служит основой регрессионного тестирования. Четвёртое — снижение затрат на ввод нового сотрудника. Терминология — по ISTQB Glossary (test policy, test strategy, test plan, test case); шаблоны документов — по ISO/IEC/IEEE 29119.

### Слайд 32. Тестовая стратегия

**Слайд:**
- Тестовая стратегия (test strategy) — долгосрочное описание подхода к тестированию на уровне организации или программы проекта. Задаёт уровни и виды тестирования, принципы приоритизации, а также область тестирования и то, что осознанно оставлено вне области тестирования.
- Уровни применения
- Тестовая политика — организационный уровень; общие цели и правила.
- Тестовая стратегия — уровень программы или проекта; подход.
- Тестовый план — конкретная работа: способ, роли, сроки.
- Назначение
- Единый критерий решений: что тестируется в первую очередь, где останавливаемся, от чего отказываемся. Приоритет определяется риском: объём следует за риском, а не за удобством.
- Подходы к организации (ISTQB): часть 1
- Аналитический — проверки выводятся из формального анализа, прежде всего анализа рисков.
- Риск-ориентированный — приоритет по вероятности и последствиям дефектов.
- Модельный — строится модель системы (состояния, данные, потоки), проверки выводятся из неё.
- Подходы к организации (ISTQB): часть 2
- Процессный — опирается на стандарты и регламентированные процессы.
- Чек-листный — использует заранее подготовленные перечни проверок.
- Эвристический — основан на опыте и суждениях тестировщика.
- На практике подходы комбинируют: для критичных сервисов — риск-ориентированный, для рутинных — чек-листный.

**Speaker notes:**

> Определение. Тестовая стратегия (test strategy) — долгосрочное описание подхода к тестированию на уровне организации или программы проекта. В отличие от плана, она не задаёт даты и ресурсы, а определяет подход и принципы: какие тестовые уровни и виды тестирования применяются и по какой причине.
>
> Разграничение уровней. В ISTQB Glossary и ISO/IEC/IEEE 29119 различаются три сущности, которые часто смешивают. Тестовая политика (test policy) — организационный уровень: общие цели, принципы и правила тестирования в компании. Тестовая стратегия (test strategy) — уровень программы или проекта: подход к тестированию и его обоснование. Тестовый план (test plan) — уровень конкретной работы: способ, роли, сроки и критерии. На практике стратегия нередко входит в тест-план отдельным разделом.
>
> Стратегия отвечает на два вопроса: почему тестирование организовано именно так и почему часть проверок осознанно исключена из области тестирования. Второй вопрос существенен: решение «не тестировать X» также является стратегическим и должно обосновываться оценкой риска, а не отсутствием времени. Наличие такого обоснования отличает стратегию от формальной отписки.
>
> Подходы к организации тестирования в ISTQB описаны как семейства. Аналитический подход опирается на формальный анализ, прежде всего анализ рисков. Риск-ориентированный расставляет приоритеты проверок по вероятности и последствиям дефектов. Модельный строит модель системы — состояния, данные, потоки — и выводит проверки из неё. Процессный опирается на стандарты и регламентированные процессы. Чек-листный использует заранее подготовленные перечни проверок. Эвристический основан на опыте и суждениях тестировщика. На практике подходы комбинируют.
>
> Обоснование приоритизации. Риск первичен, объём работ следует за риском. Это даёт единый критерий решений о том, что тестируется в первую очередь, где останавливаются и от чего отказываются. Конкретная стратегия для API создания клиента разбирается на следующем слайде.

### Слайд 34. Тестовый план

**Слайд:**
- Уровни плана
- Проектный — на весь проект.
- Релизный — на конкретный релиз.
- Итерации — на итерацию или веху.
- Разделы плана (ISO/IEC/IEEE 29119-3)
- Область тестирования и подход.
- Критерии входа и выхода; критерии приостановки и возобновления.
- Ресурсы, расписание, метрики, риски.
- Сквозная иллюстрация — пункты плана для задачи «Создание клиента»
- Область: валидация и дубли групп contacts / individual / tax
- Подход: чёрный ящик; КЭ и ГЗ; риск-ориентированный приоритет
- Критерий входа: стенд доступен, требования согласованы
- Критерий выхода: 0 дефектов критического и высокого уровней; ≥ 95 % покрытия ключевых полей
- Приостановка / возобновление: при дефекте критического уровня проверки приостанавливаются до его устранения
- Ресурсы и риски: 1 тестировщик, 1 аналитик; риск — поздние правки схемы валидации
- Стандарты: IEEE 829 отозван; актуальная линейка шаблонов тест-планов — ISO/IEC/IEEE 29119-3.

**Speaker notes:**

> Тестовый план (test plan) — документ, описывающий область тестирования, подход, ресурсы, расписание, критерии и риски. Если стратегия отвечает на вопрос «почему», то план отвечает на вопросы «как, кто и когда». Составляет его ответственный за тестирование в начале проекта; план не является статичным — он пересматривается по ходу проекта, а критерии выхода уточняются по мере накопления данных.
>
> Уровни плана. Проектный план охватывает весь проект. Релизный — конкретный релиз. План итерации — итерацию или веху. Чем ниже уровень, тем конкретнее содержание: проектный план отвечает на вопрос, как организовано тестирование проекта в целом, план итерации — что именно подлежит проверке в её рамках.
>
> Разделы плана. Область тестирования и подход. Критерии входа — условия, при которых начало работ имеет смысл, например доступность стенда и согласованность требований. Критерии выхода — условия завершения, например отсутствие открытых дефектов критического и высокого уровней при достигнутом целевом покрытии. Критерии приостановки и возобновления — основания временно остановить проверки (как правило, блокирующий дефект критического уровня) и условия их продолжения. Далее следуют ресурсы, расписание, метрики и риски. Состав разделов принимается по ISO/IEC/IEEE 29119-3 — актуальной линейке шаблонов тест-планов; стандарт IEEE 829 отозван, хотя его структура по-прежнему узнаваема в рабочих документах.
>
> Сквозная иллюстрация — план для задачи «Создание клиента». Область: валидация и контроль дублей по группам полей contacts, individual и tax. Подход: чёрный ящик, техники классов эквивалентности и граничных значений, риск-ориентированный приоритет. Критерий входа: стенд доступен, требования согласованы. Критерий выхода: отсутствие открытых дефектов критического и высокого уровней и не менее 95 % покрытия ключевых полей. Приостановка: блокирующий дефект критического уровня. Ресурсы: один тестировщик и один аналитик. Риск: поздние правки схемы валидации, требующие повторного прогона набора.
>
> Для практики 2 план представляет собой компактный шаблон на всю систему: критерии, ресурсы и расписание до проходной 25.09. Требуется структура, а не объём.

### Слайд 35. Чек-листы

**Слайд:**
- Чек-лист — упорядоченный перечень проверок, определяющий, что подлежит проверке, без конкретных входных данных, шагов и ожидаемых результатов. Разновидность высокоуровневого набора проверок.
- Свойства
- Краткость формулировок · пригодность к повторному применению · логическая полнота без дублирования. Ожидаемые результаты обычно не приводятся.
- Отличие от тест-кейса
- Чек-лист определяет, что проверяется; тест-кейс — как: данные, шаги, ожидаемый результат. Соответствует высокоуровневому тест-кейсу.
- Сквозной пример — чек-лист «Создание клиента»
- Заполненность обязательных полей групп contacts / individual / tax
- Допустимость отсутствия необязательных полей
- Соответствие форматов полей email, phone, birth_date, tax_number
- Отклонение дублей external_id
- Области применения: дымовое тестирование · критический путь · каркас исследовательского тестирования.

**Speaker notes:**

> Определение. Чек-лист — упорядоченный перечень проверок, определяющий, что подлежит проверке, но не содержащий конкретных входных данных, шагов и ожидаемых результатов. В ISTQB Glossary это самостоятельная сущность; ближайший аналог — высокоуровневый тест-кейс, однако чек-лист, как правило, менее детален и не фиксирует ожидаемые результаты.
>
> Свойства качественного чек-листа. Краткость — формулировка пункта воспринимается и выполняется быстро. Пригодность к повторному применению — один и тот же перечень применяется на новой сборке или в другом релизе. Логическая обоснованность — пункты выводятся из целей и функций объекта, а не формулируются произвольно. Полнота и неизбыточность — существенное не упущено, дублирование отсутствует. Ожидаемые результаты в чек-лист, как правило, не включаются: они детализируются в тест-кейсах; исключение составляют нетривиальные проверки и случаи, когда тестирование ведётся непосредственно по чек-листу.
>
> Области применения. Дымовое тестирование после сборки — быстрая оценка работоспособности системы. Критический путь — проверка ключевых пользовательских сценариев. Исходный каркас для исследовательского тестирования — чек-лист задаёт структуру, которую тестировщик дополняет по ходу исследования.
>
> Сквозной пример — чек-лист «Создание клиента»: заполненность обязательных полей групп contacts, individual и tax; допустимость отсутствия необязательных полей; соответствие форматов email, phone, birth_date и tax_number; отклонение дублей external_id. Четыре пункта задают направление проверок, не содержа ни одного конкретного значения; именно из них в дальнейшем выводятся тест-кейсы.

### Слайд 36. Тест-кейс: структура и виды

**Слайд:**
- Тест-кейс (test case) — совокупность входных данных, предусловий, шагов и ожидаемых результатов, разработанная для проверки конкретной цели. В отличие от чек-листа содержит конкретику и воспроизводим.
- Классические поля
- Идентификатор · предусловие · шаги · ожидаемый результат · статус.
- Дополнительно: приоритет · связанное требование · постусловие.
- Уровни и виды
- Высокоуровневый — без конкретных значений; низкоуровневый — с данными и шагами.
- Позитивные — валидные классы; негативные — невалидные.
- Правило комбинирования: несколько валидных значений допустимо объединять в один тест-кейс; несколько невалидных объединять нельзя, иначе неоднозначно, какая проверка вызвала отказ. Критерий качества: отсутствие входных данных, ожидаемого результата или цели делает тест-кейс непригодным.

**Speaker notes:**

> Определение. Тест-кейс (test case) — совокупность входных данных, условий выполнения, ожидаемых результатов и постусловий, разработанная для проверки конкретной цели. Если чек-лист определяет, что подлежит проверке, то тест-кейс — как она выполняется и каким должен быть результат. Поэтому тест-кейс детерминирован: он воспроизводится другим исполнителем с тем же результатом, что и образует основу регрессионного тестирования.
>
> Классические поля. Идентификатор — уникальный номер, на который ссылаются отчёты и дефекты. Предусловие — состояние системы до выполнения. Шаги — выполняемые действия. Ожидаемый результат — реакция, которую система обязана выдать. Статус — пройден, не пройден, заблокирован. В расширенных шаблонах добавляются приоритет, связанное требование и постусловие. Именно связь с требованием обеспечивает прослеживаемость «требование → тест-кейс».
>
> Виды и уровни. Высокоуровневый тест-кейс не содержит конкретных значений и описывает идею проверки; низкоуровневый содержит конкретные данные и шаги. По направлению проверки различают позитивные (валидные классы) и негативные (невалидные).
>
> Правило комбинирования. Несколько валидных значений допустимо объединять в один тест-кейс; несколько невалидных значений объединять нельзя, иначе неоднозначно, какая именно проверка вызвала отказ и что послужило причиной. Критерий качества формулируется строго: при отсутствии входных данных, ожидаемого результата или цели тест-кейс непригоден. Конкретный пример низкоуровневого негативного тест-кейса разбирается на следующем слайде.

### Слайд 37. Тест-кейс: пример

**Слайд:**
- Негативный тест-кейс по граничному значению — TC-CLI-014
- Объект: POST /api/v1/clients/create-individual · проверяемое условие: длина поля email
| Поле тест-кейса |
| Значение |
| Идентификатор   TC-CLI-014 |
| Связанное требование  email длиной не более 254 символов и корректного формата |
| Вид и уровень  негативный, низкоуровневый; граничное значение |
| Предусловие  стенд доступен; клиент с указанным email не создан |
| Шаги  выполнить  POST /api/v1/clients/create-individual ; email длиной 255 символов; остальные поля валидны |
| Ожидаемый результат  HTTP 400, код  VALIDATION_ERROR , клиент не создан |
| Постусловие  запись клиента отсутствует в хранилище |
| Приоритет  высокий |
- Аналогичный тест-кейс: возраст 17 лет → HTTP 400, клиент не создан. Классы эквивалентности и граничные значения из начала лекции преобразованы в конкретные поля тест-кейса.

**Speaker notes:**

> Сквозной пример. Негативный тест-кейс по граничному значению для поля email, TC-CLI-014. Идентификатор — TC-CLI-014. Связанное требование: email длиной не более 254 символов и корректного формата. Вид: негативный, низкоуровневый, проверяется граничное значение. Предусловие: стенд доступен, клиент с указанным email не создан. Шаги: выполняется POST /api/v1/clients/create-individual, в поле email передаётся строка длиной 255 символов, остальные поля валидны. Ожидаемый результат: HTTP 400 с кодом VALIDATION_ERROR, клиент не создан. Постусловие: запись клиента в хранилище отсутствует. Приоритет высокий.
>
> Аналогично формулируется кейс на возраст 17 лет: ожидается HTTP 400 и отсутствие созданного клиента. Существенно, что классы эквивалентности и граничные значения из первой части лекции здесь преобразованы в конкретные поля тест-кейса: техника задаёт, какие значения выбираются, тест-кейс фиксирует проверяемый факт и результат.
>
> Различие с чек-листом на том же примере: чек-лист указывает «форматы полей проверены», тест-кейс фиксирует «email длиной 255 символов даёт HTTP 400 с кодом VALIDATION_ERROR». Первое задаёт направление проверок, второе — проверяемый факт и ожидаемый результат.

### Слайд 44. Инструмент: PICT — модель и запуск

**Слайд:**
- Запуск
- pict /?
- pict model.txt > cases.txt
- Требования к модели
- не менее шести параметров;
- по два–четыре значения на параметр;
- ограничения модели (constraints);
- на выходе — покрытие каждой пары значений.

**Speaker notes:**

> Попарное тестирование на практике выполняется инструментом. PICT принимает на вход текстовую модель — параметры и их значения, — а на выходе выдаёт набор строк, где каждая пара значений встречается хотя бы один раз. Команда pict model.txt > cases.txt сохраняет результат в файл.
>
> Требования к модели формулируются строго: не менее шести параметров, по два–четыре значения на параметр, обязательные ограничения модели. Именно ограничения отличают корректный набор от набора с невозможными сочетаниями. Модель и результат генерации коммитятся в репозиторий и проверяются автоматически.

### Слайд 45. PICT: модель авторизации

**Слайд:**
- card_status:        ACTIVE, INACTIVE, BLOCKED, EXPIRED
- amount_vs_daily:    below, equal, above
- amount_vs_monthly:  below, equal, above
- amount_vs_balance:  below, equal, above
- expiry:             valid, current_month, expired
- terminal_type:      pos, atm, ecom
- mcc:                grocery, restaurant, electronics, travel
# Ограничения
- IF [card_status] <> "ACTIVE" THEN [amount_vs_daily] = "below"
- AND [amount_vs_monthly] = "below" AND [amount_vs_balance] = "below";
- IF [expiry] = "expired" THEN [amount_vs_balance] = "below";
- Полный перебор — 4 × 3 × 3 × 3 × 3 × 3 × 4 = 3888 комбинаций; попарный набор покрывает все пары при кратном сокращении числа строк.

**Speaker notes:**

> Пример модели для сервиса авторизации. Каждый параметр — это класс эквивалентности, выделенный по требованиям; каждая строка сгенерированного набора — заготовка отдельного тест-кейса. Ограничения исключают невозможные сочетания: при неактивной карте лимиты и баланс не проверяются, а по истёкшей карте списание невозможно.
>
> Покрытие всех пар не гарантирует полноты: критичные сочетания трёх и более параметров добавляются вручную. Полный перебор даёт 3888 комбинаций — попарный набор сокращает его, сохраняя проверку каждой пары значений.

### Слайд 46. Ядро: распределение техник

**Слайд:**

| Authorization | Классы эквивалентности, границы, pairwise | глубокий |
| Card-Management | Классы эквивалентности, границы (Luhn, expiryDate MMYY), pairwise | глубокий |
| Gateway, Switch | Классы маршрутизации, границы лимита запросов, обработка 503 | чек-лист |
| Симуляторы, Logger, Dashboard | Классы сценариев, дымовые проверки | чек-лист |


**Speaker notes:**

> Распределение техник по объектам. Для ядра применяется полный набор техник, поскольку там сосредоточены бизнес-правила и риски: классы эквивалентности, границы и попарное тестирование. Попарное тестирование строится для обоих сервисов ядра: для Authorization — по условиям запроса авторизации, для Card-Management — по условиям создания карты и выборки. Для периферийных сервисов достаточно классов и чек-листов: их поведение проще, а глубокая модель не даёт соразмерного эффекта.
>
> Такой подход соответствует принципу риск-ориентированного тестирования: объём работ следует за риском, а не распределяется равномерно по системе.

### Слайд 47. Тест-кейс: поля и правила

**Слайд:**
- _(визуальный слайд)_

**Speaker notes:**

> Формат тест-кейса сохраняется таким же, как в примере TC-CLI-014: идентификатор, связанное требование, вид, предусловие, шаги и ожидаемый результат. Добавляется поле источника — класс, граница или строка попарного набора: оно показывает, какой техникой получен кейс.

**Speaker notes:**
