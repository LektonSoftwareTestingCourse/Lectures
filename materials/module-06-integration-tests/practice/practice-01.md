> **Связь с лекциями**: [`lecture-01.md`](../slides/lecture-01.md) (границы уровня, managed/unmanaged, Testcontainers, PostgreSQL, миграции), [`lecture-02.md`](../slides/lecture-02.md) (RabbitMQ, Awaitility, изоляция данных, flaky-тесты)

## Цель практики

Написать интеграционные тесты для стыков СМП с managed-зависимостями — PostgreSQL и RabbitMQ — поднимаемыми в реальных контейнерах Testcontainers, и проверить сквозной проход транзакции через цепочку сервисов с реальными БД и брокером.

**Образовательная задача**: студент переходит от unit-тестов модуля 4, где репозитории подменялись моками, к тестированию тех же стыков «как есть». Метод `upsertLimitUsage`, который в практике 4 мокался в `AuthServiceImplSimpleTest`, здесь тестируется настоящим — с реальным SQL `ON CONFLICT` на реальном PostgreSQL. Студент учится различать managed-зависимости (поднимаем в контейнере) и unmanaged (заменяем заглушкой WireMock), управлять тестовыми данными и обеспечивать детерминизм прогонов, включая асинхронные взаимодействия через брокер.

**Ограничение задания**: E2E бизнес-сценарии с баг-репортами и вариативностью путей входят в модуль 7 и в данную практику не включаются. Сквозной проход здесь один и предметный: аппрув транзакции → проверка её следов в БД обоих сервисов и в брокере.

## Часть 1. Цели, охват, критерии сдачи

### Что создаётся

Интеграционные тесты для трёх сервисов СМП и сквозной цепочки. Тесты размещаются в стандартной структуре Maven и именуются суффиксом `*IT`, чтобы выполняться плагином maven-failsafe, а не surefire:

```
services/{service}/src/test/java/...
docs/practice-6/integration-test-report.md
```

| Сервисы: Card Management, Authorization, Transaction Logger + цепочка Switch → Authorization → Card Management → Transaction Logger |

### Критерии сдачи (приёмка)

Для сдачи артефакта должны быть выполнены **все** условия:

1. **Зелёный CI**: job `integration-tests` выполняет `mvn verify` и завершается успешно. Job запускает прогон **дважды подряд** на одном runner'е — оба прогона зелёные. Это проверка детерминизма: тесты не зависят от порядка выполнения и от остаточного состояния БД, брокера и контейнеров.
2. **Все четыре задания выполнены** (см. часть 3): `CardRepositoryIT`, `LimitUsageRepositoryIT`, сквозной тест цепочки, тест poison message → DLQ.
3. **Отчёт** `docs/practice-6/integration-test-report.md` заполнен по структуре из части 4.
4. Код тестов соответствует правилам изоляции лекций: статический `@Container` на класс, очистка данных в `@BeforeEach`, уникальные бизнес-ключи (RRN/STAN) на тест, Awaitility для асинхронных ожиданий, никаких `Thread.sleep`.

> **Баллы начисляются только при наличии всех компонентов задания**: отсутствие любого из них делает артефакт неполным.

## Часть 2. Демонстрация: первый интеграционный тест на живом Docker

Преподаватель на экране показывает тестовый класс `CardRepositoryIT` для сервиса Card Management и запускает его на живом Docker: Testcontainers скачивает образ, стартует контейнер PostgreSQL, прогоняет wait-strategy, поднимает случайный порт и подставляет URL подключения в Spring-контекст.

### Шаг 1. Структура класса

```java
@DataJpaTest
@Testcontainers
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import({
        CardRepositoryPersistenceAdapter.class,
        CardExpiryDateMapper.class,
        MapperConfig.class
})
class CardRepositoryIT {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    private CardRepository repository;

    @Autowired
    private CardJpaRepository jpaRepository;

    @PersistenceContext
    private EntityManager entityManager;
}
```

Разбор:

- `@DataJpaTest` — срез Spring-контекста: только JPA-слой, без веб-слоя и лишних бинов. Тестируем стык с БД, а не весь сервис.
- `@AutoConfigureTestDatabase(replace = NONE)` — запрет подмены DataSource на встроенную H2. Это ключ к тесту: запросы выполняются настоящим PostgreSQL, а не его имитацией.
- `@Import({CardRepositoryPersistenceAdapter, CardExpiryDateMapper, MapperConfig})` — адаптер и мапперы не являются JPA-сущностями и не попадают в срез `@DataJpaTest` автоматически; их нужно импортировать явно. `MapperConfig` — тестовая конфигурация, подключающая только MapStruct-маппер `CardPersistenceMapper` через `@ComponentScan` с фильтром, чтобы не тянуть остальные мапперы пакета, требующие лишних бинов.
- `CardJpaRepository` и `EntityManager` — низкоуровневый доступ для очистки данных: `deleteAllInBatch()` и нативный SQL. Зачем нативный SQL — см. правило изоляции № 2 в части 3.
- `@Container static PostgreSQLContainer` — контейнер объявлен статически: один контейнер на класс, а не на каждый тестовый метод. Старт контейнера — секунды; поднимать его заново на каждый тест — неоправданная цена.
- `@ServiceConnection` — Spring Boot сам конструирует JDBC-URL, логин и пароль из запущенного контейнера. Никакого `@DynamicPropertySource` и ручного проброса портов.

### Шаг 2. Тест round-trip

```java
@Test
void shouldCreateAndFindCard() {
    // Arrange
    CardModel card = newCard(uniquePan());

    // Act
    repository.save(card);
    Optional<CardModel> found = repository.findByPan(card.pan());

    // Assert
    assertThat(found).isPresent();
    assertThat(found.get().status()).isEqualTo(CardModelStatus.ACTIVE);
}
```

Разбор:

- Round-trip — базовый тест персистентности: сохранили сущность, прочитали её же, проверили, что поля пережили цикл «Java → SQL → Java». Ловит ошибки маппинга, типов колонок и нейминга.
- `uniquePan()` — уникальный идентификатор на каждый тест. Данные тестов не должны пересекаться даже случайно.

### Шаг 3. Намеренная поломка: почему не H2

Преподаватель переключает тест на H2 (убирает `replace = NONE` и добавляет `@TestPropertySource` с `spring.flyway.enabled=false`, `ddl-auto=create-drop`, `H2Dialect`) и запускает сравнение. 

Разбор механики: миграции Card Management — PostgreSQL-specific, на H2 Flyway падает (частичный индекс `CREATE UNIQUE INDEX ... WHERE status != 'DELETED'` из V5.8 H2 не поддерживает). Поэтому для H2-прогона Flyway отключают, а схему генерирует Hibernate из `@Entity` — то есть прогон на H2 выполняется **не на той схеме, что в проде**. «Зелёный» тест на H2 ≠ совместимость с продовой СУБД: два из трёх тестов это скрывают, и только диалектный тест ловит расхождение. Корректно проверять схему и поведение только на той же СУБД, что и в проде.

## Часть 3. Задания

Выполняются четыре задания. Рекомендуемый порядок: CardRepositoryIT → LimitUsageRepositoryIT → poison message → DLQ → сквозной проход.

### Общие правила для всех заданий

1. **Контейнер — один на класс**: статический `@Container`; не поднимать контейнер на каждый метод и не использовать singleton на весь набор.
2. **Очистка данных — в `@BeforeEach`**, а не в `@AfterEach`: тест должен гарантировать чистое состояние до себя, а не надеяться на предыдущий. Для БД — `TRUNCATE ... RESTART IDENTITY CASCADE`; для очередей — purge.
3. **Уникальные бизнес-ключи**: каждый тест генерирует собственные RRN/STAN/PAN (например, с вкраплением идентификатора теста) — тесты не должны конфликтовать по уникальным индексам.
4. **Правило трёх транзакций**: Arrange, Act и Assert — каждый в своей транзакции. Никакого `@Transactional` на тестовом методе — он маскирует rollback и скрывает ошибки персистентности.
5. **Асинхронные ожидания — только Awaitility**: `await().atMost(5, SECONDS).pollInterval(100, MILLISECONDS).untilAsserted(...)`. Таймаут — это диагноз, а не ручка настройки: `Thread.sleep` и повышение таймаутов «чтобы прошло» запрещены.

### Задание 1. `CardRepositoryIT` — персистентность карт (Card Management)

Написать интеграционный тест репозитория карт по образцу демонстрации из части 2. Проверки:

- **Round-trip**: сохранение и чтение карты, поля переживают цикл без искажений.
- **Уникальное ограничение**: сохранение второй активной карты с тем же PAN завершается ошибкой целостности (`PanCollisionException`). Учесть, что миграция V5.8 создаёт частичный уникальный индекс `uk_cards_pan ON cards (pan) WHERE status != 'DELETED'`: PAN карты в статусе `DELETED` можно переиспользовать — тест должен проверить обе ветки (отказ на дубликат активной карты и успех на PAN удалённой).
- **Миграции на чистой БД**: контекст поднимается на пустом контейнере, все миграции V5.1–V5.8 применяются без ошибок. Это проверяется самим фактом успешного старта теста — падение миграции не даст выполниться ни одной проверке.

В отчёте — абзац «почему H2 это не поймал бы» (коммитить класс с тестами на H2 не нужно. Нужно локально прогнать и  в отчете результат): частичный уникальный индекс V5.8 (`WHERE status != 'DELETED'`)  воспроизводится  H2 ? А round-trip? а запрет дубликата PAN ?

### Задание 2. `LimitUsageRepositoryIT` — атомарный upsert лимитов (Authorization)

Метод `LimitUsageRepository.upsertLimitUsage` выполняет нативный SQL `INSERT ... ON CONFLICT (pan, usage_date) DO UPDATE` с атомарной проверкой дневного и месячного лимитов в `WHERE`. В практике 4 этот метод мокался — теперь он тестируется настоящим, на реальном PostgreSQL. Проверки:

- **Первый upsert** создаёт запись и возвращает признак успешного обновления.
- **Повторный upsert** на ту же пару `(pan, usage_date)` не создаёт дубликат, а атомарно наращивает суммы — данные не теряются.
- **Граница лимита**: upsert, превышающий дневной лимит, отклоняется (обновления не происходит), и состояние записи остаётся прежним.

В отчёте — уточнение о схеме Authorization: она создаётся hibernate (`ddl-auto: update`), а Flyway управляет лишь sequence — проверка миграций здесь не требуется, тестируется совместимость entity и нативного запроса с реальной СУБД.

### Задание 3. Сквозной проход транзакции (цепочка сервисов)

Интеграционная часть проверяет цепочку сервисов — сквозной проход транзакции. Поднимается окружение: PostgreSQL и RabbitMQ в контейнерах, сервисы Switch, Authorization, Card Management, Transaction Logger, а также WireMock-заглушки для unmanaged-зависимостей — BIN-lookup и Merchant Acquirer (контракты стабов берутся из спецификаций соответствующих сервисов). Окружение может подниматься через Docker Compose с переопределёнными адресами зависимостей или через оркестрацию Testcontainers — способ выбирает исполнитель, проверяется воспроизводимость запуска одной командой без ручных шагов.

Сценарий теста:

1. Подготовить тестовые данные: карта с известным PAN и лимитами в БД Card Management (через репозиторий или API), WireMock-стабы настроены на успешные ответы.
2. Отправить `POST /api/internal/authorize` в Switch с уникальными RRN/STAN.
3. Проверить синхронный ответ: `APPROVED`.
4. **Проверить следы изнутри, а не только HTTP-ответ** (это отличие от практики 5, где цепочка проверялась как чёрный ящик):
   - через Awaitility — запись с тем же RRN появилась в БД Transaction Logger (асинхронный эффект через брокер);
   - в БД Authorization лимит по карте изменился на сумму транзакции (upsert отработал на реальной БД);
   - резерв в БД Card Management создан.

### Задание 4. Poison message → DLQ (Transaction Logger)

Проверить поведение брокера при недесериализуемом сообщении. Опубликовать в exchange `smp.transactions` сообщение с битым JSON с routing key `transaction.log`. Проверки:

- сообщение оказывается в dead-letter queue `transaction-log-dlq` (появляется там быстро — ошибка десериализации отбраковывает сообщение при первой доставке, без повторных попыток);
- основная очередь `transaction-log` пуста — poison message не блокирует поток;
- сервис жив и следующее валидное сообщение обрабатывается успешно.

Учесть две ловушки из устройства системы. Во-первых, у DLQ настроен TTL 60 секунд — сообщения в ней протухают: проверка содержимого DLQ должна выполняться сразу, без пауз, иначе тест станет флаки по внешней причине. Во-вторых, DLQ и DLX объявлены конфигурацией Switch, а не Transaction Logger: если в тесте поднят только Transaction Logger — топологию DLQ нужно декларировать в тестовой конфигурации самостоятельно, иначе сообщение потеряется в DLX без привязки.

## Часть 4. Отчёт и самопроверка

### Отчёт `docs/practice-6/integration-test-report.md`

Структура отчёта:

1. **Граница уровней**: какие проверки остались в unit-тестах (практика 4), какие переехали в интеграционные и почему. Пример обязателен: `upsertLimitUsage` — мок в практике 4, реальный тест здесь.  Абзац «почему H2 это не поймал бы»

3. **Стратегия изоляции**: выбранный жизненный цикл контейнеров, способ очистки данных, генерация уникальных ключей — с обоснованием.
4. **Диаграмма цепочки задания 3**: сервисы и зависимости с пометкой managed (подняты как есть) / unmanaged (заглушки WireMock).

### Лист самопроверки

- [ ] CI зелёный: job `integration-tests` проходит, прогон выполняется дважды — оба раза успешно
- [ ] Все тесты — `*IT`, выполняются failsafe на фазе `verify`
- [ ] PostgreSQL и RabbitMQ поднимаются Testcontainers, никаких H2/in-memory подмен
- [ ] Контейнеры статические, один на класс
- [ ] Очистка данных в `@BeforeEach`, уникальные RRN/STAN/PAN на тест
- [ ] Асинхронные проверки — через Awaitility; нет `Thread.sleep`
- [ ] DLQ-проверка
- [ ] Тесты зелёные при запуске всего набора целиком, не только поодиночке
- [ ] Отчёт заполнен по всем пяти пунктам структуры
