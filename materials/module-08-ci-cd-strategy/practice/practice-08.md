## Часть А. Отчётность в CI (1 балл)

Ваш пайплайн отвечает «зелёное/красное», но не «что именно происходит с тестами во времени». Добавляем два инструмента.

**Allure с историей прогонов:**

- Allure подключён к тестовым модулям (как минимум `java-services` и `e2e-tests`): результаты собираются при прогоне, отчёт генерируется в CI.
- Отчёт публикуется одним из двух способов: артефактом сборки (скачиваемый `allure-report`) или на GitHub Pages со ссылкой из репозитория.
- **История обязательна**: в отчёте виден тренд минимум по двум прогонам (график Trend на главной странице). Для этого история сохраняется между запусками (каталог `allure-history` копируется в `allure-results` перед генерацией либо используется выкладка на Pages с сохранением `history/`).

**Тренд покрытия:**

- `jacoco.xml` (или `jacoco.csv`) по каждому модулю сохраняется артефактом прогона — у вас это уже есть из модуля 4.
- В отчёте практики — таблица «прогон → branch coverage по модулям» минимум по трём запускам CI и один абзац выводов: куда движется покрытие, где дыры (вспомните жёлтые ромбики из модуля 4 и закон Гудхарта — тренд читаем вместе с качеством тестов).

Ссылки на прогон с Allure-отчётом и на опубликованный отчёт прикладываются в `strategy.md`, раздел «Метрики».

## Часть Б. Нагрузочный smoke (2 балла)

Проверяем, что СМП держит ожидаемый поток транзакций. Это **smoke**, а не stress и не capacity: вопрос прогона — «система работает под штатной нагрузкой без деградации и ошибок», а не «где её предел».

**Подготовка:**

1. Сброс состояния: `docker compose down -v`, затем поднятие полного стека с наблюдаемостью: `docker compose --profile observability up -d`.
2. Пул данных под длительность прогона: карты с запасом по балансу и лимитам (создаются через `POST /api/cards`); каждая транзакция — с уникальным `stan`. Повторный `stan` — это сценарий дубля, а не нагрузка.
3. Профиль нагрузки зафиксирован в отчёте: интенсивность (RPS через Terminal Simulator, режим `start-continuous`), длительность измерительной фазы (не менее 5 минут), warmup-фаза (1–2 минуты, в статистику не входит).

**Прогон:**

- Не менее **500 транзакций** через Gateway в измерительной фазе.
- Во время прогона наблюдаем обе стороны: клиентскую (Terminal Simulator: фактический RPS, ответы, ошибки) и серверную (Grafana/Prometheus: latency, CPU, пулы; RabbitMQ: глубина очередей).
- Фактический RPS должен соответствовать заданному: если генератор не вытягивает интенсивность — это видно по провалу throughput, и это результат о стенде, а не о системе.

**Метрики и пороги (фиксируются в `load-report.md`):**

| Метрика | Порог | Источник |
|---|---|---|
| Latency p95 | < 2 с | клиент + сервер (Grafana) |
| Error rate | < 1% | ответы Gateway (коды `00` против остальных) |
| Throughput | = заданному RPS (без провала) | клиент + Prometheus |
| Лаг асинхронного следа | записи логгера доезжают, backlog очередей не растёт монотонно | RabbitMQ / `GET /api/transactions/search` |

**Интерпретация — обязательна и оценивается отдельно от факта прогона.** Для каждой метрики: факт против порога и вывод. Если порог не пройден — разбор: где «колено», какой ресурс насытился, что видно по очередям. Скриншоты дашбордов — в `docs/practice-8/img/`.

**Что не требуется:** нагрузочный прогон в CI (shared-раннеры шумят — лекция 15, слайды 16–17), soak-тест, поиск предела capacity.

## Часть В. Финальная тестовая стратегия (2 балла)

Документ `docs/practice-8/strategy.md` — сверка намерений стратегии из практики 2 с фактами декабря. Структура — по шаблону [`artifact-8-strategy.md`](../../artifacts/artifact-8-strategy.md); ключевые разделы:

1. **Карта покрытия** — матрица «требования/сервисы × уровни (unit, API, интеграционные, E2E, нагрузка)». Ячейка заполняется только ссылками на артефакты: тесты, прогоны Actions, баг-репорты. «Помню, что проверял» не считается.
2. **Карта рисков** — не менее **пяти рисков**. У каждого: событие и последствие, вероятность, влияние, обоснование в одну фразу, привязка к тестам, которые риск закрывают (или отметка «не закрыт»).
3. **Сводка дефектов** — баг-репорты практики 7, сгруппированные по severity и звеньям (ответ / данные / асинхронный след).
4. **Метрики** — ссылки на Allure с историей, тренд покрытия (часть А), результаты нагрузочного smoke (часть Б) с выводами.
5. **Что осталось непроверенным** — каждый пробел: что + почему + какой риск остаётся. Пустой раздел читается как «автор не знает границ своего тестирования».
6. **Рекомендации** — 3–5 пунктов в формате «пробел/риск + действие + ожидаемый эффект». «Добавить больше тестов» — не рекомендация.

Этот документ — основа презентации на индивидуальной защите: карта покрытия, карта рисков, дефекты, метрики, рекомендации — это 80% ваших слайдов.

## Критерии

| Критерий | Баллы | Что должно быть |
|---|:---:|---|
| Отчётность в CI | 1 | Allure-отчёт генерируется в CI и опубликован (артефакт или Pages); видна история ≥ 2 прогонов; таблица тренда покрытия ≥ 3 запусков с выводами |
| Нагрузочный smoke | 2 | ≥ 500 транзакций, warmup вынесен из статистики, уникальные `stan`; четыре метрики (p95, error rate, throughput, лаг следа) с фактом против порога; интерпретация и разбор отклонений; скриншоты в `img/` |
| Финальная стратегия | 2 | Coverage map с артефактами в ячейках; ≥ 5 рисков с вероятностью, влиянием, обоснованием и привязкой к тестам; сводка дефектов по severity; раздел непроверенного; 3–5 конкретных рекомендаций |

Типичные потери баллов: Allure без истории; тренд покрытия из одного прогона; warmup включён в статистику; повторные `stan` в нагрузке; метрики без интерпретации («приложил скриншот»); риски без обоснования или без привязки к тестам; ячейки карты без артефактов; пустой раздел «что осталось непроверенным»; рекомендации уровня «писать больше тестов».
