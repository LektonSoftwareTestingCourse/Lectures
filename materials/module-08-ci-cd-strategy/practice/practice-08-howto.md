# Практика 8: инструкция по выполнению

> **Модуль**: 8 — Продвинутый CI/CD, отчётность, тест-менеджмент, финальная стратегия
> **Задание**: [`practice-08.md`](practice-08.md)
> **Сроки**: выдача 11.12.2026 (ранний доступ с 10.12.2026), приёмка и дедлайн 18.12.2026 — окна на доработку после приёмки нет

Пошаговая инструкция для самостоятельной работы. Каждый шаг заканчивается проверяемым результатом; не переходите дальше, пока он не получен. Ориентировочные трудозатраты: шаги 1–4 (часть А) — 3–5 часов, шаги 5–7 (часть Б) — 4–6 часов, шаг 8 (часть В) — 5–7 часов.

## Шаг 0. Подготовка

1. Подтянуть изменения эталонного репозитория в свой `Practic{Имя}{Фамилия}` (см. `docs/submission-guide.md`, раздел «Синхронизация»).

## Шаг 1. Allure локально

1. В `pom.xml` тестовых модулей (как минимум `java-services`-модули и `e2e-tests`) добавить зависимость:

```xml
<dependency>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-junit5</artifactId>
    <version>2.24.0</version>
    <scope>test</scope>
</dependency>
```

2. В корневой `pom.xml` добавить плагин генерации отчёта:

```xml
<plugin>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-maven</artifactId>
    <version>2.12.0</version>
</plugin>
```

3. Прогнать тесты одного модуля: `mvn -pl services/switch test`. Проверить, что появился каталог `target/allure-results` с json-файлами результатов.
4. Сгенерировать и открыть отчёт: `mvn allure:serve` — в браузере откроется Allure со сьютами и тестами.

Если `allure-results` пуст — зависимость не в том модуле или не в `test`-скоупе: Allure собирает результаты через JUnit-листенер, без зависимости писать некому.

**Результат шага:** локальный Allure-отчёт открывается и показывает ваши тесты.

## Шаг 2. Allure в CI

1. В workflow джобов `java-services` и `e2e-tests` добавить два шага (обязательно с `if: always()` — отчёт нужен и при падении тестов):

```yaml
- name: Generate Allure report
  if: always()
  run: mvn allure:report

- name: Upload Allure report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: allure-report-${{ matrix.service || 'e2e' }}
    path: '**/target/site/allure-maven-plugin'
    retention-days: 30
```

2. Запушить, дождаться прогона, скачать артефакт `allure-report`, открыть `index.html` — отчёт из CI совпадает с локальным.

**Результат шага:** Allure-отчёт доступен как артефакт сборки в Actions.

## Шаг 3. История прогонов

История — это каталог `history/` внутри сгенерированного отчёта. Чтобы Trend появился, перед генерацией нового отчёта в `allure-results` кладут `history/` от предыдущего прогона.

1. Добавить шаги в workflow **до** генерации отчёта:

```yaml
- name: Download previous Allure history
  if: always()
  uses: actions/download-artifact@v4
  with:
    name: allure-history
    path: allure-history
  continue-on-error: true   # первого прогона истории ещё нет

- name: Restore history into results
  if: always()
  run: |
    for d in $(find . -type d -name allure-results); do
      mkdir -p "$d/history"
      cp -r allure-history/. "$d/history/" 2>/dev/null || true
    done
```

2. **После** генерации отчёта — сохранить новую историю:

```yaml
- name: Upload Allure history
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: allure-history
    path: '**/target/site/allure-maven-plugin/history'
    retention-days: 30
```

3. Прогнать CI **дважды**. Во втором прогоне на главной странице отчёта появляется график Trend с двумя точками.

Альтернатива артефактам — GitHub Pages (`peaceiris/actions-gh-pages@v3`, выкладка отчёта и `history/` в ветку `gh-pages`; в Settings → Pages выбрать Source: GitHub Actions). Даёт постоянную ссылку, но настраивается дольше; артефактного варианта для сдачи достаточно.

**Результат шага:** во втором прогоне CI виден Trend минимум по двум запускам; ссылка на прогон сохранена для отчёта.

## Шаг 4. Тренд покрытия

1. Убедиться, что `jacoco.xml` по модулям сохраняется артефактом прогона — это настроено в модуле 4.
2. Собрать таблицу минимум по трём запускам CI (можно использовать прогоны из шагов 2–3): прогон → branch coverage по каждому модулю. Цифры — из `jacoco.xml` артефактов (`counter type="BRANCH" ... covered/missed`).
3. Написать один абзац выводов: куда движется покрытие, где дыры (жёлтые ромбики), помня закон Гудхарта — тренд читаем вместе с качеством тестов, а не как самоцель.

**Результат шага:** таблица тренда + абзац выводов готовы для раздела «Метрики» в `strategy.md`. Часть А закрыта.

## Шаг 5. Стенд для нагрузочного прогона

1. Сброс состояния: `docker compose down -v`.
2. Поднять полный стек с наблюдаемостью: `docker compose --profile observability up -d`. Дождаться health-check всех сервисов.
3. Проверить точки наблюдения:
   - Grafana: `http://localhost:3001` (**не 3000** — на 3000 живёт Web Dashboard);
   - Prometheus: `http://localhost:9090`;
   - RabbitMQ management: `http://localhost:15672` (guest/guest) — вкладка Queues.
4. Создать пул данных: ~50 карт через `POST /api/cards` (поля — по `api-spec.md`, как в ваших E2E-тестах), с запасом по балансу и лимитам: баланс и дневной лимит минимум в 10 раз выше суммарного объёма прогона на карту. Пример цикла:

```bash
for i in $(seq 1 50); do
  curl -s -X POST http://localhost:8080/api/cards \
    -H "Content-Type: application/json" \
    -d "{\"pan\": \"40000000000000$(printf '%02d' $i)\", \"balance\": 1000000, \"dailyLimit\": 5000000}"
done
```

5. Зафиксировать профиль прогона: целевой RPS (начните с 5–10), длительность измерительной фазы ≥ 5 минут, warmup 1–2 минуты.

**Результат шага:** стек с наблюдаемостью поднят, пул карт создан, профиль записан.

## Шаг 6. Нагрузочный прогон

1. Запустить генерацию: `POST /api/simulator/terminal/start-continuous` с заданным rate (см. ТЗ `06-terminal-simulator.md`). Статус — `GET /api/simulator/terminal/status`.
2. **Warmup 1–2 минуты**: не смотрим на цифры — идёт разогрев JIT, пулов, кэшей. Время начала измерительной фазы фиксируем.
3. Измерительная фаза ≥ 5 минут. Наблюдаем обе стороны:
   - клиент: фактический RPS, ответы, ошибки (лог/статус симулятора);
   - сервер: Grafana (latency, CPU, пулы), RabbitMQ Queues (глубина очередей — не растёт ли монотонно).
4. Контрольные проверки по ходу: фактический RPS ≈ заданному (иначе bottleneck — генератор); error rate < 1%; backlog очередей колеблется около нуля.
5. Остановить генерацию (stop-эндпоинт симулятора, если реализован, иначе `docker compose stop terminal-simulator`). Дождаться, пока очереди догонят хвост, — и проверить лаг следа: записи логгера доехали (`GET /api/transactions/search?stan=...`).
6. Скриншоты дашбордов — в `docs/practice-8/img/`.

Первый прогон почти всегда «в мусорку»: исчерпались балансы, RPS не вытянут, warmup забыт. Это нормально — на прогоны закладывайте 2–4 попытки.

**Результат шага:** ≥ 500 транзакций в измерительной фазе, метрики и скриншоты собраны.

## Шаг 7. Отчёт по нагрузке (`load-report.md`)

Собрать `docs/practice-8/load-report.md` по шаблону из [`artifact-8-strategy.md`](../../artifacts/artifact-8-strategy.md):

1. Профиль прогона: RPS, warmup, длительность, дата, стенд.
2. Данные: размер пула, балансы, схема генерации `stan`.
3. Таблица «метрика → порог → факт → вывод» по всем четырём: p95, error rate, throughput, лаг следа.
4. Наблюдения и скриншоты.
5. Разбор отклонений: если порог не пройден — где «колено», какой ресурс насытился, что с очередями. **Балл ставится за интерпретацию, не за скриншоты.**

**Результат шага:** `load-report.md` готов. Часть Б закрыта.

## Шаг 8. Стратегия (`strategy.md`)

1. Скопировать каркас из [`artifact-8-strategy.md`](../../artifacts/artifact-8-strategy.md) в `docs/practice-8/strategy.md` — заполняйте по разделам в течение недели, не в последний вечер.
2. Карта покрытия: пройдитесь по своим модулям тестов; ячейка = ссылки на тесты/прогоны/баг-репорты, не галочки.
3. Карта рисков: ≥ 5 рисков по формату лекции 16 — событие, вероятность, влияние, обоснование одной фразой, привязка к тестам.
4. Сводка дефектов: баг-репорты практики 7 по severity и звеньям.
5. Метрики: ссылки из шагов 3, 4, 7 + выводы.
6. Непроверенное: каждый пробел — что + почему + остаточный риск.
7. Рекомендации: 3–5 в формате «пробел/риск + действие + эффект».

**Результат шага:** `strategy.md` заполнен по всем семи разделам.

## Если что-то пошло не так

| Симптом | Причина | Действие |
|---|---|---|
| Allure-отчёт пустой (0 тестов) | нет зависимости `allure-junit5` или отчёт генерируется не из того каталога | проверить `target/allure-results` после `mvn test`; путь в шаге генерации |
| Trend пустой во втором прогоне | `history/` не скопирована в `allure-results` до генерации | порядок шагов: download history → restore → `mvn allure:report` → upload history |
| `download-artifact` падает | первого прогона истории ещё нет | `continue-on-error: true` на шаге скачивания |
| Pages 404 | не включён Pages или нет permissions | Settings → Pages → Source: GitHub Actions; `permissions: pages: write, id-token: write` |
| Фактический RPS ниже заданного | генератор — bottleneck (CPU в потолке) | снизить RPS до вытягиваемого и зафиксировать в отчёте; проверка генератора против эхо-стаба |
| Error rate растёт, дефектов нет | исчерпаны балансы/лимиты карт (коды `51`/`61`) | пул больше, балансы и лимиты ×10 от объёма прогона |
| p95 скачет от прогона к прогону | шум стенда | закрыть лишнее, warmup длиннее, 2–3 прогона и взять медиану |
| Backlog очередей растёт монотонно | консьюмер не догоняет продюсера | это находка, а не ошибка: зафиксировать и разобрать в отчёте |
| Grafana пустая | профиль `observability` не поднят | `docker compose --profile observability up -d` |
| Grafana не открывается на :3000 | на 3000 живёт Web Dashboard | Grafana — `http://localhost:3001` |
