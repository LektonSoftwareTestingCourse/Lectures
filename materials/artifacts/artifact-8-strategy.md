```markdown
# Финальная тестовая стратегия: СМП

## 1. Контекст и цель тестирования
- Система, контур тестирования за семестр, чем эта стратегия отличается от стратегии практики 2

## 2. Карта покрытия (coverage map)
| Требование / сервис | Unit | API | Интеграционные | E2E | Нагрузка |
|---|---|---|---|---|---|
| <требование> | <ссылка на тесты> | ... | ... | <SC-NNN> | <load-report> |
- Ячейка = ссылки на артефакты (тесты, прогоны Actions, баг-репорты), не галочки

## 3. Карта рисков (≥ 5)
| ID | Событие и последствие | Вероятность | Влияние | Обоснование | Чем закрыт |
|---|---|---|---|---|---|
| R-1 | <риск> | низк./сред./выс. | низк./сред./выс./крит. | <одна фраза> | <тесты / «не закрыт»> |

## 4. Сводка дефектов
| BR-NNN | Заголовок | Severity | Звено | Статус |
- Группировка по severity и звеньям (ответ / данные / асинхронный след), выводы

## 5. Метрики
- Allure: ссылка на опубликованный отчёт с историей (≥ 2 прогонов)
- Тренд покрытия: таблица «прогон → branch coverage по модулям» (≥ 3 запусков) + выводы
- Нагрузочный smoke: сводка из `load-report.md` (p95, error rate, throughput, лаг следа) + вывод

## 6. Что осталось непроверенным
- Каждый пробел: что не проверено + почему + какой риск остаётся

## 7. Рекомендации
- 3–5 пунктов: пробел/риск + конкретное действие + ожидаемый эффект
```

## Состав `docs/practice-8/load-report.md`

```markdown
# Нагрузочный smoke: СМП

## 1. Профиль прогона
| Интенсивность (RPS) | Warmup | Измерительная фаза | Всего транзакций | Дата, стенд |

## 2. Данные
- Пул карт (количество, балансы, лимиты), схема генерации `stan`

## 3. Метрики против порогов
| Метрика | Порог | Факт | Вывод |
| Latency p95 | < 2 с | | |
| Error rate | < 1% | | |
| Throughput | = заданному RPS | | |
| Лаг асинхронного следа | backlog не растёт монотонно | | |

## 4. Наблюдения
- Скриншоты Grafana/Prometheus/RabbitMQ (в `img/`), поведение очередей, CPU, пулы

## 5. Разбор отклонений
- Если порог не пройден: где «колено», какой ресурс насытился, что с очередями
```

## Требования

- **Часть А (отчётность)**: Allure-отчёт генерируется в CI и опубликован (артефакт сборки или GitHub Pages); история минимум двух прогонов (график Trend); тренд покрытия — таблица по трём и более запускам с выводами.
- **Часть Б (нагрузка)**: не менее 500 транзакций в измерительной фазе; warmup (1–2 мин) исключён из статистики; уникальные `stan`; пул карт с запасом по балансу и лимитам; четыре метрики с фактом против порога; интерпретация обязательна — балл за выводы, не за скриншоты. Прогон локальный, не в CI.
- **Часть В (стратегия)**: coverage map с артефактами в ячейках; не менее 5 рисков с вероятностью, влиянием, обоснованием и привязкой к тестам; сводка дефектов практики 7 по severity; заполненный раздел непроверенного; 3–5 конкретных рекомендаций.
- Каждый риск и каждая рекомендация должны быть защищаемы устно: на индивидуальной защите задаются вопросы «почему оценка такая».

## Как сдавать

Ветка `practice-8` + Issue с label `practice-8` и ссылками на репозиторий, ветку, Actions run и опубликованный Allure. CI прогоняет тесты и собирает Allure-отчёт; LLM находит документы в ветке по каноническим путям и проверяет по рубрике; стратегия защищается на проходной практике 18.12 и на индивидуальной защите.
