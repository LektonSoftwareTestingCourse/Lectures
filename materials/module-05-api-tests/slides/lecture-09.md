### Слайд 2. Место API-тестов в пирамиде

**Слайд:**
- Unit — логика в изоляции; E2E — вся система целиком; API — контракты между сервисами
- API-тесты: быстрее E2E (сотни мс), надёжнее (меньше зависимостей)
- Покрывают реальные контракты: JSON-форматы, статус-коды, заголовки
- Не зависят от UI — не ломаются при смене вёрстки
- В микросервисной архитектуре — основной уровень автоматизации

**Speaker notes:**

> Вспомним пирамиду из лекции 5. Unit-тесты проверяют логику в изоляции, но не скажут, правильно ли сервис A вызывает сервис B. E2E-тесты проверяют всё целиком, но они медленные и нестабильные. API-тесты — золотая середина: реальное взаимодействие через HTTP, но без пользовательского интерфейса.
>
> В микросервисной архитектуре это основной уровень автоматизации. В СМП восемь сервисов общаются через десятки контрактов: Gateway → Switch, Switch → Authorization, Authorization → Card Management, Authorization → Bin Lookup. Каждый контракт нужно верифицировать.
>
> Почему API-тестов обычно больше, чем E2E? Три причины: скорость (сотни миллисекунд против секунд), стабильность (меньше точек отказа) и стоимость поддержки (контракт меняется реже, чем интерфейс). Это мы подробно разбирали в лекции 5 про экономику пирамиды.

### Слайд 3. Что такое REST API

**Слайд:**
- REST — архитектурный стиль для распределённых систем (R. Fielding, 2000)
- API — Application Programming Interface, программный интерфейс
- REST API = набор эндпоинтов, к которым обращаются по HTTP
- Ключевые идеи: ресурсы через URL, операции через HTTP-методы, состояние в запросе
- Пример СМП: `GET /api/cards/{pan}` — ресурс «карта», операция «прочитать»

**Speaker notes:**

> Начнём с определений, потому что дальше всё строится на них.
>
> API (Application Programming Interface) — программный интерфейс: набор правил, по которым одна программа может вызывать функции другой. REST (Representational State Transfer) — архитектурный стиль для распределённых систем, предложенный Роем Филдингом в диссертации 2000 года. REST — не протокол и не стандарт, а набор принципов.
>
> REST API — это набор эндпоинтов (конкретных URL), к которым обращаются по протоколу HTTP. Ключевые идеи REST: ресурсы адресуются URL (например, `/api/cards/4000001234560001` — это ресурс «конкретная карта»), операции над ресурсом задаются HTTP-методом (GET — прочитать, POST — создать), а состояние передаётся в запросе, потому что сервер не хранит состояние клиента между запросами.
>
> Пример из СМП: `GET /api/cards/{pan}` читает карту по номеру. Ресурс — карта, операция — чтение. `POST /api/cards` создаёт карту. Ресурс — коллекция карт, операция — создание.
>
> Вопрос аудитории: чем REST API отличается от вызова функции внутри одной программы? Почему нам как тестировщикам важно, что это именно HTTP?
>
> Ответ: внутри одной программы вызов функции происходит напрямую в памяти, и ошибки видны сразу как исключения. REST API — это взаимодействие через сеть: между вызовом и ответом лежит HTTP, сериализация данных в JSON, возможные сетевые сбои, таймауты, потери. Поэтому тестировщику важно проверять не только «правильный ли результат», но и статус-коды, заголовки, формат тела ответа, поведение при недоступности. Это целый слой проверок, которого нет у обычного вызова функции. Конкретные техники этих проверок — в лекции 10.

### Слайд 4. HTTP-методы

**Слайд:**
- GET — прочитать ресурс (идемпотентный, без побочных эффектов)
- POST — создать ресурс или выполнить действие
- PUT — заменить ресурс целиком (идемпотентный)
- DELETE — удалить ресурс (идемпотентный)
- PATCH — частично обновить ресурс
- В СМП основные: GET (cards, transactions/search), POST (transactions, cards)

**Speaker notes:**

> HTTP-методы — это «глаголы» REST. Важно понимать их семантику и особенно понятие идемпотентности — подробно разберём его в лекции 10, но заложим базу сейчас.
>
> GET — прочитать ресурс. Не должен иметь побочных эффектов: сколько бы раз вы ни вызвали `GET /api/cards/123`, карта не изменится. POST — создать ресурс или выполнить действие. Не идемпотентен: два POST на `/api/cards` создадут две карты. PUT — заменить ресурс целиком, идемпотентен: повторный PUT даёт тот же результат. DELETE — удалить ресурс, идемпотентен: повторное удаление даёт тот же итог (ресурс удалён). PATCH — частичное обновление.
>
> В СМП основные методы — GET и POST. GET для чтения: `GET /api/cards/{pan}`, `GET /api/transactions/search`. POST для создания и действий: `POST /api/cards`, `POST /api/transactions` (провести авторизацию), `POST /api/simulator/terminal/run` (запустить симулятор).
>
> Вопрос аудитории: почему `POST /api/transactions` — это POST, а не PUT, хотя транзакция «создаётся»?
>
> Ответ: потому что семантика здесь — действие, а не создание ресурса в классическом смысле. POST передаёт команду «авторизуй эту транзакцию», у которой есть побочные эффекты — резервирование средств, генерация RRN, публикация в очередь. Это ближе к вызову действия, чем к созданию адресуемого ресурса. Кроме того, авторизация не идемпотентна по природе, что также соответствует семантике POST, а не идемпотентного PUT.

### Слайд 5. HTTP-статус-коды

**Слайд:**
- 2xx — успех: 200 OK, 201 Created
- 4xx — ошибка клиента: 400 Bad Request, 404 Not Found, 409 Conflict, 429 Too Many Requests
- 5xx — ошибка сервера: 500 Internal Server Error, 503 Service Unavailable
- Статус-код — часть контракта, его нужно тестировать
- В СМП: 200 (успех), 201 (создание карты), 400 (валидация), 404 (нет карты), 409 (дубль), 429 (лимит), 503 (downstream недоступен)

**Speaker notes:**

> Статус-коды — это язык, на котором сервер сообщает результат. Три больших класса.
>
> 2xx — успех. 200 OK — стандартный успех. 201 Created — ресурс создан (например, POST /api/cards возвращает 201). 4xx — ошибка клиента: клиент прислал что-то не то. 400 Bad Request — невалидные данные (PAN короче 16 цифр). 404 Not Found — ресурс не существует. 409 Conflict — конфликт (карта с таким PAN уже есть). 429 Too Many Requests — превышен rate limit. 5xx — ошибка сервера, проблема на нашей стороне: 500 — необработанное исключение, это всегда баг; 503 — сервис недоступен, downstream лежит.
>
> Ключевой тезис для тестировщика: статус-код — это часть контракта, и его нужно тестировать так же тщательно, как тело ответа. Правильный статус-код — половина правильного поведения.
>
> В СМП весь набор: 200, 201, 400, 404, 409, 429, 503. Мы будем писать тесты на каждый из них.
>
> Вопрос аудитории: сервер вернул 500 на запрос с невалидным PAN. Это нормально или баг?
>
> Ответ: баг. Невалидные данные — это 400, а не 500. Код 500 зарезервирован для необработанных ошибок. Различение 4xx и 5xx — важнейший навык в API-тестировании: ошибка клиента — это «исправь свой запрос», ошибка сервера — «у нас сломано». Мы вернёмся к этому различению в лекции 10 на примере бизнес-отказов.

### Слайд 6. Что такое контракт API

**Слайд:**
- Контракт — формальное соглашение о формате запросов и ответов
- Определяет: эндпоинты, методы, параметры, тела, статус-коды, заголовки
- Контракт — это артефакт, тест — это проверка соответствия
- В микросервисах контракт — «договор» между командами
- Пример СМП: POST /api/transactions принимает AuthorizationRequest, возвращает AuthorizationResponse

**Speaker notes:**

> Контракт API — это формальное соглашение о том, как выглядит запрос и ответ. Что определяет контракт? Эндпоинты (какие URL есть), методы (что с ними можно делать), параметры (query и path), формат тела запроса, формат тела ответа, статус-коды для каждого случая, заголовки.
>
> Важное разграничение: контракт — это артефакт (документ или файл), а тест — это проверка соответствия реального поведения контракту. Контракт описывает «как должно быть», тест проверяет «так ли на самом деле».
>
> В микросервисах контракт — это договор между командами. Команда Switch говорит команде Authorization: «Я буду слать тебе вот такой JSON, а ты верни вот такой». Если кто-то нарушает договор, другая сторона ломается, даже если её собственные тесты зелёные. Эту проблему мы уже затронули в лекции 6, когда обсуждали риски подхода «гонять только изменённые сервисы».
>
> Пример из СМП: контракт `POST /api/transactions` — на вход AuthorizationRequest (поля mti, stan, pan, amount, merchantId и так далее), на выход AuthorizationResponse (mti, rrn, authCode, status и так далее). Этот контракт зафиксирован в [`practic/docs/api-spec.md`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/docs/api-spec.md).
>
> Вопрос аудитории: где живёт контракт в вашем проекте? Кто его владелец и кто отвечает за его соблюдение?
>
> Ответ: в реальных проектах владельцем контракта обычно выступает команда-поставщик (provider), которая публикует спецификацию. Но за соблюдение отвечают обе стороны: потребитель пишет тесты против контракта, поставщик — гарантирует соответствие. В СМП единая спецификация собирается DevOps-ролью из контрактов всех команд, как мы видели в ТЗ DevOps. Если контракт не зафиксирован письменно, он живёт «в головах» и рано или поздно расходится между командами.

### Слайд 7. Что такое OpenAPI

**Слайд:**
- OpenAPI (ранее Swagger) — индустриальный стандарт описания REST API
- Машиночитаемый формат: YAML или JSON
- Описывает: эндпоинты, методы, параметры, схемы запросов и ответов, статус-коды
- Один файл = полное описание API + интерактивная документация (Swagger UI)
- В СМП спецификация — [`practic/docs/api-spec.md`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/docs/api-spec.md) (исходник OpenAPI 3.0)

**Speaker notes:**

> OpenAPI (раньше назывался Swagger) — индустриальный стандарт описания REST API. Это машиночитаемый документ в формате YAML или JSON, который описывает всё про API: какие эндпоинты есть, какие методы, какие параметры, какие схемы запросов и ответов, какие статус-коды.
>
> Зачем он нужен? Один файл OpenAPI даёт сразу несколько вещей. Во-первых, документацию — человек читает и понимает API. Во-вторых, интерактивную справку: Swagger UI рендерит OpenAPI в веб-страницу, где можно прямо в браузере обращаться к эндпоинтам. В-третьих, основу для генерации: из OpenAPI можно сгенерировать клиентские библиотеки, серверные стабы и JSON-схемы.
>
> В СМП OpenAPI-спецификация есть в [`practic/docs/api-spec.md`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/docs/api-spec.md), в человекочитаемом виде. В реальном проекте DevOps-роль отвечает за сборку единой спецификации из контрактов всех команд, это мы упоминали в лекции 6.
>
> Вопрос аудитории: что надёжнее как источник правды — OpenAPI-спецификация или код сервиса? Почему они могут расходиться?
>
> Ответ: надёжнее всего — автоматически синхронизировать оба источника. Если спецификация пишется вручную отдельно от кода, она неизбежно устаревает: разработчик изменил код, но забыл обновить спецификацию. Поэтому в зрелых командах либо генерируют спецификацию из кода (по аннотациям), либо генерируют код и схемы из спецификации. Источник правды — тот, который меняется первым. Расхождение — это сигнал к тестированию: если код и спецификация расходятся, тест должен это поймать.

### Слайд 8. Читаем OpenAPI-спецификацию СМП

**Слайд:**
- Разделы: Health, Cards, Transactions, Simulator, Dashboard, WebSocket, внутренние эндпоинты
- Каждый эндпоинт: метод, путь, параметры, тело, ответы, ошибки
- Модели данных: Card, AuthorizationRequest, AuthorizationResponse, Transaction
- Коды ответов: 00 (Approved), 51 (Insufficient Funds), 54 (Expired Card), 61 (Exceeds Limit)
- Суммы в минорных единицах (копейки), даты ISO 8601

**Speaker notes:**

> Пройдёмся по реальной спецификации СМП, чтобы увидеть, как устроен контракт на практике.
>
> Спецификация разбита на разделы по доменам: Health, Cards, Transactions, Simulator, Dashboard, WebSocket и отдельно внутренние межсервисные эндпоинты. Для каждого эндпоинта указаны метод, путь, тело запроса, ответ и ошибки.
>
> Отдельный блок — модели данных. Например, Card имеет поля pan (16 цифр), status (перечисление ACTIVE, INACTIVE, BLOCKED, EXPIRED), availableBalance, dailyLimit, monthlyLimit. AuthorizationResponse — mti, stan, rrn, authCode, responseCode, status.
>
> Два важных правила из спецификации. Первое: все суммы в минорных единицах — копейках, а не рублях. Значение 150000 — это 1500 рублей. Это критично для тестов: перепутать копейки и рубли — классическая ошибка, ведущая к неверным ожиданиям в проверках баланса. Второе: даты в формате ISO 8601.
>
> Отдельно — коды ответов по стандарту ISO 8583: 00 = Approved, 51 = Insufficient Funds, 54 = Expired Card, 61 = Exceeds Amount Limit. Это доменный слой поверх HTTP-статусов: HTTP может быть 200, а внутри — responseCode 51 (недостаточно средств). Важно различать два уровня кодов при проектировании проверок. Этот момент подробно раскроем в лекции 10 на негативных сценариях.

### Слайд 9. Инструментарий: REST-assured

**Слайд:**
- Java-библиотека для тестирования REST API (DSL)
- Синтаксис в стиле given/when/then — читается как тест-кейс
- Интеграция с JUnit 5, Hamcrest matchers, JSONPath
- Подходит для автоматизации: тесты живут в коде, гоняются в CI
- Пример:
```java
given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/api/transactions")
.then()
    .statusCode(200)
    .body("status", equalTo("APPROVED"))
    .body("rrn", notNullValue());
```

**Speaker notes:**

> Первый инструмент — REST-assured. Он появился в 2010 году и с тех пор стал стандартом де-факто для API-тестов на Java. Это Java-библиотека, которая предоставляет DSL (Domain-Specific Language) — специализированный язык, заточенный под HTTP-запросы, в отличие от универсального языка, которым является сама Java.
>
> Главное преимущество REST-assured — синтаксис в стиле Gherkin. Разберём, что это такое, потому что на этом держится вся читаемость тестов. Gherkin — это язык описания сценариев в формате Given/When/Then, изначально созданный для Behaviour-Driven Development (BDD — разработка через поведение). Given — предусловие («дано»), When — действие («когда»), Then — результат («тогда»). Такой синтаксис делает тесты читаемыми как спецификация: даже нетехнический специалист может понять, что проверяется, не вникая в то, как это реализовано.
>
> Базовая структура REST-assured теста — это три блока. Блок `given()` — предусловия, то есть что мы отправляем: заголовки (Content-Type — формат тела запроса, Authorization — токен доступа), query-параметры (то, что идёт после `?` в URL), path-параметры (переменные в пути вроде `/api/cards/{pan}`), тело запроса. Блок `when()` — действие: HTTP-метод и путь. Блок `then()` — проверки: статус-код, тело ответа (через JSONPath и Hamcrest matchers), заголовки ответа, время ответа.
>
> Такая трёхчастная запись читается как предложение: «при условии, что тело — валидный JSON, когда я делаю GET /api/transactions/search со статусом APPROVED, тогда ожидаю статус 200 и непустой результат за время менее двух секунд». Именно эта читаемость делает REST-assured стандартом индустрии.
>
> Почему given/when/then — это естественно? Обратите внимание: эта трёхчастная структура — не изобретение REST-assured. Это универсальный шаблон построения любого тест-кейса, ручного или автоматического. В ручном тестировании тест-кейс всегда выглядит так: «Предусловие: карта активна, баланс 1000 руб. Шаги: 1) отправить запрос авторизации на 500 руб, 2) проверить ответ. Ожидаемый результат: статус APPROVED, баланс 500 руб». Предусловие → шаги → ожидаемый результат. Given → When → Then. На модуле 2 вы изучали тест-дизайн в целом — классы эквивалентности, граничные значения, decision tables. Любая из этих техник в итоге порождает тест-кейсы именно в такой трёхчастной структуре. REST-assured просто переносит этот универсальный шаблон в код: `given()` — это предусловия тест-кейса, `when()` — шаги, `then()` — ожидаемый результат. Это не просто синтаксический сахар, а прямое отражение того, как мы мыслим о тестировании.
>
> Вопрос аудитории: вспомните техники тест-дизайна из модуля 2. Как бы вы применили классы эквивалентности и граничные значения к параметрам этого запроса? Набросаем вместе: для `status` — APPROVED и DECLINED (два класса эквивалентности), для `limit` — 1, 50, 100, 0, −1 (граничные значения). Это и будет наш тест-дизайн для search.
>
> Ещё вопрос: что здесь от Gherkin, а что от Java? Ответ: Gherkin даёт читаемость для человека (бизнес-аналитик может прочитать тест), а Java — всю мощь языка (циклы, условия, библиотеки) для сложных сценариев. REST-assured удачно совмещает и то, и другое.
>
> Под капотом REST-assured использует Apache HTTP Client для отправки запросов — это зрелая Java-библиотека для работы с HTTP, но нам не придётся иметь с ней дело напрямую: DSL всё инкапсулирует. Интегрируется REST-assured с JUnit 5 — фреймворком запуска тестов и проверок-assertions, с которым вы детально познакомитесь в модуле 4. Для выразительных проверок используется Hamcrest — библиотека matcher'ов (проверок) в стиле `assertThat(value, is(equalTo(expected)))`. Она даёт `equalTo()`, `notNullValue()`, `greaterThan()`, `containsString()`, `hasSize()` — читаемые проверки вместо ручных `if`-сравнений.
>
> Для навигации по ответу используется JSONPath — язык запросов к JSON, аналог XPath для XML. Он позволяет обратиться к любому полю в JSON-документе: `$.store.book[0].title` — это название первой книги в магазине. В REST-assured мы будем использовать упрощённый синтаксис: `"status"` — поле первого уровня, `"items[0].pan"` — первый элемент массива.
>
> Подключается REST-assured одной Maven-зависимостью (координаты `io.rest-assured:rest-assured`), а статический импорт `io.restassured.RestAssured.*` даёт доступ к `given()`, `when()`, `get()`, `post()` и другим методам без префикса класса — поэтому в тестах они вызываются просто как `given()`.
>
> И важный философский момент тест-дизайна: чем API-тест отличается от unit-теста? Unit-тест проверяет реализацию — «правильно ли работает этот метод». API-тест проверяет поведение — «правильно ли сервис отвечает на этот запрос». Различие принципиально: unit-тесты привязаны к коду, API-тесты — к контракту. Изменение реализации без изменения контракта не должно ломать API-тесты, и это их сила как регрессионного барьера. Вспомните Testing Trophy из лекции 5 — это ровно тот аргумент «тестируем поведение, а не реализацию», который там звучал.
>
> REST-assured — это про автоматизацию: тесты живут в коде, версионируются, гоняются в CI-пайплайне по каждому push — ровно так, как мы разбирали в лекции 6. Детально разберём его в лекции 10 и на практике.

### Слайд 10. Инструментарий: Postman

**Слайд:**
- Графический клиент для ручного исследования API
- Коллекции запросов, окружения (environments), переменные
- Быстрая проверка: «что вернёт этот эндпоинт?»
- Нет компиляции и запуска — мгновенный ответ на вопрос
- Для исследования и отладки, а не для регрессионной автоматизации

**Speaker notes:**

> Второй инструмент — Postman. Это графический клиент для работы с HTTP API. Если REST-assured про автоматизацию, то Postman про ручное исследование и быструю отладку. Давайте сразу развеем миф: Postman — это не «детская» игрушка, а полноценный инструмент, который в реальных проектах используют и разработчики, и тестировщики, и аналитики. Просто у него своя ниша.
>
> Ключевые возможности. Коллекции — наборы запросов, сгруппированные по сценариям; в реальных командах коллекции часто хранят в репозитории и экспортируют, чтобы они были у всех одинаковые. Окружения (environments) — наборы переменных (baseUrl, токены), переключаемые одним кликом: это то, чем пользуются, чтобы один и тот же набор запросов гонять на dev, staging и prod, меняя только адрес. Переменные — можно взять значение из ответа одного запроса и подставить в следующий: например, создать карту, вытащить PAN, и дальше тестировать транзакции с этим PAN. Плюс встроенный скриптинг на JavaScript для простых проверок прямо в Postman.
>
> Как это реально работает на проектах? Postman — это инструмент разведки и отладки, а не регрессионной автоматизации. Когда тестировщик получает новую фичу, он первым делом открывает Postman и вручную дёргает эндпоинт: «что он вернёт, если послать такой JSON?» Это быстрее, чем писать и запускать код, — вбил запрос, нажал Send, увидел ответ. На этой стадии рождается понимание контракта, которое потом переносится в автотесты.
>
> Ещё одно реальное применение — ручные сценарии, которые не автоматизируют. Например, разовая проверка нового партнёрского API, отладка проблемы в продакшне, или демонстрация заказчику. В таких случаях держать запрос в коллекции Postman удобнее, чем писать под него тест-код, который потом удалять.
>
> Но есть и граница. Postman-коллекции сложно поддерживать в CI и сложно версионировать как код: коллекция — это набор запросов, который не запускается сам по себе при каждом коммите, не ревьюится как код, и его легко оставить устаревшим. Поэтому как только проверка становится регулярной и должна выполняться при каждом изменении — ей место в REST-assured, который живёт в репозитории и гоняется в пайплайне.
>
> Вопрос аудитории: как вы думаете, почему «Postman вместо автоматизации» — это антипаттерн в долгосрочной перспективе?
>
> Ответ: коллекция Postman не даёт автоматической обратной связи — её надо запускать вручную, и в какой-то момент команда просто перестаёт это делать. Регрессионные тесты должны жить в репозитории и запускаться автоматически при каждом изменении (вспомним лекцию 6: тесты без автоматического запуска мертвы). Postman хорош для разовой разведки, но как единственный инструмент регресса он оставляет проверки «на ручной запуск», и они быстро превращаются в мёртвый груз.

### Слайд 11. REST-assured vs Postman: когда что

**Слайд:**
- Postman: ручное исследование, быстрые проверки, отладка контракта
- REST-assured: автоматические регрессионные тесты, CI-интеграция
- Postman — быстрый старт, но сложно версионировать и гонять в CI
- REST-assured — требует кода, но тесты живут с проектом и гоняются автоматически
- Правильный воркфлоу: исследовать в Postman → зафиксировать в REST-assured

**Speaker notes:**

> Сведём инструменты. Postman — ручное исследование и отладка. REST-assured — автоматический регресс и CI.
>
> Postman даёт быстрый старт: не нужно писать код, просто кликаешь. Но у этого есть цена: коллекции Postman живут вне репозитория (или в JSON-экспорте, который неудобно ревьюить), их сложно запускать в CI, и они не интегрируются с Java-проектом. REST-assured требует написать код, но этот код живёт в репозитории, версионируется вместе с продуктом, ревьюится как обычный код и автоматически гоняется в пайплайне.
>
> Правильный воркфлоу инженера тестирования: сначала исследуешь API в Postman — быстро нащупываешь, как работает эндпоинт, какие коды возвращает, какие краевые случаи. Потом, когда поведение понятно, фиксируешь проверки в REST-assured — они становятся регрессионным активом проекта.
>
> Вопрос аудитории: в каком случае имеет смысл оставить проверку в Postman и не переносить её в код?
>
> Ответ: когда проверка разовая и неповторяющаяся — например, исследование нового эндпоинта перед написанием спецификации, или разовая демонстрация заказчику, или быстрая отладка чужого сервиса, где мы не будем писать постоянные тесты. Как только проверка должна выполняться регулярно — она должна жить в коде. Критерий простой: будет ли эта проверка нужна завтра и послезавтра? Если да — ей место в REST-assured, а не в коллекции Postman.

### Слайд 12. Базовый REST-assured тест на СМП

**Слайд:**
```java
@Test
void shouldApproveValidTransaction() {
    String requestBody = """
    {
        "mti": "0100", "stan": "000001",
        "pan": "4000001234560001",
        "processingCode": "000000",
        "amount": 150000,
        "currencyCode": "643",
        "terminalId": "TERM001",
        "terminalType": "POS",
        "merchantId": "MERCH12345678901",
        "mcc": "5411",
        "acquirerId": "ACQ001"
    }
    """;

    given()
        .contentType(ContentType.JSON)
        .body(requestBody)
    .when()
        .post("/api/transactions")
    .then()
        .statusCode(200)
        .body("mti", equalTo("0110"))
        .body("status", equalTo("APPROVED"))
        .body("responseCode", equalTo("00"))
        .body("rrn", notNullValue())
        .body("authCode", notNullValue())
        .body("processingTimeMs", greaterThan(0));
}
```
- Проверяем: статус-код, поля тела, бизнес-результат, время ответа
- Каждая проверка — отдельная строка, легко читать

**Speaker notes:**

> Разберём базовый тест на примере главного эндпоинта СМП — `POST /api/transactions`. Это happy path: валидная карта, достаточно денег, все поля корректны. Но прежде чем смотреть на проверки, обратите внимание на саму структуру — это и есть та базовая структура DSL, о которой мы начали говорить на слайде 9.
>
> Тест разбит на три блока, ровно как тест-кейс в ручном тестировании. Блок `given()` — предусловия: мы задаём Content-Type JSON и тело запроса. Это «дано: валидный запрос на авторизацию». Блок `when()` — действие: POST на `/api/transactions`. Это «когда: отправляю запрос». Блок `then()` — проверки: статус-код, поля ответа, сгенерированные коды, время. Это «тогда: ожидаю 200 и APPROVED». Один и тот же шаблон «предусловие → действие → проверка» работает и в ручном тест-кейсе, и в REST-assured, — разница лишь в том, что здесь он выражен кодом.
>
> Теперь пройдёмся по содержанию. Запрос содержит поля по контракту AuthorizationRequest: mti=0100 (запрос авторизации), stan (номер запроса), pan (номер карты), amount=150000 (1500 рублей в копейках), merchantId, mcc, acquirerId.
>
> Проверки в `then()`: statusCode(200) — HTTP-успех; mti должен смениться с 0100 на 0110 (ответ авторизации); status = APPROVED; responseCode = "00" (одобрено по ISO 8583); rrn и authCode не null — система их сгенерировала; processingTimeMs больше нуля.
>
> Обратите внимание на читаемость: каждая проверка — отдельная строка, видно, что проверяется. Это и есть преимущество DSL. И заметьте: мы проверяем не только «вернул 200», но и бизнес-результат — статус APPROVED и сгенерированные коды. Код 200 без APPROVED не значит, что система работает правильно.
>
> Это happy path, позитивный сценарий. Негативные сценарии и более сложные техники — в лекции 10.

### Слайд 13. Проверка статус-кодов: тест на каждый случай

**Слайд:**
```java
@ParameterizedTest
@ValueSource(strings = {"", "123", "400000123456000", "40000012345600001"})
void shouldReturn400ForInvalidPan(String invalidPan) {
    given()
        .contentType(ContentType.JSON)
        .body(transactionJson(invalidPan, 150000L))
    .when()
        .post("/api/transactions")
    .then()
        .statusCode(400)
        .body("error", equalTo("VALIDATION_ERROR"));
}
```
- Один тест — несколько невалидных значений (классы эквивалентности PAN)
- Проверяем и статус-код, и структуру тела ошибки
- Аналогично: 404 (нет карты), 409 (дубль карты), 429 (лимит), 503 (downstream)

**Speaker notes:**

> Теперь негативный сценарий — тестирование валидации. Это `@ParameterizedTest` из JUnit 5: один тест-метод запускается несколько раз с разными входными данными. Об аннотации JUnit 5 мы говорили в лекции 6 и детально разберём в модуле 4.
>
> Здесь мы проверяем классы эквивалентности для PAN: пустая строка, слишком короткий (15 цифр), слишком длинный (17 цифр). Все эти значения попадают в один класс «невалидный PAN» — и все должны вернуть HTTP 400. Проверяем не только статус-код, но и структуру тела ошибки: поле `error` должно быть `VALIDATION_ERROR` — так определил контракт.
>
> Почему классы эквивалентности, а не перебор всех вариантов? Потому что все длины меньше 16 и больше 16 обрабатываются валидатором одинаково. Проверять 0, 1, 2 и так далее до 15 цифр бессмысленно — это исчерпывающее тестирование, которое невозможно и не нужно [Spillner et al., 2014, 2.4]. Мы берём по одному представителю из каждого класса. Это прямое применение техники из модуля 2.
>
> Аналогично тестируем остальные статус-коды: 404 (GET карты, которой нет), 409 (создание карты с существующим PAN), 429 (превышение rate limit), 503 (downstream недоступен). Каждый статус-код из контракта — минимум один тест.

### Слайд 14. Организация API-тестов в проекте

**Слайд:**
- Базовый URL и общие заголовки выносятся в `RequestSpecification` или `@BeforeAll`
- Тестовые данные готовятся в `@BeforeEach`, чтобы каждый тест был независим
- Тесты группируются по эндпоинтам и сценариям, а не «в одну кучу»
- Окружение (Docker Compose или Testcontainers) поднимается до запуска
- В CI эти же тесты гоняются автоматически — как мы разбирали в лекции 6

**Speaker notes:**

> Раз мы заговорили о том, как это реально устроено на проектах, остановимся на организации API-тестов — это то, что отличает поддерживаемый тест-сьют от хаоса.
>
> Первое правило — не дублировать общие настройки. Базовый URL (`http://localhost:8080`) и общие заголовки выносят в одно место: в REST-assured это `RequestSpecification` — переиспользуемый объект с настройками запроса, либо статический блок в `@BeforeAll`. Представьте, что у вас сто тестов, и в каждом написано `baseUri(...)`: сменился адрес окружения — и вам надо править сто мест. С одним RequestSpecification вы правите одно.
>
> Второе правило — изолированные тестовые данные. Тесты готовят данные в `@BeforeEach`, а не полагаются на данные, оставшиеся от другого теста. Почему? Потому что порядок выполнения тестов не гарантирован, и если тест B зависит от карты, созданной тестом A, он начнёт падать непредсказуемо. Это тот же принцип независимости тестов, о котором мы говорили в лекции 6 на примере flaky smoke-тестов.
>
> Третье правило — группировка. Тесты группируют по эндпоинтам и сценариям: отдельный класс на карты, отдельный на транзакции, отдельный на health-check. Это делает сьют читаемым и позволяет запускать точечно: `mvn test -Dtest=CardApiTest`, а не «всё сразу».
>
> Четвёртое — окружение. API-тестам нужен живой сервис, поэтому перед запуском поднимают окружение: в СМП это Docker Compose (`docker compose up -d`), в реальных проектах для изоляции часто используют Testcontainers — библиотеку, которая поднимает контейнеры прямо из теста. Подробно Testcontainers разберём в модуле 6 у Ирины Габановой.
>
> И наконец, главное: эти же тесты, что вы пишете локально, гоняются в CI по каждому push. Мы это детально разобрали в лекции 6 — там же в пайплайне СМП есть джоб `java-services`, который прогоняет тесты всех сервисов. Так локальная практика и промышленный процесс смыкаются в одну систему.
>
> Вопрос аудитории: зачем выносить создание тестовой карты в `@BeforeEach`, если тест и так её создаёт в начале? Ответ обсудим: разница в том, что `@BeforeEach` гарантирует одинаковое начальное состояние для всех тестов, даже если тест упал на середине и оставил данные в промежуточном состоянии.

### Слайд 15. Интерактив: найди ошибку в тесте

**Слайд:**
```java
@Test
void shouldDeclineForInsufficientFunds() {
    String pan = createCard(10000L);  // баланс 100 руб

    given()
        .contentType(ContentType.JSON)
        .body(transactionJson(pan, 150000L))  // покупка на 1500 руб
    .when()
        .post("/api/transactions")
    .then()

```
- Вопрос: найдите ошибку в этом тесте и объясните, почему это проблема
- Подсказка: сервер обрабатывает insufficient funds корректно — это не баг
- Ответ: HTTP 500 — неверный ожидаемый статус. Недостаток средств — бизнес-правило, сервер должен вернуть 200 со статусом DECLINED, а не 500

**Speaker notes:**

> Интерактив. Посмотрите на тест. Карта с балансом 100 руб (10 000 копеек). Пытаемся купить на 1500 руб (150 000 копеек). Ожидаем HTTP 500 и статус DECLINED.
>
> Что не так? Давайте думать вместе. HTTP 500 — что это значит? Internal Server Error — необработанная ошибка на сервере. NullPointerException, SQLException, выход за границы массива. Это всегда баг.
>
> А insufficient funds — это ожидаемая бизнес-ситуация. Это не баг. Сервер должен обработать её штатно: проверить баланс, обнаружить недостаток, вернуть HTTP 200 со статусом DECLINED и причиной INSUFFICIENT_FUNDS.
>
> Если сервер действительно возвращает 500 на недостаток средств — это баг сервера, и тест его правильно ловит, но с неправильным ожиданием: ожидает 500, хотя правильное поведение — 200. Если же сервер возвращает 200/DECLINED, а тест ждёт 500 — тест упадёт ложно: система работает правильно, а тест красный. Это называется false positive в тестировании — тест сигнализирует о баге там, где бага нет.
>
> Мораль: знайте, какой статус-код ожидать. HTTP 500 зарезервирован для необработанных ошибок. Бизнес-отказы — это 200 с DECLINED или 422 Unprocessable Entity. Это различие двух уровней кодов, которое мы обсуждали на слайдах 5 и 8, здесь применено на практике.
>
> Второй вопрос: что ещё можно улучшить в этом тесте? Дополнительные проверки: во-первых, убедиться, что баланс не изменился после отклонённой транзакции — был 100 руб, остался 100 руб; во-вторых, проверить `processingTimeMs` — отказ по insufficient funds должен быть даже быстрее успешной авторизации, потому что нет вызова `POST /reserve` на резервирование.
>
> Третий вопрос: как бы вы спроектировали классы эквивалентности для тестирования insufficient funds? Какие граничные значения выбрали бы?
>
> Ответ: ключевые границы — это баланс ровно равен сумме (граница между одобрением и отказом), баланс на единицу меньше суммы (первый отказ), баланс на единицу больше (первое одобрение), нулевой баланс. Это классическое применение граничных значений из модуля 2 к домену процессинга.

### Слайд 16. Выводы и анонс

**Слайд:**
- REST API = ресурсы (URL) + операции (HTTP-методы) + статус-коды
- Контракт — формальное соглашение, OpenAPI — его машиночитаемая форма
- Статус-код — часть контракта, тестируем каждый
- REST-assured — автоматизация, Postman — исследование
- Лекция 10: паттерны API-тестов — позитивные/негативные, аутентификация, идемпотентность

**Speaker notes:**

> Подведём итог. REST API — это ресурсы через URL, операции через HTTP-методы, результат через статус-коды. Контракт — формальное соглашение о форматах, а OpenAPI — его машиночитаемая форма, из которой можно генерировать документацию и схемы. Статус-код — часть контракта: на каждый код из спецификации пишем тест. Инструменты: REST-assured для автоматизации, Postman для исследования; правильный воркфлоу — сначала разведка в Postman, потом фиксация в коде.
>
> На следующей лекции перейдём от основ к паттернам: как правильно строить позитивные и негативные сценарии, как тестировать аутентификацию, что такое идемпотентность и как её проверять, и как тестировать асинхронные контракты. Вопросы?
