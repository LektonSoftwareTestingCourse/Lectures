### Слайд 2. Позитивные сценарии: happy path

**Слайд:**
- Позитивный сценарий — валидные данные, корректный бизнес-исход
- Начинаем тестирование всегда с happy path — «карта активна, денег хватает»
- Проверяем не только статус-код, но и бизнес-результат
- Пример СМП: POST /api/transactions → 200, APPROVED, RRN сгенерирован, authCode присутствует
- Happy path — точка отсчёта, от которой отходят все негативные ветки

**Speaker notes:**

> Позитивный сценарий — это тест, где все данные валидны и система должна отработать успешно. В API-тестировании позитивный сценарий часто называют happy path — «счастливый путь».
>
> Почему начинаем именно с него? Три причины. Первое: если happy path не работает, нет смысла тестировать негативные ветки — базовый сценарий сломан. Второе: happy path фиксирует эталон корректного поведения, от которого мы отталкиваемся, проектируя остальные тесты. Третье: happy path проверяет больше, чем кажется, — не только «вернул 200», но и весь бизнес-результат.
>
> Пример СМП: `POST /api/transactions` с валидной картой. Проверяем: HTTP 200, `status` = APPROVED, `responseCode` = "00", `rrn` сгенерирован (12 цифр), `authCode` присутствует (6 символов), `processingTimeMs` больше нуля. Заметьте — код 200 без APPROVED не значит «работает правильно». Проверяем именно бизнес-исход.
>
> Вопрос аудитории: что должно произойти с балансом карты после успешной авторизации? Как проверить это в API-тесте?
>
> Ответ: баланс должен уменьшиться на сумму транзакции. Проверка выполняется дополнительным GET-запросом `GET /api/cards/{pan}` после авторизации, где мы сверяем `availableBalance` с ожидаемым значением (начальный баланс минус сумма). Это пример цепочки запросов, которую мы разбирали в лекции 9: первый запрос меняет состояние, второй его проверяет. Именно такая двухшаговая проверка отличает поверхностный тест «вернул 200» от содержательного теста «система действительно изменила данные».

### Слайд 3. Негативные сценарии: declined-кейсы

**Слайд:**
- Негативный сценарий — невалидные данные или некорректный бизнес-исход
- Два типа негатива: ошибки валидации (400) и бизнес-отказы (200 + DECLINED)
- В СМП алгоритм авторизации даёт шесть declined-веток:
  - Карта не найдена → responseCode 14
  - Статус INACTIVE/BLOCKED → DECLINED
  - Срок истёк → responseCode 54
  - Дневной лимит превышен → responseCode 61
  - Месячный лимит превышен → DECLINED
  - Недостаточно средств → responseCode 51

**Speaker notes:**

> Негативный сценарий — тест, где данные невалидны или бизнес-исход отрицательный. Важно различать два типа негатива, потому что они живут на разных уровнях.
>
> Первый тип — ошибки валидации: клиент прислал некорректные данные, сервер вернул 400 Bad Request. Пример: PAN из 15 цифр, amount отрицательный, пропущено обязательное поле. Это уровень HTTP, мы разбирали его в лекции 9.
>
> Второй тип — бизнес-отказы: запрос корректен, но бизнес-логика говорит «нет». Сервер возвращает 200 + DECLINED с причиной. Это уровень домена. Ключевое различие: бизнес-отказ — это не баг, это ожидаемое поведение.
>
> В СМП алгоритм авторизации (ТЗ Authorization) даёт целую таблицу declined-веток, и каждая — отдельный тест. Карта не найдена → 14 (Invalid Card Number). Статус INACTIVE или BLOCKED → DECLINED. Срок истёк → 54 (Expired Card). Дневной лимит превышен → 61 (Exceeds Limit). Недостаточно средств → 51 (Insufficient Funds).
>
> Вопрос аудитории: сколько негативных тестов нужно для этого эндпоинта? Вспомните классы эквивалентности из модуля 2. Подсказка: статус карты имеет несколько значений, и каждое — отдельный класс эквивалентности.
>
> Ответ: статус карты — это перечисление ACTIVE, INACTIVE, BLOCKED, EXPIRED. Каждое значение — отдельный класс эквивалентности, потому что алгоритм обрабатывает их по-разному. Плюс отдельный класс «карта не найдена». Итого только по статусу — четыре ветки. Добавляем лимиты (дневной, месячный), срок действия, баланс — и получаем минимум восемь тестов на declined-ветки, плюс happy path. Это прямое применение техники классов эквивалентности из модуля 2: выделяем классы входных данных, на каждый — один представительный тест.

### Слайд 4. Аутентификация в API: зачем и какая бывает

**Слайд:**
- Аутентификация — проверка, кто обращается к API
- Авторизация — проверка, что ему можно делать
- В реальных API почти всегда есть доступ по токену или ключу
- Основные схемы: API key, Basic Auth, Bearer token (OAuth2)
- В СМП аутентификации нет — API открытый, это упрощение учебного проекта

**Speaker notes:**

> Переходим к аутентификации. Сначала два термина, которые часто путают. Аутентификация (authentication) — проверка, кто обращается: «это действительно тот, за кого себя выдаёт». Авторизация (authorization) — проверка, что этому субъекту можно: «имеет ли он право на эту операцию». В русском языке оба слова звучат похоже, но это разные вещи.
>
> Почему тестировщику это важно? Потому что в реальных API почти всегда есть контроль доступа, и его нужно тестировать: что происходит с запросом без токена, с невалидным токеном, с токеном без нужных прав.
>
> Основные схемы. API key — простой ключ, передаётся в заголовке или параметре. Basic Auth — логин и пароль, закодированные в base64 в заголовке `Authorization: Basic ...`. Bearer token — токен доступа, чаще всего по стандарту OAuth2, передаётся в `Authorization: Bearer <token>`.
>
> Важная честность: в СМП аутентификации нет — все эндпоинты открыты. Это сознательное упрощение учебного проекта, чтобы не усложнять первые практики. Но в реальном процессинге контроль доступа обязателен. Поэтому разберём схемы теоретически, а на практике вы примените их в реальных проектах.

### Слайд 5. Как тестировать API с аутентификацией

**Слайд:**
- Тест без токена → 401 Unauthorized
- Тест с невалидным токеном → 401
- Тест с валидным токеном, но без прав → 403 Forbidden
- Тест с валидным токеном и правами → 200
- В REST-assured: `.header("Authorization", "Bearer " + token)` или `.auth().oauth2(token)`

**Speaker notes:**

> Разберём, как тестировать API с аутентификацией. Базовый набор — четыре теста, по одному на каждый класс эквивалентности доступа.
>
> Без токена → 401 Unauthorized: сервер должен отказать, а не вернуть данные. Невалидный токен (истёкший или поддельный) → тоже 401. Валидный токен, но без нужных прав → 403 Forbidden: пользователь опознан, но операция ему запрещена. Валидный токен с правами → 200: доступ разрешён.
>
> Различие 401 и 403 важно: 401 — «я тебя не знаю» (проблема идентификации), 403 — «я тебя знаю, но не пущу» (проблема прав). Тестировщик должен проверять оба. Это то же различение статус-кодов, которое мы ввели в лекции 9, применённое к доступу.
>
> В REST-assured это делается через заголовок: `.header("Authorization", "Bearer " + token)` или специализированный метод `.auth().oauth2(token)`. Токен обычно получают отдельным запросом к эндпоинту логина и подставляют в последующие.
>
> Вопрос аудитории: как в автоматическом тесте получить валидный токен? Что делать, если токен живёт 15 минут, а тест-сьют идёт час?
>
> Ответ: токен получают программно в начале теста, обращаясь к эндпоинту логина с тестовыми учётными данными, и сохраняют в переменную. Если токен живёт меньше времени прогона, есть два приёма: либо получать токен заново при получении 401 (ретрай с перезапросом), либо использовать refresh token для продления. Проблема короткоживущего токена — это пример того, как срок жизни данных влияет на тест-дизайн: мы проектируем тест так, чтобы он не зависел от устаревания.

### Слайд 6. OAuth2 и bearer token в деталях

**Слайд:**
- OAuth2 — стандарт делегирования доступа, а не «просто пароль»
- Поток: клиент запрашивает токен → получает → шлёт с каждым запросом
- Токен имеет срок жизни (expires_in) и скоупы (scope) — права
- Тестировать: истечение токена, чужие скоупы, обновление (refresh token)
- В REST-assured токен подставляется в заголовок или через RequestSpecification

**Speaker notes:**

> OAuth2 — это стандарт делегирования доступа. Суть потока: клиент запрашивает токен у сервера авторизации, получает его и шлёт с каждым запросом в заголовке Authorization. Токен — это «пропуск» с ограниченным сроком и правами.
>
> Два ключевых свойства токена, которые нужно тестировать. Первое — срок жизни (expires_in): токен живёт ограниченное время, после истечения сервер должен вернуть 401. Тестируем, что происходит ровно на границе срока. Второе — скоупы (scope): токен выдаётся под конкретные права, например `read:cards`, но не `write:cards`. Тестируем: запрос с токеном без нужного скоупа должен вернуть 403.
>
> Есть ещё refresh token — долгоживущий токен для получения новых access-токенов. Тестируем цикл: access истёк → refresh → новый access.
>
> В REST-assured для чистоты токен обычно настраивают один раз в RequestSpecification — это переиспользуемый объект с общими настройками запроса (baseUrl, заголовки), который подставляется во все тесты. Не дублируем заголовок в каждом тесте.

### Слайд 7. Идемпотентность: определение

**Слайд:**
- Идемпотентность — повторный идентичный запрос даёт тот же результат без побочных эффектов
- GET, PUT, DELETE — идемпотентны по семантике HTTP
- POST — не идемпотентен по умолчанию: два POST создают два ресурса
- В финансовых системах идемпотентность критична: повторная отправка не должна списать деньги дважды
- В СМП: повторный POST /api/transactions с тем же STAN не должен дублировать транзакцию

**Speaker notes:**

> Идемпотентность — одно из самых важных понятий в API-тестировании, особенно в финансовых системах. Определение: операция идемпотентна, если повторный идентичный запрос даёт тот же результат без дополнительных побочных эффектов.
>
> По семантике HTTP: GET идемпотентен (сколько ни читай, ресурс не меняется), PUT идемпотентен (повторная замена даёт тот же итог), DELETE идемпотентен (повторное удаление — ресурс всё равно удалён). А вот POST не идемпотентен по умолчанию: два POST на `/api/cards` создадут две карты. Это мы уже затрагивали в лекции 9, когда разбирали семантику методов.
>
> Почему это критично в финансах? Представьте: клиент отправил запрос на оплату, сеть моргнула, ответ потерялся, клиент повторил запрос. Если операция не идемпотентна, деньги спишутся дважды. В процессинге это катастрофа.
>
> В СМП идемпотентность обеспечивается через STAN (System Trace Audit Number) — уникальный номер запроса. Повторный `POST /api/transactions` с тем же STAN должен вернуть тот же ответ, а не создать вторую транзакцию и не списать деньги повторно.
>
> Вопрос аудитории: почему именно STAN, а не PAN или amount, служит ключом идемпотентности? Что делает STAN уникальным?
>
> Ответ: PAN идентифицирует карту, а не конкретный запрос — по одной карте может быть много транзакций, и повторный запрос с тем же PAN — это законная другая покупка. Amount тоже не уникален: две разные покупки на одну сумму — норма. STAN же — это уникальный номер конкретного запроса, который клиент присваивает один раз и повторяет только при ретрае. Поэтому именно STAN позволяет отличить «повторную отправку того же запроса» от «нового запроса».

### Слайд 8. Почему POST /api/transactions нуждается в идемпотентности

**Слайд:**
- Сетевые сбои, таймауты, ретраи — причины повторной отправки
- Клиент не знает: дошёл ли первый запрос, или ответ потерялся по пути
- Без идемпотентности повторный запрос = двойное списание
- В СМП: STAN — ключ дедупликации, RRN — результат первой обработки
- Тест: два POST с одним STAN → одинаковый RRN, баланс списан один раз

**Speaker notes:**

> Почему эта проблема вообще возникает? Сетевые сбои, таймауты, автоматические ретраи. Клиент отправил запрос, не дождался ответа (таймаут) и повторил. Он не знает: первый запрос дошёл и обработался, но ответ потерялся, или не дошёл вовсе.
>
> Если операция не идемпотентна, получаем двойное списание. Решение — ключ дедупликации. В СМП это STAN: уникальный номер, который клиент присваивает запросу. Если сервер видит STAN, который уже обрабатывал, он возвращает результат первой обработки, а не выполняет операцию заново.
>
> Как это выглядит в тесте. Отправляем `POST /api/transactions` со STAN=000001, получаем RRN=012345678901 и APPROVED. Отправляем тот же запрос снова. Ожидаем: тот же RRN, и баланс карты списан ровно один раз, а не дважды.
>
> Вопрос аудитории: что проверять, чтобы убедиться, что деньги списаны один раз? Подсказка: это требует второго запроса — какого?
>
> Ответ: второго GET-запроса к карте. После двух POST с одним STAN делаем `GET /api/cards/{pan}` и сверяем баланс. Если он равен «начальный минус одна сумма транзакции», значит списание произошло один раз. Если «минус две суммы», идемпотентность нарушена. Это тот же приём цепочки запросов из лекции 9: операция меняет состояние, а проверяем мы его отдельным запросом.

### Слайд 9. Тестирование идемпотентности

**Слайд:**
```java
@Test
void shouldBeIdempotentForSameStan() {
    String requestBody = transactionJson(pan, "000001", 150000L);

    // Первый запрос
    String firstRrn = given()
        .contentType(ContentType.JSON)
        .body(requestBody)
    .when()
        .post("/api/transactions")
    .then()
        .statusCode(200)
        .body("status", equalTo("APPROVED"))
        .extract().path("rrn");

    // Повторный запрос с тем же STAN
    String secondRrn = given()
        .contentType(ContentType.JSON)
        .body(requestBody)
    .when()
        .post("/api/transactions")
    .then()
        .statusCode(200)
        .extract().path("rrn");

    // RRN должен совпасть — это результат первой обработки
    assertEquals(firstRrn, secondRrn);

    // Баланс списан один раз
    given()
    .when()
        .get("/api/cards/" + pan)
    .then()
        .statusCode(200)
        .body("availableBalance", equalTo(initialBalance - 150000L));
}
```
- Два запроса с одним STAN → одинаковый RRN
- Финальная проверка: баланс уменьшен ровно один раз

**Speaker notes:**

> Вот конкретный тест идемпотентности. Логика трёхшаговая.
>
> Первый шаг — отправляем запрос с STAN=000001, извлекаем RRN из ответа. Второй шаг — отправляем точно тот же запрос с тем же STAN. Третий шаг — две проверки.
>
> Проверка первая: `firstRrn` равен `secondRrn`. Если RRN совпал, сервер вернул результат первой обработки, а не создал новую транзакцию. Это главный сигнал идемпотентности.
>
> Проверка вторая — баланс. `GET /api/cards/{pan}` и проверяем, что `availableBalance` равен `initialBalance - 150000`, то есть сумма списана ровно один раз. Если бы сервер обработал запрос дважды, баланс был бы `initialBalance - 300000`.
>
> С точки зрения тест-дизайна этот тест проверяет идемпотентность на двух уровнях — на уровне API (совпадение RRN) и на уровне данных (одно списание). Одно без другого недостаточно: RRN может совпасть, а деньги всё равно списаться дважды из-за бага в логике резервирования. Выбор тестовых данных опирается на граничный случай: сумма транзакции меньше баланса, но если повторить — уже превысит остаток. Поэтому тест с одним списанием и двумя списаниями даёт разный результат, и проверка баланса их различает.

### Слайд 10. Асинхронные контракты в СМП

**Слайд:**
- Синхронный контракт: запрос → ответ (HTTP)
- Асинхронный контракт: публикация → очередь → потребление (RabbitMQ)
- В СМП: Switch публикует транзакцию в exchange `smp.transactions` (routing key `transaction.log`)
- Logger потребляет из очереди `transaction-log` и сохраняет в PostgreSQL
- Проблема тестирования: нет немедленного ответа

**Speaker notes:**

> До сих пор мы говорили о синхронных HTTP-контрактах: запрос и сразу ответ. Но в СМП есть вторая половина — асинхронные контракты через RabbitMQ, брокер сообщений.
>
> RabbitMQ — это посредник: publisher публикует сообщение в обменник (exchange), брокер маршрутизирует его в очередь (queue) по routing key, consumer забирает из очереди и обрабатывает. Ключевые понятия: exchange — точка приёма сообщений, queue — буфер ожидания, routing key — правило маршрутизации.
>
> В СМП конкретно: Switch публикует транзакцию в exchange `smp.transactions` (тип topic) с routing key `transaction.log`. Logger слушает очередь `transaction-log` через `@RabbitListener`, забирает сообщение и сохраняет в PostgreSQL. Это тот самый асинхронный путь, который мы упоминали в лекции 5, когда описывали архитектуру СМП.
>
> Почему это усложняет тестирование? В синхронном HTTP мы отправили запрос и сразу получили ответ. В асинхронном — отправили сообщение, а когда его обработают, неизвестно. Ответа нет, есть только факт «сообщение опубликовано». Значит, тест должен ждать и опрашивать.

### Слайд 11. Eventual consistency и Awaitility

**Слайд:**
- Eventual consistency — система станет согласованной, но не сразу
- В СМП: транзакция APPROVED, но в Logger запись появится через мгновение
- Нельзя `Thread.sleep(5000)` — это хрупко и медленно
- Awaitility — библиотека активного ожидания условия
- Паттерн: опрашивать каждые N мс, максимум M секунд

**Speaker notes:**

> Ключевое понятие — eventual consistency, согласованность в конечном счёте. Система не приходит в согласованное состояние мгновенно, но гарантирует, что придёт через некоторое время. В СМП: Gateway вернул APPROVED, но запись в Logger появится в базе чуть позже, когда сообщение пройдёт очередь и обработается.
>
> Как тестировать? Антипаттерн — `Thread.sleep(5000)`: «поспать пять секунд и надеяться». Почему плохо? Если сообщение обработалось за 200 миллисекунд, мы теряем почти пять секунд впустую на каждом тесте. Если обработка заняла шесть секунд под нагрузкой, тест упадёт ложно, хотя система работает. Sleep хрупок и медлен.
>
> Правильный паттерн — активное ожидание. Библиотека Awaitility делает именно это: «каждые 500 миллисекунд проверяй условие, максимум десять секунд, как только условие истинно — продолжай». Тест проходит ровно тогда, когда условие выполнено, без лишних пауз и без ложных падений.
>
> Это перекликается с тем, что мы обсуждали в лекции 6 про ожидание готовности сервисов в smoke-тесте: и там, и тут мы боремся с асинхронностью старта и обработки, только там — на уровне инфраструктуры, а здесь — на уровне бизнес-сообщений.

### Слайд 12. Тест асинхронного контракта

**Слайд:**
```java
@Test
void shouldEventuallyConsumeTransaction() {
    String rrn = sendTransactionAndGetRrn();

    await().atMost(10, TimeUnit.SECONDS)
        .pollInterval(500, TimeUnit.MILLISECONDS)
        .untilAsserted(() -> {
            given()
            .when()
                .get("/api/transactions/search?rrn=" + rrn)
            .then()
                .statusCode(200)
                .body("total", equalTo(1));
        });
}
```
- Awaitility опрашивает Logger каждые 500 мс до 10 секунд
- Тест проходит, как только транзакция появилась в поиске
- Failure modes: недоступность RabbitMQ, потеря сообщения, дублирование

**Speaker notes:**

> Вот тест асинхронного контракта. Отправляем транзакцию, получаем RRN. Затем Awaitility опрашивает Logger через `GET /api/transactions/search?rrn=...` каждые 500 миллисекунд, максимум десять секунд. Как только `total=1`, тест проходит.
>
> Это покрывает happy path асинхронного контракта. Но тестировщик должен проверять и режимы отказа (failure modes).
>
> Первое: RabbitMQ недоступен при публикации. По ТЗ Switch, если Publisher Confirms не получен за две секунды, Switch откатывает резервирование через reversal (mti=0400) и возвращает клиенту DECLINED с responseCode 96 (System Error). Гарантия: ни одна транзакция не будет APPROVED без записи в очереди. Это бизнес-правило нужно тестировать.
>
> Второе: потеря сообщения при рестарте брокера. Третье: дублирование — брокер может доставить сообщение дважды (семантика at-least-once), и Logger должен быть идемпотентным: не создавать дубликат по тому же RRN. Заметьте: идемпотентность, которую мы разбирали на слайдах 7–9, здесь возвращается уже на стороне потребителя сообщений — это ещё один её контекст.
>
> Вопрос аудитории: как в тесте смоделировать недоступность RabbitMQ? Какие инструменты позволяют контролируемо «ронять» внешние зависимости?
>
> Ответ: есть два подхода. Первый — интеграционный: остановить контейнер RabbitMQ через Docker в тесте и проверить поведение системы. Второй — изоляционный: использовать заглушку (например, WireMock для HTTP или тестовый брокер), которая имитирует отказ. В реальных проектах для контролируемых отказов часто применяют специальные инструменты fault injection, которые мы затронем в модуле 6 при интеграционном тестировании.

### Слайд 13. Продвинутые паттерны: пагинация и фильтры

**Слайд:**
- Пагинация: limit (сколько вернуть) и offset (сколько пропустить)
- Классы эквивалентности limit: валидные (1–100), 0, отрицательные, больше 100
- Фильтры поиска: status, pan, merchantId, declineReason
- Поиск с нулевым результатом — это 200 с пустым списком, а не 404
- JSONPath `transactions.size()` — проверить размер массива

**Speaker notes:**

> Два практических паттерна, которые часто встречаются в API. Пагинация — разбиение большого списка на страницы. Без неё `GET /api/transactions/search` при миллионе транзакций вернул бы миллион записей и уронил бы сервер.
>
> Параметры: limit (сколько записей вернуть, по умолчанию 50) и offset (сколько пропустить). Тест-дизайн через классы эквивалентности для limit: валидные значения (1, 50, 100), граница 0, отрицательные (−1 → 400), больше максимума (150 → 400 или ограничение). Каждый класс — свой тест. Здесь же применяются граничные значения: 0 и 100 — это ровно границы валидного диапазона. Это прямая связка с техниками из модуля 2.
>
> Фильтры поиска — параметры, сужающие выборку. В СМП: status, pan, merchantId, declineReason. Важный кейс: поиск с нулевым результатом, например PAN из 16 нулей. Ожидаем 200 с `total=0` и пустым массивом. Это не 404: код 404 значит «эндпоинт не существует», а пустой результат — нормальный ответ на существующий запрос. Это различение статус-кодов из лекции 9.
>
> JSONPath `transactions.size()` возвращает количество элементов в массиве — проверяем, что оно не превышает limit.

### Слайд 14. Интерактив: спроектируйте тест-кейсы

**Слайд:**
- Дано: эндпоинт POST /api/transactions, алгоритм авторизации с шестью declined-ветками
- Вопрос 1: сколько минимум тест-кейсов нужно для покрытия всех declined-веток? Перечислите их.
- Вопрос 2: тест на идемпотентность падает раз в пять прогонов. Какие гипотезы?
- Вопрос 3: как проверить, что транзакция не появилась в Logger при недоступности RabbitMQ?
- Обсуждение: 2–3 минуты на вопрос

**Speaker notes:**

> Финальный интерактив — три вопроса на проектирование тест-кейсов.
>
> Вопрос 1: минимум declined-тестов. По алгоритму авторизации шесть веток: карта не найдена (14), INACTIVE, BLOCKED, EXPIRED (54), дневной лимит (61), месячный лимит, недостаточно средств (51). Плюс happy path. Минимум семь тестов — по одному на ветку. Но статус карты даёт несколько значений: INACTIVE, BLOCKED, EXPIRED — это три разных класса, плюс карта не найдена — четвёртый. Итого с happy path минимум восемь тестов. Это классическое применение классов эквивалентности: каждый класс статуса карты — свой тест.
>
> Вопрос 2: идемпотентность падает раз в пять прогонов. Гипотезы: STAN не уникален — тест генерирует одинаковый STAN для разных прогонов, и предыдущая транзакция «всплывает»; гонка данных — параллельный тест меняет ту же карту; баланс карты не изолирован — предыдущий тест оставил карту в непредсказуемом состоянии. Диагностика: изолировать тестовые данные, уникализировать STAN на каждый прогон. Здесь работает приоритизация гипотез — начинаем с самой вероятной. Это ровно та же дисциплина диагностики, что мы обсуждали в лекции 6 на примере flaky smoke-тестов.
>
> Вопрос 3: транзакция не появилась в Logger при недоступности RabbitMQ. Это негативный тест асинхронного контракта. Моделируем отказ брокера, отправляем транзакцию, проверяем: клиент получил DECLINED + responseCode 96, резервирование откатано (баланс не изменился), и в Logger записи нет. Проверяем через Awaitility «наоборот»: ждём несколько секунд и убеждаемся, что запись не появилась.
