## Условие

Дана система массового процессинга — одиннадцать микросервисов, объединённых единой точкой входа Gateway, с контрактами, зафиксированными в спецификации и реализованными в коде. Спецификация и реализация в ряде мест расходятся.

Требуется разработать набор API-тестов, который проверяет контракты СМП и обнаруживает их нарушение. Нарушением считается любое изменение наблюдаемого поведения, противоречащее контракту: состав и формат тела ответа, значение статус-кода, доменный код и причина отказа, допустимые значения параметров, эффекты, которые запрос оставляет в системе.

Тесты исполняются на поднятом стеке по команде, не требующей ручных шагов, и запускаются в CI автоматически. Способ организации — выделенный модуль, тесты внутри сервиса или собственный пайплайн — определяется исполнителем; проверяется воспроизводимость запуска.

Область работы ограничена синхронными HTTP-контрактами. Тестирование взаимодействия с PostgreSQL и RabbitMQ в контейнерах относится к модулю 6.

## Технологический стек

Работа выполняется на том же стеке, что и сервисы СМП: Java 21, Maven, JUnit 5. Отступление от стека допускается только по согласованию и с сохранением всех требований к приёмам.

| Компонент | Назначение | Обязательность |
|---|---|---|
| Java 21 | язык тестов, совпадает с версией сервисов | обязательно |
| Maven | сборка и запуск, профили `services/pom.xml` | обязательно |
| JUnit 5 (`org.junit.jupiter`) | фреймворк тестов, параметризация, жизненный цикл | обязательно |
| REST-assured (`io.rest-assured`) | HTTP-клиент с DSL `given/when/then` | обязательно |
| Hamcrest (`org.hamcrest`) | матчеры для проверок тела ответа | обязательно |
| Awaitility (`org.awaitility`) | ожидание асинхронного условия | обязательно |
| Jackson (`com.fasterxml.jackson`) | сборка тел запросов и разбор ответов | по потребности |
| JSON Schema Validator (`io.rest-assured:json-schema-validator`) | валидация ответа против схемы | по потребности |
| Docker Compose | подъём стека СМП перед прогоном | обязательно |

Версии фиксируются в `pom.xml` проекта. Ориентир, согласованный с существующими модулями репозитория: REST-assured 5.4.0, Awaitility 4.2.2, TestNG 7.10.2 — последний **не используется**, приведён как справка о том, что уже есть в проекте.

## Приёмы и паттерны, подлежащие демонстрации

Наличие приёма в коде проверяется на защите: требуется показать место в коде и объяснить, зачем он применён. Приёмы не заменяют полноту покрытия — оба требования проверяются независимо.

### Структура и организация

| Приём | Требование | Зачем |
|---|---|---|
| `given / when / then` | каждый тест разделён на три визуально различимых блока | читаемость, соответствие структуре тест-кейса |
| `RequestSpecification` | базовый адрес и общие заголовки заданы один раз | отсутствие дублирования в каждом тесте |
| Группировка по эндпоинтам | тесты разделены по классам, соответствующим доменам | точечный запуск, читаемость сьюта |
| Support-слой | билдеры тел запросов и фабрики данных вынесены отдельно от проверок | переиспользование без потери читаемости |

### Работа с данными

| Приём | Требование | Зачем |
|---|---|---|
| `@ParameterizedTest` | минимум два теста используют параметризацию (`@ValueSource`, `@CsvSource` или `@MethodSource`) | один метод на класс эквивалентности |
| Уникальные данные на тест | каждый тест создаёт свои идентификаторы (UUID, STAN, PAN) | изоляция, отсутствие flaky |
| Подготовка данных через API | состояние системы меняется только запросами, не прямым доступом к БД | тест проверяет контракт, а не обходит его |
| Известное начальное состояние | баланс, лимиты и статус карты задаются явно | воспроизводимость ожидаемых значений |

### Проверки

| Приём | Требование | Зачем |
|---|---|---|
| Проверка тела, а не только статуса | для каждого кода `2xx` и `4xx` проверяется содержимое ответа | отличать свою ошибку от чужой |
| `matchesPattern` для генерируемых значений | `rrn`, `authCode` и подобные проверяются на формат, а не на точное значение | значения непредсказуемы, но формат — часть контракта |
| Проверка отсутствия значения | необязательные поля проверяются через `nullValue()` | отличие `null` от отсутствующего поля |
| Композитные матчеры | используются `equalTo`, `oneOf`, `hasSize`, `greaterThanOrEqualTo`, `notNullValue` | выразительность и информативность падений |

### Работа с массивами и фильтрами

| Приём | Требование | Зачем |
|---|---|---|
| GPath-фильтр | минимум один тест отбирает запись внутри ответа: `transactions.findAll { ... }` | проверка привязана к объекту теста, а не ко всей выборке |
| Проверка размера | размер массива проверяется через `hasSize` или `size()` | контроль пагинации и результатов поиска |

### Асинхронность

| Приём | Требование | Зачем |
|---|---|---|
| `Awaitility` | ожидание условия через `await().atMost(...).pollInterval(...).untilAsserted(...)` | вместо фиксированной паузы |
| Ожидание отсутствия | отдельный тест проверяет, что эффект **не** наступил | откат и негативные сценарии |
| Явные границы ожидания | `atMost` и `pollInterval` заданы осознанно, а не «побольше» | предсказуемое время прогона |

### Работа с контрактом

| Приём | Требование | Зачем |
|---|---|---|
| Валидация по схеме | минимум один тест использует `matchesJsonSchemaInClasspath` или эквивалент | дешёвая проверка формата целиком |
| Ссылка на источник ожидания | в комментарии или имени теста указано, откуда взято ожидаемое значение | обоснованность проверки |
| Проверка заголовков | минимум один тест проверяет заголовок ответа (`X-Cache`, `Content-Type`, `Retry-After`) | заголовки — часть контракта |

### Негативные сценарии

| Приём | Требование | Зачем |
|---|---|---|
| Один невалидный класс — один тест | невалидные значения не смешиваются в одном запросе | локализация причины отказа |
| Проверка текста ошибки | поле сообщения проверяется там, где оно часть контракта | формулировка видна потребителю |
| Проверка принадлежности отказа | определяется, какой сервис вернул ошибку | в микросервисах это критично для диагностики |

### Доказательство работоспособности тестов

| Приём | Требование | Зачем |
|---|---|---|
| Намеренная поломка | минимум три теста проверены на способность падать | тест, который не падал, не проверен |
| Мутационная проверка | для теста идемпотентности — отключение дедупликации и проверка, что тест краснеет | проверка проверок |

## Требования к полноте покрытия

Требования ниже задают границы, но не перечень проверок. Конкретный состав тестов, значения и ожидаемые результаты определяются самостоятельно — на основе спецификации, кода и техник тест-дизайна из модуля 2.

**1. Полнота по эндпоинтам.** Покрываются все эндпоинты, доступные через Gateway, а также внутренние эндпоинты, участвующие в цепочке авторизации и логирования. Перечень составляется самостоятельно из трёх источников: спецификации, контроллеров сервисов и конфигурации маршрутов Gateway. Источники не совпадают между собой — расхождения подлежат фиксации.

**2. Полнота по статус-кодам.** Для каждого эндпоинта покрываются все статус-коды, которые он способен вернуть, а не только успешный. Основание — код обработки и раздел ошибок в спецификации.

**3. Полнота по бизнес-отказам.** Покрывается каждый исход отказа, предусмотренный алгоритмом авторизации. Для каждого исхода проверяются и доменный код, и причина отказа: часть исходов имеет совпадающие коды, и проверка только кода их не различает.

Отдельно учитывается, что один и тот же исход может достигаться разными путями — через состояние карты и через данные запроса. Проверяются оба пути, различие между ними объясняется.

**4. Полнота по валидации.** Покрывается каждое правило проверки входного запроса: формат и длина полей, числовые ограничения, обязательность. По каждому правилу используются классы эквивалентности и граничные значения; для каждого нарушения проверяется не только статус-код, но и тело ошибки — из него должно следовать, какое поле и какое правило нарушены.

**5. Полнота по параметрам запроса.** Покрываются все параметры фильтрации и пагинации. Для каждого параметра проверяются допустимые значения и границы; для комбинаций применяется попарное покрытие. Отдельно проверяется случай пустой выборки и поведение при некорректной комбинации параметров.

**6. Полнота по повторной доставке.** Проверяются все исходы повторной обработки одного и того же сообщения, включая случай совпадения ключа при расхождении данных.

**7. Асинхронные эффекты.** Проверяется как появление эффекта в системе, так и его отсутствие при откате. Проверка отсутствия требует отдельного подхода и не сводится к проверке наличия.

**8. Сквозная проверка.** Проверяется, что транзакция, отправленная через Gateway, достигает хранилища и становится доступной для поиска.

**9. Обоснование достаточности.** В отчёте приводится обоснование, почему предложенный набор достаточен: какие классы входных данных выделены, чем подтверждена их полнота, что осознанно оставлено вне покрытия и по какой причине.

Ориентир по объёму: набор, закрывающий перечисленные требования, содержит несколько десятков проверок. Точное число определяется составом классов, а не назначается.

## Расхождения контракта и реализации

Расхождения между спецификацией и кодом подлежат выявлению, экспериментальной проверке и описанию: какое поведение декларировано, какое наблюдается, какой источник следует считать верным и насколько расхождение значимо для потребителя.

Приведение теста в соответствие с наблюдаемым поведением без фиксации самого расхождения не допускается: расхождение либо оформляется как дефект, либо признаётся известным ограничением с обоснованием.

## Требования к результату

Помимо полноты покрытия оценивается осмысленность проверок.

| Требование | Признак нарушения |
|---|---|
| Тест проверяет поведение, а не факт ответа | проверяется только статус-код, тело не проверяется |
| Тест привязан к созданным им данным | константные идентификаторы, общие между тестами |
| Тест изолирован | зависит от порядка запуска или данных другого теста |
| Тест способен падать | не был красным ни разу за время работы |
| Асинхронный эффект проверяется ожиданием условия | используется фиксированная пауза |
| Ожидания обоснованы источником | значение взято «по интуиции», без ссылки на контракт или код |

В отчёте приводится не менее трёх примеров намеренного нарушения ожидания или поведения системы с подтверждением, что соответствующий тест стал красным.

## Критерии приёмки

- [ ] Покрыты все эндпоинты из трёх источников; расхождения между источниками зафиксированы
- [ ] Для каждого эндпоинта покрыты все возможные статус-коды
- [ ] Покрыт каждый исход бизнес-отказа: код и причина проверяются совместно
- [ ] Для исходов, достижимых разными путями, проверены оба пути
- [ ] Покрыто каждое правило валидации, с классами эквивалентности и границами
- [ ] Покрыты все параметры фильтрации и пагинации, включая пустую выборку
- [ ] Покрыты все исходы повторной доставки
- [ ] Проверен асинхронный эффект: и появление, и отсутствие
- [ ] Проверена сквозная цепочка от Gateway до хранилища
- [ ] Тесты запускаются одной командой и автоматически в CI
- [ ] Три последовательных прогона не дают падений
- [ ] Использован предписанный стек: Java 21, Maven, JUnit 5, REST-assured, Hamcrest, Awaitility
- [ ] Продемонстрированы все приёмы из разделов «Структура», «Данные», «Проверки», «Асинхронность», «Контракт»
- [ ] `RequestSpecification` используется, базовый адрес не дублируется в тестах
- [ ] Минимум два параметризованных теста
- [ ] Минимум один GPath-фильтр и одна проверка заголовка
- [ ] Асинхронность проверяется через Awaitility, фиксированных пауз нет
- [ ] В отчёте есть обоснование достаточности набора
- [ ] В отчёте описаны выявленные расхождения с классификацией
- [ ] В отчёте приведены доказательства способности тестов падать

Артефакт считается сданным только при наличии всех компонентов.
