## Зачем эта практика

Прежде чем писать unit-, API-, интеграционные и E2E-тесты (модули 4–7), нужно понимать систему целиком: из чего она состоит, кто с кем взаимодействует и **каким способом — синхронно (HTTP) или асинхронно (RabbitMQ)**. Это знание добывается **из кода**, это практика white-box: источник истины — [`services/`](../../../Practic-SMP/services/).

## Задание

### (а) Карта системы — 6 диаграмм

Построить/верифицировать 6 диаграмм. Для каждой — явно указать, **чего не хватает в текущем проекте** и что вы сделали. Каждая диаграмма должна быть **подтверждена кодом** (ссылки на классы/файлы).

| № | Диаграмма | Чего не хватает в проекте | Что требуется |
|---|---|---|---|
| А1 | C4 Level 1 — Context | отсутствует полностью | границы СМП и внешние акторы: терминал, мерчант/эквайрер, пользователь дашборда, внешний BIN Lookup; протокол входа каждого |
| А2 | C4 Level 2 — Container | есть (`architecture-diagram.puml` + mermaid), но **не размечены sync/async**; async-связи (outbox, publisher confirms) не отражены; не сверены с `docker-compose.yaml` | 11 сервисов + PostgreSQL + RabbitMQ; явно разметить **sync (HTTP/JDBC) vs async (AMQP)** с exchange/queue |
| А3 | C4 Level 3 — Component (Authorization, Card-Management) | отсутствует | внутренняя структура: controller → service → client/repository; где HTTP-клиенты, JDBC, outbox-публикация |
| А4 | Sequence | есть только happy path | полный путь транзакции в трёх сценариях: **happy path + declined + reversal (mti 0400)**; где синхронный вызов, где асинхронная «вилка» |
| А5 | RabbitMQ-топология | описана текстом/таблицей, но **не визуализирована** | exchange → queue → consumer, DLX/DLQ, publisher confirms (2s), retry (3 попытки, TTL 60s) |
| А6 | State-transition | отсутствует | состояния `Card.status` (ACTIVE/INACTIVE/BLOCKED/EXPIRED) и жизненный цикл Transaction (APPROVED/DECLINED/ROLLED_BACK) |

**Где брать материал для проверки**: [`services/`](../../../Practic-SMP/services/), [`docs/api-spec.md`](../../../Practic-SMP/docs/api-spec.md), [`docs/architecture.md`](../../../Practic-SMP/docs/architecture.md), [`tz/`](../../../Practic-SMP/tz/).

### (б) Новые тест-кейсы — 10+

Подготовить **не менее 10 тест-кейсов** на разных уровнях пирамиды. **Структура тест-кейса — строго из модуля 2** (как в артефакте 2), плюс обязательная колонка **«Уровень пирамиды»**:

| ID | Связанное требование | Уровень пирамиды | Вид | Предусловие | Шаги | Ожидаемый результат | Источник |

Требования:
- покрыть **минимум три уровня** (`unit` / `api` / `integration` / `e2e`);
- обязательно покрыть **sync** (валидация, маршрутизация по BIN, лимиты/баланс, CRUD, резервирование) и **async** (доставка в Logger, publisher-confirm + reversal, outbox → Notification, eventual consistency) пути;
- уровень выбирается по принципу «самый низкий, который адекватно проверяет сценарий»;
- «Источник» заполняется по модулю 2: класс эквивалентности / граничное значение / контракт / сценарий / состояние БД.

### (в) Распределение тест-кейсов практики 2

Взять тест-кейсы из `docs/practice-2/test-design.md` и для каждого определить уровень пирамиды. Для каждого явно указать **«что проверяет тест»** и обоснование уровня:

| ID (пр. 2) | Название | Что проверяет тест | Уровень | Обоснование |

Ключевой вопрос — что именно проверяется: чистая логика (unit), контракт (api), связь с БД/очередью (integration), сквозной сценарий (e2e).

### (г) Анализ пропорций — 20+ тест-кейсов

Свести старые и новые кейсы в таблицу и посчитать доли:

| Уровень | Старые | Новые | Итого | Доля |
|---|---:|---:|---:|---:|
| unit | | | | |
| api / integration | | | | |
| e2e | | | | |
| **Итого** | | | **20+** | 100% |

**Важно**: итоговая пирамида **не обязана совпадать с ориентиром 70/20/10** — это ориентир, а не догма. В enterprise-микросервисах доля api/integration часто выше. Задача — **объяснить, почему у вас получилось именно так**: чем вызвано смещение (плотные контракты, риск интеграций, мало критичных сквозных сценариев), и нет ли риска ice-cream cone (перекоса в E2E) или, наоборот, дефицита контрактных проверок.

## Ограничение на использование LLM

LLM **запрещено использовать для генерации диаграмм и тест-кейсов**: цель практики — ваше собственное понимание структуры кода. Допустимо ограниченное использование LLM только как **справочника по синтаксису PlantUML/mermaid** — и только после того, как вы сами определили, что и зачем рисовать. Любое утверждение о системе (связь, компонент, состояние) должно иметь ссылку на код, и на защите вы обязаны его объяснить.

## Критерии приёмки

- [ ] Присутствуют все 6 диаграмм, каждая со ссылками на классы/файлы кода
- [ ] Для каждой диаграммы указано, чего не хватало в проекте и что улучшено
- [ ] Связи размечены sync (HTTP/JDBC) / async (AMQP)
- [ ] Sequence покрывает happy path, declined и reversal (0400)
- [ ] Новых ТК ≥ 10, структура — из модуля 2 + колонка «Уровень пирамиды», покрыты sync и async
- [ ] Распределение старых ТК — с обоснованием «что проверяет тест»
- [ ] Анализ пропорций — таблица долей + объяснение, почему пирамида такая (а не формальная подгонка под 70/20/10)
- [ ] Студент способен объяснить каждую диаграмму и выбор уровня каждого ТК на защите

## Типичные ошибки

| Ошибка | Следствие |
|---|---|
| Диаграмма пересказывает documentation, а не код | не отражает реализацию |
| Async нарисован как sync | пропущены риски очередей/DLQ |
| Уровень ТК без обоснования | нельзя проверить корректность выбора |
| Подгонка пропорций под 70/20/10 без объяснения | формальный анализ, нет понимания |
| Диаграммы/ТК сгенерированы LLM | нет собственного понимания — не защитить |
