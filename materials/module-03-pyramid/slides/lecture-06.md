Нас как тестировщиков интересует в первую очередь CI — автоматический запуск тестов по каждому изменению.

### Слайд 2. Зачем тестировщику CI/CD

**Слайд:**
- Тесты без автоматического запуска — мёртвый код
- CI — это машина, которая запускает пирамиду по каждому изменению
- Быстрая обратная связь = дешёвое исправление (правило 1:10:100)
- CI/CD — не «инструмент девопса», а условие существования автоматизации тестирования
- В СМП: GitHub Actions запускает линтеры, сборку и тесты по каждому push

**Speaker notes:**

> Почему тестировщику важно понимать CI/CD? Потому что тесты, которые никто не запускает автоматически, — мёртвый код. Пирамида тестирования, которую мы разобрали на прошлой лекции, живёт только внутри пайплайна.
>
> CI — это машина, которая по каждому изменению запускает всю пирамиду: unit, API, E2E. Если тесты не запускаются автоматически, разработчик их просто не гоняет, и регрессия накапливается.
>
> Быстрая обратная связь — это деньги. Вспомним правило 1:10:100: чем раньше пойман дефект, тем дешевле исправление. CI даёт обратную связь за минуты, а не за дни ручного прогона.
>
> В СМП CI реализован на GitHub Actions: по каждому push в любую ветку запускаются линтеры, сборка всех сервисов и unit-тесты. Этот пайплайн мы детально разберём в конце лекции.

### Слайд 3. Инструменты CI/CD: обзор

**Слайд:**
- GitHub Actions — встроен в GitHub, YAML-пайплайны, бесплатен для публичных репозиториев
- GitLab CI — встроен в GitLab, `.gitlab-ci.yml`, мощные stage-графы
- Jenkins — open-source, гибкий через плагины, требует собственного сервера
- TeamCity — коммерческий от JetBrains, удобен для JVM-проектов, богатые отчёты
- Выбор зависит от того, где живёт код и какие нужны интеграции

**Speaker notes:**

> Прежде чем разбирать пайплайн СМП, посмотрим на ландшафт инструментов CI/CD, потому что в разных компаниях он разный, и вам нужно уметь выбирать.
>
> GitHub Actions — система, встроенная прямо в GitHub. Пайплайны описываются YAML-файлами в папке `.github/workflows`. Для проектов на GitHub это самый простой старт: ничего не надо ставить, раннеры предоставляет GitHub. Именно его мы используем в СМП.
>
> GitLab CI — аналог от GitLab, пайплайн описывается в `.gitlab-ci.yml`. Отличается тем, что позволяет строить наглядные графы стадий с ручными шагами-гейтами, это удобно, когда нужны промежуточные ручные одобрения перед выкаткой.
>
> Jenkins — старейший open-source сервер CI. Он очень гибкий за счёт тысяч плагинов, но эту гибкость нужно обслуживать: Jenkins обычно требует собственный сервер, администрирование и следить за обновлениями. Его выбирают, когда нужен полный контроль над инфраструктурой.
>
> TeamCity — коммерческий продукт JetBrains, той же компании, что делает IntelliJ IDEA. Особенно удобен для JVM-проектов: глубоко понимает Java, Maven, Gradle, умеет строить красивые отчёты по тестам и сборкам из коробки. В enterprise, где стек Java, TeamCity часто выбирают за готовую интеграцию и стабильность.
>
> Как выбирать? Смотрите на три вещи: где живёт репозиторий (GitHub → Actions, GitLab → GitLab CI), какой стек (JVM → TeamCity удобен), и сколько готовы инвестировать в инфраструктуру (Jenkins требует больше всего). В СМП выбор очевиден: код на GitHub, значит GitHub Actions.
>
> Вопрос аудитории: слышали ли вы о каком-нибудь из этих инструментов? В каких компаниях, по вашему опыту, что используют?
>
> Ответ-обобщение: в open-source и стартапах чаще GitHub Actions и GitLab CI из-за простоты и низкого порога входа. В крупном enterprise с историей — Jenkins и TeamCity, потому что они давно внедрены, а миграция дорога. Важно не название инструмента, а принципы: пайплайн как код, автоматический запуск по изменению, читаемые отчёты.

### Слайд 4. Пайплайн как код

**Слайд:**
- Пайплайн описывается файлом в репозитории, а не настройками в UI
- Это значит: пайплайн версионируется, ревьюится и воспроизводится
- Примеры файлов: `.github/workflows/ci.yml` (Actions), `.gitlab-ci.yml` (GitLab), `Jenkinsfile` (Jenkins)
- Изменение пайплайна идёт через обычный pull request
- Это устраняет проблему «настройки живут только в голове админа»

**Speaker notes:**

> Общий принцип всех современных инструментов CI/CD — пайплайн как код. Это значит, что конфигурация пайплайна хранится в файле внутри репозитория, а не задаётся кликами в веб-интерфейсе.
>
> Почему это важно? Пайплайн становится обычным кодом: он версионируется, его можно ревьюить через pull request, его можно воспроизвести на другой машине. Если кто-то сломал пайплайн — видно, кто и когда, и можно откатить. Если пайплайн живёт только в настройках UI, то это знание в голове одного администратора, и потерять его очень просто.
>
> Форматы файлов у каждого инструмента свои: GitHub Actions — `.github/workflows/*.yml`, GitLab CI — `.gitlab-ci.yml`, Jenkins — `Jenkinsfile`. Но идея одна и та же: декларативно описать, что должно происходить после коммита.
>
> В СМП пайплайн описан в [`practic/.github/workflows/ci.yml`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/.github/workflows/ci.yml), и мы сейчас разберём его построчно.

### Слайд 5. Быстрая обратная связь — ключевой принцип

**Слайд:**
- Обратная связь = время от изменения кода до получения результата тестов
- Цель: чем короче цикл «изменил → узнал результат», тем лучше
- Pre-commit: секунды. CI: минуты. Nightly: часы
- Разработчик в потоке: пять–десять минут ожидания срывают контекст
- Быстрая обратная связь — не «приятный бонус», а экономическая необходимость

**Speaker notes:**

> Ключевой принцип CI — быстрая обратная связь. Это время от изменения кода до получения результата тестов. Цель — сделать этот цикл максимально коротким.
>
> Почему это экономически критично? Разработчик работает в состоянии потока. Если тесты идут двадцать минут, он переключился на другую задачу и потерял контекст. Когда тесты наконец упали, ему нужно заново погружаться в код, который он писал двадцать минут назад. Если тесты идут тридцать секунд, он ещё «в потоке» и чинит баг немедленно.
>
> Отсюда вытекает слоистая структура пайплайна: pre-commit (секунды), CI (минуты), nightly (часы). Каждый слой — свой компромисс между полнотой проверок и скоростью. Это напрямую связано с пирамидой: unit-тесты быстрые и идут в pre-commit, E2E-тесты медленные и идут в ночной прогон. Подробно эту связь мы разобрали на прошлой лекции.
>
> Вопрос аудитории: что произойдёт, если все тесты, включая E2E, гонять на каждый коммит? Оцените время и последствия.
>
> Ответ: прогон растянется до десятков минут или часов на каждый коммит. Разработчик будет ждать результат и терять поток, а CI-раннеры будут постоянно заняты. В итоге команда начнёт игнорировать пайплайн или пропускать его запуск — и автоматизация перестанет работать. Поэтому медленные тесты выносят в ночной прогон.

### Слайд 6. Пирамида как карта скоростей

**Слайд:**
- Unit-тесты: миллисекунды → pre-commit и CI
- API/интеграционные: сотни миллисекунд → CI
- E2E: секунды/минуты → nightly
- Пирамида = карта, какие тесты куда ставить по скорости
- Чем ниже уровень, тем раньше в пайплайне он запускается

**Speaker notes:**

> Пирамида тестирования — это одновременно карта скоростей для CI. Посмотрим на уровни через призму «сколько времени занимает прогон».
>
> Unit-тесты: миллисекунды. Тысяча штук — секунды. Их можно гонять на pre-commit, до отправки кода в репозиторий. API- и интеграционные тесты: сотни миллисекунд плюс поднятие контекста. Сотни штук — минуты. Их место в CI-пайплайне. E2E-тесты: секунды и минуты плюс полное окружение. Их место — в ночном прогоне, раз в сутки.
>
> Правило простое: чем ниже уровень теста, тем раньше в пайплайне он запускается. Чем выше — тем позже. Это и есть связь лекции 5 и лекции 6: пирамида определяет, что писать, а CI/CD — когда запускать.
>
> На следующем слайде разберём, что такое билд-пайплайн и из каких стадий он состоит.

### Слайд 7. Что такое билд-пайплайн

**Слайд:**
- Пайплайн — последовательность автоматических шагов от коммита до результата
- Стадии (stages): lint → build → unit-test → integration-test → deploy
- Каждая стадия — отдельный набор команд с чётким критерием успеха
- Стадии выполняются последовательно, но внутри могут распараллеливаться
- Упавшая стадия останавливает пайплайн — код не идёт дальше

**Speaker notes:**

> Билд-пайплайн — это последовательность автоматических шагов, которые выполняются после коммита. Каждый шаг называется стадией.
>
> Типичная цепочка: lint (проверка стиля кода) → build (компиляция) → unit-test (модульные тесты) → integration-test (интеграционные тесты) → deploy (развёртывание). Каждая стадия — отдельный набор команд с чётким критерием успеха: линтер прошёл без ошибок, сборка собралась, тесты зелёные.
>
> Ключевые свойства. Стадии выполняются последовательно — нельзя разворачивать то, что не собралось. Но внутри стадии работа может распараллеливаться: в СМП восемь сервисов собираются параллельно через matrix-стратегию. И главное: упавшая стадия останавливает пайплайн. Если линтер красный, сборка не запустится. Если unit-тесты упали, интеграционные не пойдут. Это принцип fail fast — ловить проблему как можно раньше.
>
> Вопрос аудитории: почему важно, чтобы упавшая стадия останавливала пайплайн, а не продолжала выполнение? Что будет, если игнорировать красные тесты?
>
> Ответ: если пайплайн продолжает работу после красной стадии, мы тратим ресурсы на запуск дорогих тестов поверх уже известной проблемы. Хуже того, команда привыкает видеть «красный, но продолжает» и перестаёт воспринимать падение как сигнал к действию. Возвращаемся к антипаттерну ice-cream cone из прошлой лекции: пайплайн перестаёт быть источником правды о качестве.

### Слайд 8. Что такое smoke-тесты

**Слайд:**
- Smoke-тест — минимальная проверка, что система «дымит», то есть запустилась и базово работает
- Термин из электроники: прибор включают и смотрят, не пошёл ли дым
- Проверяет критические пути, а не детальную логику
- В СМП: health-check всех сервисов, создание карты, одна транзакция
- Быстрый отсев: если smoke красный, гонять полный набор бессмысленно

**Speaker notes:**

> Отдельно остановимся на термине smoke-тест, потому что он будет встречаться дальше по курсу. Это важное понятие.
>
> Smoke-тест — это минимальная проверка того, что система вообще запустилась и базово работает. Термин пришёл из электроники: когда собирают прибор, его включают и смотрят, не пошёл ли дым. Если дым пошёл — дальше тестировать нечего. В тестировании аналогия прямая: если система не поднялась и не отвечает на базовые запросы, гонять полный набор бессмысленно.
>
> Чем smoke отличается от полного регресса? Smoke проверяет критические пути, а не детальную логику. Он отвечает на вопрос «система жива?», а не «все ли сценарии работают корректно?». Поэтому он быстрый — минуты, а не часы.
>
> В СМП smoke-скрипт (`scripts/smoke-test.sh`) проверяет три вещи: health-check всех сервисов (все ли отвечают), создание карты (работает ли база и Card Management), одну транзакцию (работает ли весь синхронный путь). Если хотя бы одна проверка падает — система не готова к дальнейшему тестированию.
>
> Мы встретим smoke-тесты ещё раз: в модуле 8 при нагрузочном smoke, и на практике 6, где вы будете настраивать CI-пайплайн. Пока запомните принцип: smoke — это дешёвый быстрый барьер на входе в тестирование.

### Слайд 9. Стадии пайплайна: что где запускать

**Слайд:**
- Pre-commit: линтеры + быстрые unit-тесты (секунды)
- CI (по push/PR): линтеры + сборка + все unit + API-тесты (минуты)
- Nightly: E2E + нагрузочные + миграции (часы)
- Принцип: каждая стадия — свой уровень пирамиды
- Быстрые тесты — часто, медленные — редко

**Speaker notes:**

> Сводим в единую схему. Pre-commit — это хук, который выполняется до того, как код попадёт в репозиторий. Там только линтеры и быстрые unit-тесты, всё, что укладывается в секунды. Это первый барьер.
>
> CI по push или pull request — основная проверка: линтеры, полная сборка, все unit-тесты, API-тесты. Это минуты. Здесь живёт основная масса проверок из пирамиды.
>
> Nightly — ночной прогон: E2E-тесты, нагрузочные, миграции данных. Часы. Раз в сутки.
>
> Принцип: быстрые тесты гоняем часто, медленные — редко. Не потому что медленные неважны, а потому что их стоимость запуска высока. Если E2E-тест идёт десять минут, а коммитов пятьдесят в день, это пятьсот минут машинного времени в день на одни E2E. Поэтому E2E уходит в ночь.
>
> Теперь посмотрим, как это конкретно устроено в СМП.

### Слайд 10. CI/CD в СМП: обзор пайплайна

**Слайд:**
- Инструмент: GitHub Actions (файл `.github/workflows/ci.yml`)
- Триггеры: push в любую ветку + pull request в main
- Фильтр по путям: пайплайн запускается только при изменении `services/**` и инфраструктуры
- Джобы: base-lint, build-common, java-services, frontend-dashboard, smoke-tests, e2e-tests
- Параллельность: восемь Java-сервисов собираются через matrix

**Speaker notes:**

> Посмотрим на реальный пайплайн СМП — файл [`practic/.github/workflows/ci.yml`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/.github/workflows/ci.yml). Он описан на GitHub Actions.
>
> Триггеры: push в любую ветку и pull request в main. Есть фильтр по путям — пайплайн запускается только когда меняются файлы в `services/**`, `docker-compose.yaml`, `docs/api/**`, скрипты. Это экономия: изменение README не должно гонять весь пайплайн.
>
> Джобы (jobs) — это независимые единицы работы: `base-lint` (пре-коммит хуки), `build-common` (сборка общего модуля), `java-services` (сборка и тесты каждого из восьми Java-сервисов), `frontend-dashboard` (сборка фронтенда), `smoke-tests` (поднятие всего стека и smoke-прогон), `e2e-tests` (сквозные тесты).
>
> Параллельность достигается через matrix — механизм GitHub Actions, который запускает один и тот же джоб для каждого значения из списка. Для восьми сервисов — восемь параллельных сборок вместо восьми последовательных.

### Слайд 11. Разбор ci.yml: порядок стадий

**Слайд:**
```yaml
jobs:
  base-lint:
    steps: [ checkout, run pre-commit hooks ]

  build-common:
    needs: base-lint
    steps: [ checkout, setup-java, build common module ]

  java-services:
    needs: [ base-lint, build-common ]
    strategy:
      matrix:
        service: [ gateway, switch, authorization, ... ]
    steps: [ checkout, setup-java, linter, build+unit-tests ]

  smoke-tests:
    needs: [ java-services, frontend-dashboard ]
    steps: [ build images, compose up, wait, run smoke ]

  e2e-tests:
    needs: [ java-services, frontend-dashboard ]
    steps: [ build images, compose up, run e2e ]
```
- `needs` — зависимости между джобами (порядок выполнения)
- Упавший джоб блокирует зависимые от него
- smoke и e2e идут параллельно после сборки сервисов

**Speaker notes:**

> Разберём порядок стадий через ключевое слово `needs` — оно задаёт зависимости между джобами.
>
> `base-lint` — первая стадия, от неё ничего не зависит, она запускается сразу. `build-common` зависит от `base-lint` — ждёт, пока линт пройдёт. `java-services` зависит от обоих. Логика: сначала проверяем стиль, потом собираем общий модуль, потом сервисы.
>
> `smoke-tests` и `e2e-tests` зависят от `java-services` и `frontend-dashboard`, то есть стартуют только после успешной сборки всех сервисов. И они идут параллельно друг с другом — обе нуждаются в собранных образах, но не друг в друге.
>
> Важное свойство: если `java-services` упал, например из-за красных unit-тестов, то `smoke-tests` и `e2e-tests` вообще не запустятся. Это и есть fail fast — не гонять дорогие E2E, когда базовые тесты уже упали.
>
> Вопрос аудитории: зачем `smoke-tests` и `e2e-tests` разделены? Почему нельзя объединить их в один джоб?
>
> Ответ: у них разные цели и разная стоимость. Smoke-тест — быстрый отсев базовой работоспособности, он должен упасть первым и быстро. E2E — дорогие сквозные сценарии, их гонять дольше. Разделение позволяет видеть в отчёте, что именно упало: базовый smoke или детальный E2E, и параллелить их независимо. Если объединить — один медленный тест заблокирует быструю обратную связь по smoke.

### Слайд 12. Разбор ci.yml: smoke-tests

**Слайд:**
```yaml
  smoke-tests:
    needs: [ java-services, frontend-dashboard ]
    steps:
    - run: cp .env.example .env
    - run: docker compose build
    - run: docker compose up -d
    - name: Wait for services to be ready
      run: |
        for i in {1..60}; do
          curl -s http://localhost:8080/health && break
          sleep 5
        done
    - run: ./scripts/smoke-test.sh
    - name: Show logs on failure
      if: failure()
      run: docker compose logs --tail=100
    - name: Cleanup
      if: always()
      run: docker compose down -v
```
- Поднимает весь стек СМП через Docker Compose
- Ждёт готовности Gateway через health-check в цикле
- Запускает smoke-скрипт, при падении выводит логи, затем чистит окружение

**Speaker notes:**

> Джоб `smoke-tests` — это уже интеграционный уровень пирамиды. Здесь поднимается весь стек СМП через Docker Compose и прогоняются smoke-тесты, о которых мы говорили на слайде 8.
>
> Разберём шаги по порядку. `cp .env.example .env` — создать файл окружения. `docker compose build` — собрать все образы. `docker compose up -d` — поднять все контейнеры. Затем ожидание готовности: цикл до шестидесяти итераций, каждые пять секунд curl на `http://localhost:8080/health`, пока Gateway не ответит. Это важно: контейнеры стартуют не мгновенно, и если не подождать, smoke-тест упадёт из-за неготовности сервиса, а не из-за реального бага.
>
> Дальше — `./scripts/smoke-test.sh`, тот самый smoke-скрипт. Обратите внимание на два полезных приёма. `if: failure()` — вывести последние сто строк логов только если что-то упало. И `if: always()` — очистить окружение (`docker compose down -v`) в любом случае, упал тест или прошёл. Иначе контейнеры будут висеть и тратить ресурсы раннера.
>
> Вопрос аудитории: зачем после цикла ожидания дополнительный `sleep 15` (в реальном ci.yml он есть)? Почему одного факта «health-check ответил» может быть недостаточно?
>
> Ответ: health-check Gateway может ответить «ok», но downstream-сервисы ещё не до конца поднялись и не установили соединения между собой. Короткая пауза даёт системе стабилизироваться — например, Switch ещё подключается к RabbitMQ, а Authorization к Card Management. Без этой паузы первые smoke-запросы могут упасть ложно. Это классическая проблема асинхронного старта распределённой системы, и с ней мы ещё столкнёмся в модуле 6 при интеграционном тестировании.

### Слайд 13. Makefile как локальный интерфейс к пайплайну

**Слайд:**
```makefile
run:    docker compose up -d
stop:   docker compose down
build:  docker compose build
smoke:  ./scripts/smoke-test.sh
test:   mvn test + npm test
lint:   mvn checkstyle:check + npm run lint
```
- Makefile — единая точка входа для локальных команд
- Те же команды, что в CI, но запускаются на машине разработчика
- Преимущество: разработчик локально воспроизводит то, что упадёт в CI
- `make test` и `make lint` — то же, что и в GitHub Actions

**Speaker notes:**

> В СМП есть [`Makefile`](https://github.com/LektonSoftwareTestingCourse/Practic/blob/main/Makefile) — единая точка входа для локальных команд. Зачем он нужен, если есть CI?
>
> Makefile фиксирует те же команды, что запускаются в CI, но локально. Разработчик может выполнить `make lint` и `make test` до push — и заранее узнать, что упадёт в пайплайне. Это сокращает цикл обратной связи ещё сильнее: не ждать CI-раннера, а гонять проверки на своей машине за те же минуты.
>
> Ключевое преимущество — консистентность. Локально и в CI выполняются одни и те же команды. Нет расхождения «на моей машине работало». Это устраняет целый класс проблем.
>
> Примеры целей: `make run` — поднять стек, `make smoke` — прогнать smoke-тест, `make test` — все unit-тесты (Maven и npm), `make lint` — все линтеры. Это ровно те же действия, что и в ci.yml, просто оформлены для локального запуска.
>
> Заметьте связь: `make smoke` — это локальный аналог джоба `smoke-tests` из пайплайна. Разработчик может прогнать тот же smoke-скрипт у себя, не дожидаясь CI. Это пример того, как быстрая обратная связь реализуется на нескольких уровнях.

### Слайд 14. Отчёты и уведомления в CI

**Слайд:**
- CI не только «зелёный/красный» — он должен давать информацию о падении
- Логи на падении: `docker compose logs --tail=100` при `if: failure()`
- Артефакты: сохранение отчётов тестов для анализа
- Уведомления: статус пайплайна виден в PR, на почте, в мессенджере
- Без читаемых отчётов CI превращается в чёрный ящик

**Speaker notes:**

> CI — это не просто «зелёный или красный». Главная ценность пайплайна — информация о том, что именно упало и почему.
>
> В СМП на падении выводится хвост логов: `docker compose logs --tail=100` при `if: failure()`. Это первая помощь при диагностике — видно, какой сервис упал и с какой ошибкой. Дальше — артефакты: CI может сохранять отчёты тестов (XML от JUnit, HTML от Allure), чтобы их можно было скачать и изучить. Полные отчёты Allure разберём в модуле 8.
>
> Уведомления: статус пайплайна автоматически отображается в pull request — красный крестик или зелёная галочка прямо в интерфейсе GitHub. Это базовая сигнализация: разработчик видит, что его PR ломает сборку, ещё до ревью.
>
> Без читаемых отчётов и уведомлений CI превращается в чёрный ящик: что-то упало, а что — непонятно. Команда начинает игнорировать красный билд, и мы возвращаемся к проблеме ice-cream cone из лекции 5: CI перестаёт быть сигналом качества.

### Слайд 15. Интерактив и выводы

**Слайд:**
- Ситуация 1: unit-тест упал в CI. Что происходит дальше? Какие стадии не запустятся?
- Ситуация 2: smoke-тест падает раз в пять прогонов. Какие гипотезы? Как диагностировать?
- Ситуация 3: пайплайн идёт 40 минут. Как сократить время, не теряя покрытия?
- Вывод: CI/CD — условие автоматизации, пайплайн как код, fail fast
- Модуль 4: Unit-тестирование на Java / JUnit 5

**Speaker notes:**

> Финальный интерактив — три практические ситуации. Обсуждаем, я дополняю.
>
> Ситуация 1: unit-тест упал. Цепочка `needs`: `java-services` зависит от `base-lint` и `build-common`, а `smoke-tests` и `e2e-tests` зависят от `java-services`. Значит, при падении unit-теста в `java-services` не запустятся `smoke-tests` и `e2e-tests`. Это правильно — гонять E2E, когда unit красный, бессмысленно.
>
> Ситуация 2: smoke-тест падает раз в пять прогонов. Это flaky-тест. Гипотезы: сервис не успел подняться — таймаут ожидания мал; гонка данных — тест создал карту, а параллельный прогон её уже удалил; порядок тестов не контролируется. Диагностика: смотреть логи при падении, увеличить таймаут, изолировать тестовые данные. Здесь работает та же логика приоритизации гипотез, что и при диагностике обычного бага: начинаем с самой вероятной причины.
>
> Ситуация 3: пайплайн идёт сорок минут. Способы ускорить: распараллелить сервисы через matrix (уже сделано), кэшировать зависимости Maven и npm, вынести E2E в ночной прогон, гонять только изменённые сервисы. Каждый способ — компромисс между скоростью и полнотой покрытия.
>
> Вопрос аудитории: в ситуации 3 — какие риски у подхода «гонять только изменённые сервисы»?
>
> Ответ: сервисы в микросервисной архитектуре связаны контрактами. Если вы гоняете тесты только для изменённого сервиса, вы можете пропустить регрессию в сервисах-потребителях, которые зависят от его контракта. Изменили формат ответа Switch — сломался Gateway, но тесты Gateway не запустились, потому что «Gateway не менялся». Это ровно та проблема контрактов, о которой пойдёт речь в лекции 9 модуля 5. Поэтому полный набор API-контрактных тестов всё равно должен гоняться в CI целиком или по графу зависимостей.
>
> Подведём итог лекции. CI/CD — условие существования автоматизации тестирования: тесты без автоматического запуска мертвы. Пайплайн как код версионируется и ревьюится. Fail fast: упавшая стадия останавливает зависимые. Пирамида — карта, куда ставить тесты по скорости: unit в pre-commit, API в CI, E2E в ночной прогон. Smoke-тест — быстрый барьер проверки базовой работоспособности перед полным тестированием.
>
> Следующий модуль — unit-тестирование на Java с JUnit 5. Вы будете писать тесты, которые этот самый пайплайн будет гонять по каждому push. Вопросы?
